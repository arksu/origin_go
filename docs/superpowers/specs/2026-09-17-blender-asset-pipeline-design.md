# Детерминированная сборка игровых 3D-ассетов

Статус: утверждено пользователем 2026-09-17. Согласованы канонические `.blend`,
внешний CLI с `asset.yaml`, сборка без MCP, Blender 5.2.1 LTS, разделение
runtime-файлов, миграция и проверки ниже.

## Цель и область

Одна команда пересобирает выбранный 3D-ассет, только его анимации либо весь
зарегистрированный 3D-каталог. Художественные правки выполняются в Blender,
сохраняются в исходнике и сохраняют силу при любой последующей сборке.

Поддерживаемые типы источников: character, equipment и world_object. Начальная
миграция охватывает существующие commoner и stone_axe. Контракт статического
world_object проверяется небольшим тестовым ассетом; замена игрового 2D-рендера
зданий/предметов на 3D является отдельной работой.

`all` означает все зарегистрированные 3D-ассеты. Конвейер не может заново
создать существующие PNG, звуки или другие ресурсы без соответствующих исходников
и рецептов. Историческая ветка Blender-to-sprites v1–v3 удаляется после миграции.

## Наблюдаемое текущее состояние

- `rig_meshy_commoner.py` читает анимационный донор из v3 и пересоздаёт rig v4.
- `prepare_stone_axe.py` ссылается на исходник в пользовательской Downloads.
- `merge_axe_animations.py` дописывает клипы в runtime-файл персонажа.
- `equipment.ts` содержит вручную перенесённые трансформы левого/правого хвата.
- `ActorAssetCache` использует Three.js GLTFLoader без настройки meshopt/KTX2.
- `ActorInstance` ожидает модель и все её клипы в одном GLB.
- `ActorSockets` создаёт отсутствующие sockets в начале координат кости.

Ранее измеренный runtime commoner: 2 928 156 байт, из них текстура 1 775 866;
stone_axe: 603 820 байт, из них текстура 479 962. Это базовая точка сравнения,
а не обещание конкретного коэффициента сжатия.

## Исходники и владение данными

```
art_source/<kind>/<asset-id>/
  source.blend
  asset.yaml
  references/
  build/                 # игнорируется Git
```

В CLI и путях используются одинаковые singular kind: `character`, `equipment`,
`world_object`. Runtime-каталог задаётся декларацией, поэтому текущие публичные
категории `characters` и `equipment` могут сохраниться.

`source.blend` хранит художественные данные: геометрию, редактируемые модификаторы,
материалы, упакованные текстуры, rig, actions, poses и sockets. Сборщик открывает
файл для чтения, работает в памяти/временной копии и никогда не сохраняет
исходник поверх оригинала. Пересоздание рига, процедурный ретаргет и генерация
анимаций не являются скрытыми стадиями обычного build.

`asset.yaml` объявляет schema version, ID, тип, runtime-путь, экспортируемые actions,
диапазоны кадров, loop-правила, требования к rig, LOD/texture/size budgets,
профиль оптимизации и явные зависимости. Ключи анимаций и трансформы хвата
находятся только в Blender. Неизвестные поля и дублирующиеся ID — ошибки.

Игровые метаданные клипа (например, расстояние за цикл walk и режим движения
по времени/дистанции) объявляются в конфиге и попадают в manifest. Они не
дублируются константами в клиенте. Изменение длины шага требует согласованного
обновления этого значения, которое показывается в отчёте сборки.

Коллекция `EXPORT` содержит только экспортируемые сущности; `PREVIEW` — сцены
примерки и визуальные помощники. `ASSET_INFO` описывает контракт и порядок работы.
При открытии пользователь видит рабочую модель, доступные controllers/actions
и точки привязки. Preview показывает игровой масштаб и существующее освещение.

В персонаже sockets — именованные объекты с однозначной привязкой к костям.
В equipment две именованные точки `GRIP_L`/`GRIP_R` задают локальные системы
координат хвата. При прикреплении socket персонажа совмещается с grip предмета;
преобразование из Blender в runtime вычисляет сборщик. Допустимые слоты и режим
анимации рук объявляются в конфиге, численные трансформы извлекаются из `.blend`.

Для примерки предмет открывается с reference-персонажем в `PREVIEW`, связанным
относительным путём с его каноническим источником. Редактируются локальные grips
предмета; rig и actions персонажа редактируются в его собственном source.blend.
Связанные исходники входят в список зависимостей и проверяются при открытии.

## Команды

```
tools/assets build character/male_commoner
tools/assets build character/male_commoner --animations
tools/assets build character/male_commoner --animations --clip walk
tools/assets build all
tools/assets validate all
tools/assets verify-reproducible character/male_commoner
```

Обычный build пересобирает весь выбранный ассет. `--animations` обновляет только
клипы и ссылки на них. Несуществующий ID/action и режим animations для
статического объекта завершаются понятной ошибкой до публикации.

Для частичной сборки требуется ранее собранная модель. Экспортная проверка
сравнивает отпечаток неанимационной части источника с опубликованной моделью:
геометрия, bind/rest pose, материалы, sockets, экспортный конфиг и toolchain.
Смена только ключей не нарушает совместимость; изменение rig или других
неанимационных данных требует полного build. Для такой проверки допустима
временная подготовка меша, но повторное сжатие/публикация модели не выполняется.

## Runtime-выход и загрузка

Логические результаты ассета:

```
model.glb                  # меши, rig, sockets; без клипов
animations/<clip>.glb      # узлы rig и один клип; без мешей/текстур
textures/<texture>.ktx2
manifest.json
```

Имена физических артефактов содержат хеш содержимого. Manifest и общий каталог
связывают стабильные asset/clip ID с файлами и совместимостью. Это позволяет
менять клип без изменения URL модели и повторной загрузки текстур.

Модель и клипы содержат стабильные уникальные экспортные имена узлов и общий
rig fingerprint: иерархию, rest transforms и bind contract. Загрузчик проверяет
совместимость и привязывает animation tracks по этим именам к клону модели;
случайные UUID загруженной animation scene не являются ключами привязки.
Actions удерживаются общим кешем, экземпляры персонажей имеют собственный mixer.

Клиент читает sockets и bindings из результата сборки. Отсутствующие обязательные
sockets считаются ошибкой; ручное дублирование трансформов в TypeScript прекращается.
Политика ordinary/layered движения рук сохраняется из действующего каталога.

Для сжатия выбирается meshopt и KTX2/Basis Universal. Профиль текстур закрепляет
codec, quality, dimensions и mipmap settings. Параметры выбираются по сравнению
с текущей картинкой на игровом размере; конкретные бюджеты фиксируются после
измерения мигрированных ассетов. Не допускается проход build с неуказанным бюджетом.

Декодеры устанавливаются локально вместе с клиентом. Настраиваются KTX2 support
для игрового renderer, context restoration, освобождение ресурсов и оценка памяти
с учётом фактического формата/mipmaps. Сжатие на диске не приравнивается к размеру
декодированных буферов или GPU-памяти.

## Воспроизводимость и публикация

Blender закрепляется на 5.2.1; проверяется фактическая версия бинарника. Точный
build hash записывается в toolchain lock. Также закрепляются Python/Node окружение,
glTF exporter, optimizer, encoder и validator. Сборка не загружает зависимости из
сети; установка инструментов выполняется отдельно по lock-файлам.

Каждый ассет обрабатывается новым background-процессом Blender с отключённым
автозапуском Python из `.blend` и пользовательскими startup/addon настройками.
Порядок сущностей/клипов стабилен; случайные seeds фиксированы; даты и абсолютные
локальные пути не попадают в игровые артефакты. Диагностические логи могут иметь время.

Обязательная гарантия: две чистые сборки одних входов на одинаковой закреплённой
toolchain/platform дают одинаковые SHA-256 runtime-файлов. Это подтверждается
командой verify-reproducible. Межплатформенная побайтовая идентичность не обещается
без отдельной проверки; платформа отражается в provenance.

Стадии: preflight → проверка source → экспорт во staging → оптимизация →
проверка runtime → публикация. Сначала записываются проверенные артефакты с хешами,
затем атомарно переключается общий каталог. До переключения все прежние ссылки
остаются рабочими. Для build all переключение выполняется после успеха всего набора.
Параллельные публикации предотвращаются блокировкой; ошибка оставляет прежний каталог.
Очистка старых опубликованных поколений не является побочным эффектом build.

Provenance записывает хеши источников/зависимостей/конфига/инструментов, runtime hashes,
размеры по категориям, треугольники, rig и clips, применённые профили и результаты
проверок. Полный source hash может измениться при изменении редакторского UI;
отпечаток экспортируемого содержания вычисляется отдельно.

## Проверки и критерии приёмки

- Исходник существует, все зависимости локальны и разрешимы; размеры/числа конечны.
- Валидны коллекции, уникальные имена, материалы, веса, rig hierarchy и sockets.
- Каждый заявленный action экспортирован с ожидаемой длительностью и loop-правилом.
- Официальный glTF validator проходит после оптимизации; выдерживаются budgets.
- Клиент загружает сжатые результаты, все текущие клипы и оба хвата работают.
- Частичная пересборка walk меняет только его артефакт и служебные ссылки.
- Несовместимый rig и отсутствующий socket дают явную ошибку.
- Ошибка любого build не переключает опубликованный каталог.
- Две чистые сборки дают совпадающие runtime hashes; source.blend не изменяется.
- Визуальное сравнение: направления, idle/walk/carry, оба хвата, LOD,
  прозрачность, игровой масштаб и восстановление контекста.
- Ручной smoke test: открыть source, изменить grip/ключ, сохранить, собрать,
  проверить изменение в игре без MCP и ручного редактирования TypeScript/JSON.

## Миграция и удаление legacy

1. Зафиксировать действующие модели, клипы и хваты как baseline для сравнения.
2. Подготовить канонические commoner/stone_axe source.blend с редактируемыми actions,
   sockets и preview. Перенести одобренные ручные правки из дополнительных сцен.
3. Сохранить действующие анимации непосредственно в новом источнике персонажа;
   устранить чтение v3 donor при сборке. Сохранить требуемые сведения о происхождении.
4. Реализовать CLI, проверки, оптимизацию и публикацию; подключить runtime-каталог.
5. Подтвердить визуальное соответствие, повторяемость и частичную пересборку.
6. Удалить проверенный перечень исходников v1–v3, их генераторов/bake-скриптов,
   устаревших GLB и рабочих дублей, уже перенесённых в канонические источники.
   Исторические документы явно пометить как superseded; действующие инструкции обновить.
7. Проверить отсутствие рабочих ссылок на удалённые пути и выполнить чистый build all.

Перед удалением проверить отслеживание файлов Git: неотслеживаемые уникальные
материалы перенести в references или сохранить в резервную копию. Само удаление
legacy уже запрошено пользователем; Git-история сохраняет отслеживаемые версии.
