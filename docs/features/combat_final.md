# Origin: итог проработки non-target боевой системы

Дата фиксации: 2026-10-04.

Назначение: сохранить решения и рассуждения из обсуждения так, чтобы продолжить проектирование по этому документу без истории чата. Это документ дизайна, а не отчёт о реализованной боевой системе.

## 1. Как читать документ и продолжать работу

В документе используются четыре статуса:

- **Утверждено** — пользователь выбрал правило или принял соответствующее предложение. Не возвращать отвергнутые альтернативы без новой причины.
- **Рабочая модель** — формула или детализация, предложенная в обсуждении для развития выбранного подхода. Сохранена для продолжения; её численные коэффициенты и неоговорённые детали нельзя считать окончательно утверждёнными.
- **Открыто** — решения ещё нет. Не заполнять этот пробел молча.
- **Текущее состояние кода / исследование** — проверенный контекст. Наличие механики в другой игре или в старом коде не означает её принятия для нового боя.

Последние уточнения пользователя имеют приоритет над ранними пожеланиями. Пользователь принял весь пакет из 30 рекомендаций с тремя уточнениями: кровотечение пока не требуется; объекты boulder пропускают стрелы; `chance` записывается в диапазоне 0–1, например `0.35`. Основные разделы отражают этот пакет. Принятые начальные значения можно балансировать; принятие модели не означает, что вся таблица оружия и противников уже рассчитана.

Позднее пользователь утвердил стартовый пресет v0 из раздела 17.1: задача первой редакции — реализовать и проверить механики; идеальный баланс и полная таблица прогрессии не требуются. Также уточнены исключение атакующего из целей топора, повреждение всех объектов мира с уничтожением при HP = 0, использование общей боевой системы монстрами и добровольный подъём после 60 секунд KO.

**Последнее уточнение, 2026-10-04:** боевые приёмы используют существующую механику действий и стандартный прогрессбар. `execution.ticks` задаёт длительность выполнения топора; при 100% сервер повторно проверяет условия и выполняет приём. Stamina и собственный cooldown топора относятся к моменту выполнения, включая промах. Движение отменяет незавершённый приём без урона, оплаты и нового cooldown. Recovery полностью исключён; после завершения можно сразу начать другое доступное действие. Лук сохраняет удержание и отпускание кнопки, частичное натяжение, начальную оплату и расход за время; 100% означает полное натяжение, выпуск происходит только при отпускании.

**Уточнение области первого боевого этапа, 2026-10-04:** сразу реализуется рабочая модель урона по игрокам и всем объектам игры. Попадания используют фактические collider и здоровье существующих игровых сущностей: SHP/HHP и правила KO/смерти для игроков, HP и уничтожение при HP = 0 для обычных объектов мира. Сохранение дробного здоровья, загрузка и последствия уничтожения входят в подключение соответствующих получателей урона. Проверки выполняются на этих же игровых сущностях через общий боевой путь; отдельного предварительного этапа с другим набором получателей или моделью здоровья нет.

Эти решения заменяют прежние правила обязательного выполнения топора, оплаты при старте и движения на Crawl во время атаки. При дальнейшем планировании [combat_phases.md](combat_phases.md) и [combat_protocol.md](combat_protocol.md) нужно согласовать с этой редакцией; их прежние правила жизненного цикла и ограничения первого этапа по получателям урона не имеют приоритета над последними решениями пользователя. Область рабочего урона можно разделить на несколько изменений по техническим зависимостям, сохраняя общую модель и прямое подключение игровых сущностей.

Предыдущие обсуждения проходили в режиме explore. Пользователь явно разрешил сохранить их в этом отдельном документе. Создание документа не означает разрешения реализовать боевую систему, менять существующие спецификации или фиксировать невыбранные параметры.

Исходные материалы:

- [combat2.md](combat2.md) — исследование сложности Legacy-боя H&H и вариантов упрощения.
- [combat_system.md](combat_system.md) — исследование Legacy-умений и боевой модели H&H.
- [knocked_dead.md](knocked_dead.md) — прежняя заметка о KO/death; некоторые её выводы уточнены в разделе 15.

Эти материалы являются справочным исследованием. Описанные там ATK/DEF, Initiative, Intensity, Advantage, карточки приёмов и прочие механики Legacy не входят автоматически в выбранную систему Origin.

## 2. Краткий реестр принятых решений

| Область | Принятое правило |
|---|---|
| Основа | Non-target: попадание определяется геометрией удара или столкновением снаряда |
| Урон | Один тип урона |
| Повреждаемые цели | Все объекты мира с действующим запасом здоровья; существа используют SHP/HHP, остальные объекты — HP и уничтожаются при HP = 0 |
| Самопопадание топором | Атакующий исключается по ID до геометрического отбора и выбора ближайшей цели обоих приёмов |
| Монстры | Их приёмы основаны на той же системе действий, попаданий, урона, cooldown и эффектов |
| Friendly fire | Союзники — обычные цели, без исключений для группы или дружбы |
| Прогрессия | Без искусственного общего потолка силы ветерана; late game должен сохранять смысл |
| PvP-разрыв | Около двух ударов ветерана до KO новичка допустимо; это ориентир, не гарантированный минимум |
| Формула melee | `Draw = B × (STR/S0)^0.25 × (Qweapon/Q0)^0.25 × ActionDamageMultiplier`; начальные нормировки `S0 = 1`, `Q0 = 10` |
| Броня | `A = Σ BaseArmor × sqrt(Q/Q0)` по надетым предметам; итоговый урон `D = Draw² / (Draw + A)` |
| Доспехи | Тип и Quality влияют на очки брони; сериализацию сейчас не проектируем |
| Топор | Два отдельных действия: удар по площади и усиленный удар по одной ближайшей цели |
| Первая редакция v0 | Два приёма топора, лук с натяжением и отдельными стрелами, общая система бафов/дебафов, начальная рана и поддержка stunned; конкретный оглушающий приём — отдельно |
| Геометрия топора | Одна проверка сектора 90° при 100% серверного прогресса; направление фиксируется при старте; дальность обоих приёмов одного топора одинакова |
| Преграды для топора | Не проверяются: стены и другие объекты не закрывают цель от обоих ударов |
| Выбор одиночной цели | В момент удара, по расстоянию до ближайшей части collider внутри сектора |
| Выполнение топора | Стандартный цикл действий и прогрессбар; длительность задаёт `execution.ticks`; на 100% — повторная проверка условий и выполнение приёма |
| Движение с топором | Принятая команда движения отменяет выполнение без урона, оплаты и нового cooldown; особого режима Crawl для атаки нет |
| Отмена топора | Стандартные отмена и переключение действия доступны до выполнения; незавершённый приём не оплачивается |
| Завершение боевого действия | После выполнения или отмены нет дополнительной задержки; новое действие проверяется по собственному cooldown, ресурсам и состоянию персонажа |
| Прерывание станом или KO | Незавершённое действие отменяется; ранее запущенные cooldown других выполненных действий продолжают идти |
| Обычное попадание | Само по себе не сбивает выполнение топора или натяжение лука, пока сохраняются условия действия |
| Последствия приёма | Один приём может накладывать несколько дебафов; независимая проверка каждого на каждой задетой цели |
| Шанс дебафа | После проверки применимости к цели — один фиксированный `chance` в диапазоне **0–1** на дебаф целиком; например, `0.35 = 35%`; при успехе включаются все его эффекты |
| Бафы и дебафы | Общая система статусов по образцу L2J; статус содержит один или несколько эффектов |
| Идентичность и замена статуса | У каждого бафа/дебафа свой ID; новое успешное наложение безусловно заменяет активный статус с тем же ID |
| Рана | Дебаф с собственными эффектами, который может быть наложен попаданием с определённым шансом |
| Срок раны | Сохраняется до явного снятия, без автоматического истечения по времени |
| Начальная рана | Общий для двух приёмов топора ID; `STR −10%`, `chance = 0.15`, `durationMs = null`; начальные значения для балансировки |
| Кровотечение | Пока не входит в текущую фазу; правила DoT отложены |
| Повторная рана с тем же ID | Новый экземпляр заменяет прежний; одновременно действует один экземпляр, бессрочность сохраняется |
| Штрафы разных дебафов | Штрафы к одной характеристике суммируются, а не заменяются сильнейшим |
| Модификаторы характеристик | В definitions поддерживаются фиксированные и процентные изменения |
| Расчёт модификаторов | Сначала сумма фиксированных изменений, затем общий процентный множитель; порядок наложения статусов не влияет на результат |
| Нижние границы атрибутов | Эффективная характеристика не ниже **1**, процентный множитель не ниже **0** |
| Дробные характеристики | Дробная часть эффективных значений сохраняется в расчётах |
| CON и максимумы ресурсов | MHP и максимум stamina рассчитываются от эффективного CON с учётом бафов, дебафов и дробной части |
| lifeDeathFactor | Постоянный множитель MHP для существующего мира; v0 = 1.0; изменение только после полного wipe, не на горячую и не обычным перезапуском |
| Текущее здоровье при изменении MHP | Абсолютные HHP/SHP сохраняются с обрезкой по новым пределам; увеличение MHP их не восстанавливает |
| Текущая stamina при изменении максимума | Абсолютный запас сохраняется с обрезкой по новому максимуму; рост максимума ничего не восполняет |
| Временные дебафы | Длительность — положительное целое число миллисекунд; durationMs = null означает бессрочность |
| Повторный временный статус с тем же ID | Параметры и срок берутся из нового применения; окончание `now + новая длительность` |
| Сила при замене статуса | Не сравнивается: слабое применение также заменяет сильное с тем же ID |
| Оглушение | Отдельный эффект специального приёма; прерывает действие, не тождественен KO |
| Повторный stun с тем же ID | Новый экземпляр с окончанием `now + новая длительность`, даже если новый срок короче оставшегося |
| Снятие stun уроном | Один общий бросок 10% на обычный входящий damage-вызов, включая нулевой результат; при успехе снимаются все прежние воздействия stun, остальные воздействия сохраняются |
| Порядок попадания | Урон и проверка снятия старого stun, затем новые эффекты этого попадания |
| Cooldown | Собственный у каждого действия; два удара топора имеют независимые cooldown |
| Начало cooldown топора | При выполнении на 100% серверного прогресса, включая промах |
| Оплата stamina за топор | Вся стоимость один раз при выполнении на 100%; отмена или провал финальной проверки не оплачиваются |
| Промах топора | Выполненный приём с пустым набором попаданий; полная стоимость и cooldown применяются |
| Начало cooldown лука | При фактическом выпуске стрелы |
| Оплата stamina за лук | Начальная стоимость при начале натяжения, затем постоянный расход за время натяжения и удержания; выпуск без доплаты |
| Возврат stamina за лук | При отмене натяжения/удержания не возвращаются ни начальная стоимость, ни расход за время |
| Исчерпание stamina с луком | Натяжение/удержание отменяется, персонаж опускает лук без автоматического выстрела |
| Лук | Отдельная стрела с маленьким collider, прямой полёт с постоянной скоростью |
| Сила натяжения | Максимум зависит от STR игрока; дальность зависит от достигнутого натяжения |
| Время натяжения | Задаётся типом лука, не растёт вместе с STR |
| Минимальное натяжение | `charge = 0.10`; отпускание раньше отменяет действие без стрелы и cooldown, stamina не возвращается |
| Прогресс лука | Показывает натяжение; на 100% продолжается удержание до отпускания кнопки, автоматического выпуска нет |
| Качество выстрела | `Qshot = sqrt(Qbow × Qarrow)`; качество учитывается один раз |
| Боеприпас | Доступная стрела из личного инвентаря обязательна до оплаты старта; резервируется при натяжении, списывается при выпуске, освобождается при отмене |
| Движение с луком | Во время натяжения и удержания персонаж стоит |
| Отмена лука движением | Команда движения отменяет натяжение и позволяет сразу перейти к движению |
| Спад урона стрелы | Первые 30% дальности выстрела — 100%; затем линейно до 20% |
| Преграды для стрелы | Объекты с collider по умолчанию блокируют, включая контейнеры и мебель; **boulder, трава, мелкий декор и трупы пропускают** |
| Stamina | Разрешено расходовать до нуля, без обязательного резерва для боя |
| Здоровье существ | `softPart = min(D, SHPbefore)`; SHP уменьшается на softPart, HHP — на `0.20 × softPart + (D − softPart)`, без повторного начисления доли на overflow |
| Урон и рана | Прямое уменьшение SHP/HHP не зависит от успеха наложения дебафа-раны |
| Восстановление HHP | Только лечением; самостоятельного восстановления нет |
| Лечение | Взаимодействие с дебафами; конкретная механика исключена из scope текущего обсуждения |
| Персонаж в активном KO | Весь рассчитанный урон идёт в HHP; после окончания 60 секунд — обычное распределение SHP/HHP, даже если персонаж продолжает лежать |
| KO | Первые 60 секунд подняться нельзя; затем доступен добровольный подъём, можно продолжить изображать нокаут |
| Повторный KO | Попадания во время активного KO не продлевают таймер; новое исчерпание SHP после его завершения запускает новые 60 секунд, даже без физического подъёма |
| Выход из боя | Тело остаётся до более позднего срока: окончание KO или 30 секунд после LastCombatEventAt; точный перечень событий — раздел 13.6 |
| Сохранение | Статусы, KO, cooldown и LastCombatEventAt сохраняются; абсолютные сроки продолжают идти при переподключении и перезапуске. Выпущенные стрелы при перезапуске удаляются без компенсации |
| Hearth Fire | Через 30 секунд KO доступен будущий возврат к Hearth Fire |
| Пробуждение и подъём | Через 60 секунд KO заканчивается, живому обеспечивается минимум 1 SHP в пределах HHP; подъём добровольный и повторно здоровье не восстанавливает |
| Добровольное лежание | До подъёма нельзя двигаться, ползти, атаковать, натягивать лук или выполнять другие игровые действия; доступен только подъём при отсутствии блокирующих состояний |
| Collider лежащего в v0 | Размеры, положение относительно персонажа и фильтры столкновений не меняются из-за позы; лежание не даёт геометрической защиты |
| Смерть | HHP = 0; возможна сразу от удара, без обязательного промежуточного KO |

Подробные границы этих правил и оставшиеся вопросы приведены далее.

## 3. Цели боя и прогрессии

### 3.1. Non-target и тактика

**Утверждено.** Игрок атакует в направлении взгляда/прицеливания. Ему не требуется предварительно закреплять противника как target. Для топора проверяется область удара, для лука — траектория отдельного снаряда.

Тактическое значение имеют дистанция, положение, направление атаки, момент начала и длительность действия, расход stamina и ошибки противника. Автоматический выбор ближайшей цели у одного приёма топора остаётся частью non-target модели: цель определяется внутри геометрии конкретного удара, а не сопровождается заранее.

### 3.2. Как изменилось требование к разрыву сил

Сначала пользователь выбрал заметное преимущество развития с возможностью победить тактикой, затем попросил умерить разрыв из-за permadeath. Позднее он явно уточнил окончательную позицию:

- Искусственно жёстко ограничивать развитие ветеранов нельзя: это разрушит late game.
- В мире будут более сильные монстры и более сложные условия.
- Допустим ориентир около двух попаданий ветерана до KO новичка.
- В таком столкновении отсутствие у новичка реальных шансов осознанно принимается.
- Снижение угрозы новичкам предполагается решать разными областями обитания и отсутствием смысла их убивать.

**Окончательное правило:** не балансировать весь бой вокруг равных шансов новичка и ветерана. Тактика важна, но не обязана компенсировать произвольно большую разницу развития.

«Два удара» не означает защиту от первого смертельного попадания, принудительный нижний предел TTK или ограничение максимального урона. При достаточно большой разнице сил возможна смерть от одного удара.

Географическое разделение игроков, награды, стоимость агрессии, преступления и экономические стимулы пока не спроектированы. Указанное направление не является уже существующей системой защиты новичков.

### 3.3. Один тип урона

**Утверждено.** Сейчас нет отдельных режущего, колющего, дробящего, магического и других типов урона и соответствующих сопротивлений.

SHP и HHP — два последствия одного рассчитанного попадания. Это не два разных типа урона.

### 3.4. Приёмы монстров

**Утверждено:** монстры будут иметь приёмы, основанные на этой же боевой системе. Их атаки используют общие определения и жизненный цикл действий, геометрию попаданий, cooldown, расчёт урона/брони и механизм бафов/дебафов. AI выбирает и запускает приём через общий серверный путь; отдельной упрощённой системы попаданий и урона для монстров не создаём.

Параметры конкретного монстра и его приёмов могут отличаться: базовый урон, характеристики, дальность, времена и список эффектов задаются контентом. Монстру не требуется физический предмет «топор», чтобы использовать общий механизм секторной атаки. Конкретный набор приёмов монстров, их числа и поведение AI не входят в стартовый пресет игрока и будут наполняться позднее.

## 4. Урон, STR, Quality и броня

### 4.1. Обозначения

| Обозначение | Значение |
|---|---|
| `B` | Базовый урон оружия/действия в выбранной модели |
| `STR` | Сила атакующего |
| `CON` | Конституция, влияющая на существующие максимумы здоровья и stamina |
| `Qweapon`, `Qbow`, `Qarrow`, `Qi` | Quality оружия, лука, стрелы и отдельного предмета брони |
| `Qshot` | Общее качество выстрела: `sqrt(Qbow × Qarrow)` |
| `S0`, `Q0`, `F0` | Положительные опорные значения для нормировки |
| `Draw` | Сила попадания до применения брони; уже с модификатором действия и дистанции |
| `A` | Суммарные очки брони конкретной цели |
| `D` | Полученный урон после брони, перед применением к SHP/HHP существа либо HP объекта |
| `alpha` | Доля обычного урона, повреждающая HHP |

Здесь `Draw` означает raw damage, а не натяжение лука. Сила натяжения далее обозначается `F`.

### 4.2. Принятая формула ближнего урона

**Утверждено для первого балансного прогона:**

```text
DmeleeBase = B × (STR / S0)^0.25 × (Qweapon / Q0)^0.25
Draw      = DmeleeBase × ActionDamageMultiplier
```

Нормировки первого прогона: `S0 = 1` — исходное значение атрибутов в текущем проекте; `Q0 = 10` — удобное опорное качество. Это нормировки формулы, а не ограничения характеристик.

Идея степенного роста — сохранить непрерывную пользу развития без чрезмерно резкого роста от каждого множителя. При такой формуле:

- Рост только STR в 16 раз даёт двукратный множитель урона.
- Рост только Quality в 16 раз также даёт двукратный множитель.
- Одновременный рост обоих в 16 раз даёт четырёхкратный урон до брони.
- Формула не имеет общего верхнего потолка.

**Статус:** формула и показатели степени 0.25 приняты. Стартовых чисел v0 достаточно для реализации механик; проверка всей прогрессии и расширенный каталог оружия отложены до игровых проб.

Для первой редакции принят один топор с `B = 6`; множители AoE/одиночного удара — `1.0 / 1.5`. Полный стартовый пресет и проверенные примеры приведены в разделе 17.1. Дальнейшая настройка прогрессии не блокирует реализацию механик.

### 4.3. Очки брони от экипировки

**Утверждённая формула первого балансного прогона:**

```text
Ai = BaseArmor(itemType_i) × sqrt(Qi / Q0)
A  = sum(Ai)
```

Тип предмета определяет базовую защиту, Quality масштабирует её. Считаются предметы, действительно дающие очки брони. Собственная броня рассчитывается для каждой поражённой цели.

**Утверждено:** учитывать только фактически надетые предметы с очками брони, каждый один раз. Использовать существующие слоты и ограничения экипировки. Дополнительные слои и защита отдельных частей тела в этой фазе не вводятся. Для v0 выбраны тестовые предметы с `BaseArmor = 4` и `8`; при Quality 10 проверяются суммарные значения 0, 4 и 12. Полный каталог экипировки отложен.

**Утверждено для v0:** у обычных неживых объектов мира `A = 0`. Отдельного источника собственной брони построек, boulder, мебели и контейнеров в этой редакции нет; его можно добавить позднее. Броня существ продолжает считаться по принятым правилам экипировки. Отсутствие брони не исключает объект из целей.

Пользователь отдельно исключил из текущего обсуждения сериализацию доспехов. Здесь не задаются JSON-поля, формат сохранения, миграции или изменения item definitions.

### 4.4. Выбранный подход: броня зависит от силы удара

**Утверждён выбранный вариант** «зависимость от силы удара». Его сохранённое математическое выражение:

```text
D = Draw × Draw / (Draw + A)
DamageReductionFraction = A / (Draw + A)
```

Следствия:

- При `A = 0` весь положительный `Draw` проходит в здоровье.
- Одна и та же броня поглощает большую долю слабого удара и меньшую долю сильного.
- При `Draw = A` проходит половина урона.
- При конечной броне и положительном ударе результат положителен; отдельного порога «броню вообще невозможно пробить» эта формула не вводит.
- Для нулевого урона результат должен быть нулём, включая случай `Draw = A = 0`.

Иллюстрация при `A = 50`:

| Урон до брони | Урон после брони | Поглощённая доля |
|---:|---:|---:|
| 25 | 8.33 | 66.67% |
| 50 | 25 | 50% |
| 100 | 66.67 | 33.33% |
| 200 | 160 | 20% |

Таблица объясняет формулу и не задаёт параметры реальной экипировки.

Не вводить по умолчанию минимальный урон 1, жёсткий предел поглощения или дополнительный cap урона: такие правила не выбирались. Расчёты ведутся с дробной точностью `float64`; округляется только отображение. Дробный урон не обрезается до целого перед применением к здоровью.

### 4.5. Порядок вычисления

```text
базовый урон + STR/Quality/натяжение
--> множитель конкретного действия
--> спад от дистанции, если это стрела
--> броня конкретной цели
--> SHP/HHP существа либо HP объекта
--> смерть / KO существа либо уничтожение объекта либо продолжение боя
```

Усиление одиночного удара применяется **до брони**. Поэтому множитель силы приёма не равен множителю конечного урона по бронированной цели.

**Утверждено:** направление топора фиксируется при принятом старте действия; стоимость задаётся definition и списывается при выполнении на 100% прогресса. Эффективный STR атакующего и броня цели берутся в момент попадания. Для стрелы параметры атаки фиксируются при выпуске, броня цели — при столкновении.

Например, при `A = 50` обычный `Draw = 50` даёт `D = 25`. Если приём увеличивает исходный урон в 1.5 раза, `Draw = 75` даёт `D = 45`, то есть итог вырос в 1.8 раза. Значения A и Draw здесь иллюстративные; множитель одиночного удара 1.5 позднее принят для пресета v0.

## 5. Топор: два самостоятельных приёма

### 5.1. Общие правила

**Утверждено:**

- Оба приёма используют сектор **90°**.
- Атакующий **никогда не является целью собственного удара топором**: его ID исключается из кандидатов до проверки сектора, расчёта расстояний и выбора ближайшей цели. Это правило обоих приёмов, а не допуск геометрии или частный случай friendly fire.
- Направление фиксируется **при принятом старте действия**.
- После старта нельзя довернуть сам сектор вслед за новым направлением прицеливания.
- Попадание определяется **одной проверкой при выполнении на 100% серверного прогресса** по фактическому положению участников; длительного активного окна попадания нет.
- Положение сектора связано с фактической позицией атакующего в момент выполнения. Само действие не перемещает персонажа.
- Достаточно пересечения **любой части collider цели** с сектором в пределах дальности. Центр цели не обязан находиться внутри сектора.
- **Преграды не проверяются** для обоих приёмов: стены, другие объекты, персонажи и животные не заслоняют цели от удара.
- Для завершения приёма персонаж остаётся на месте. Принятая команда движения, включая WASD, отменяет выполняемое действие через стандартный путь отмены. Ограничения скорости до Crawl от атаки нет.
- Полный выход collider цели из зоны до момента удара приводит к промаху по этой цели.

Для симметричного сектора 90° это соответствует отклонению до 45° в каждую сторону от зафиксированного направления. У двух приёмов одного топора одинаковая дальность: в пресете v0 **18 мировых единиц (1.5 тайла)** от позиции атакующего.

Проверка только по сектору — осознанное правило. Если collider цели пересекает сектор, стена между игроком и целью не отменяет попадание. Это относится и к AoE, и к одиночному удару; для стрел остаются отдельные правила столкновения с препятствиями из раздела 8.

### 5.2. Удар по области

- Поражает все допустимые цели по определению раздела 11.1, попавшие в область удара; атакующий исключён.
- Одна цель получает урон не более одного раза от одного удара.
- Общая сила атаки не делится между числом целей.
- Каждой цели применяется её собственная броня, затем урон распределяется по её модели здоровья: SHP/HHP существа либо HP объекта.
- Союзники входят в набор целей на общих основаниях.

Идея: удобство против нескольких целей оплачивается меньшей силой отдельного попадания по сравнению с одиночным приёмом.

### 5.3. Усиленный удар по одной цели

- Использует тот же сектор **90°**, а не более узкий луч или конус.
- В момент удара выбирает **одну ближайшую допустимую цель** по разделу 11.1 из того же набора пересечений, который использует AoE; атакующий исключён до сравнения расстояний.
- Наносит больше исходного урона, чем удар по области.
- Выбор не закрепляется при старте действия и не сопровождает убегающую цель.
- Ближайшей целью может оказаться союзник или объект мира, например дерево, стена или boulder. Приоритета существ над остальными объектами нет.

**Утверждённая метрика:** расстояние от позиции атакующего в момент удара до ближайшей точки той части collider цели, которая находится внутри сектора. Не использовать центр цели или ближайшую точку collider, лежащую вне сектора.

Формально, если `S` — сектор удара с учётом дальности, `C` — collider цели, а `O` — вершина сектора, цель входит в набор кандидатов только при выполнении общего предиката раздела 11.1, `target.id != attacker.id` и непустом пересечении `C ∩ S`. Для одиночного удара сравнивается `distance(O, C ∩ S)`. Собственный collider атакующего не участвует в этой метрике, даже если пересекает вершину сектора.

Примеры: крупная цель может быть задета краем collider при центре за пределами угла или дальности; маленькая цель с более близким центром не обязательно будет выбрана, если пересекающая сектор часть collider другой цели находится ближе.

**Утверждено:** касание границы сектора или его предельной дальности считается контактом. При равных расстояниях выбирать цель по стабильному ID, чтобы результат не зависел от порядка обхода. Технический допуск погрешности не должен заметно расширять сектор. Конкретный допуск и направление сортировки ID оформляются при реализации.

### 5.4. Стандартное выполнение с прогрессбаром

```text
проверка старта --> executing + стандартный прогрессбар
--> 100% на сервере --> повторная проверка условий
--> выполнение приёма: оплата + cooldown + удар/промах --> завершение
```

**Утверждено:** оба приёма топора используют существующие `ActionService`, цикл timed actions и стандартные сообщения прогресса/завершения. `execution.ticks` — полная длительность действия, в v0 6 ticks (0.6 секунды при 10 Hz). Отдельных подготовительной и восстановительной фаз, таймеров или боевого прогрессбара нет. Стандартная анимация действия может отображаться на той же серверной шкале.

До принятия старта проверяются cooldown, требования к навыкам и экипировке, состояние исполнителя и достаточность stamina на одно выполнение. Во время действия сохраняются обычные проверки актуальности условий. При достижении 100% сервер ещё раз проверяет все условия непосредственно перед эффектом: исполнитель существует и может действовать, требования выполнены, stamina хватает, cooldown готов, направление допустимо. Затем определяется фактический набор пересечений сектора и выполняется приём.

Финальная проверка, списание стоимости, запуск cooldown и применение результата должны быть согласованы в одном серверном шаге. При отказе нет урона, оплаты или нового cooldown. Отсутствие целей в секторе — обычный выполненный промах, а не провал условий; стоимость и cooldown применяются полностью. Один приём разрешается ровно один раз, поздний callback отменённого действия не наносит урон.

- Обычные отмена и переключение действия используют существующий жизненный цикл; запрета добровольной отмены топора нет.
- Принятая команда движения, включая WASD, отменяет выполняемый приём без урона, расхода stamina за действие и нового cooldown. Обычные расходы на само движение сохраняются.
- Потеря требуемой экипировки или других условий отменяет незавершённый приём по стандартным правилам.
- Обычное попадание по атакующему само по себе не отменяет выполнение, пока условия действия сохраняются.
- Stun, KO и смерть прекращают незавершённое действие. Оно не возобновляется автоматически; ранее запущенные cooldown остаются под собственными сроками.

После выполнения или отмены занятость снимается сразу. Следующее действие можно начать по обычным проверкам его cooldown, ресурсов и состояния персонажа; одновременное выполнение нескольких действий не вводится. После KO для нового действия также требуется добровольно встать по разделу 13.3. Уже нанесённый урон не отменяется, уже выпущенная стрела продолжает существовать по своим правилам.

Смена экипировки подчиняется общим правилам инвентаря и актуальности требований действий. Для лука сначала требуется завершить или отменить натяжение; после выпуска дополнительного запрета смены экипировки нет. Смена оружия не сбрасывает cooldown уже выполненных приёмов.

Клиентский прогрессбар отображает серверные elapsed/total ticks. Достижение 100% на клиенте не является командой нанести урон; разрешение приёма принадлежит серверу. Буфер следующих боевых команд не вводится: отмена, переключение и новые запросы следуют стандартной механике действий.

## 6. Длительность действий и cooldown

### 6.1. Независимые cooldown и последовательное выполнение

**Утверждено:** у каждого действия собственный cooldown, в том числе у обоих ударов топора.

Формулировка пользователя была широкой: «у каждого действия вводим cooldown». Общее требование сохраняется; моменты старта и значения для ремесла, сбора и остальных небоевых действий отложены за пределы текущей боевой фазы.

Для боя:

- Cooldown ограничивает повторное применение конкретного действия.
- `execution.ticks` задаёт длительность выполнения действия с обычным прогрессбаром.
- После завершения текущего действия другое доступное действие можно начать сразу.
- Новый запрос проходит собственные проверки cooldown, ресурсов и состояния исполнителя.
- Удар по площади и одиночный удар можно чередовать, в том числе против одной цели.

Отмена или провал условий незавершённого топора не запускает cooldown. Для лука отмена без выпуска также не запускает cooldown выстрела. Ранее начатые cooldown продолжают отсчитываться при отмене других действий, stun и KO.

Пример v0: первый приём топора начинается в `t = 0`, выполняется в `t = 0.6` и запускает собственный cooldown до `t = 2.6`. Второй готовый приём можно начать сразу в `t = 0.6`; он выполнится в `t = 1.2` и будет на cooldown до `t = 3.2`. Первый можно снова начать в `t = 2.6`. Это последовательные действия с независимыми сроками.

### 6.2. Топор

- Cooldown начинается при выполнении на 100% серверного прогресса, одновременно с оплатой действия.
- Выполненный промах запускает тот же cooldown, что попадание.
- Отклонённый старт, добровольная отмена, движение, потеря условий, stun или KO до выполнения не запускают новый cooldown.
- Уже запущенный cooldown выполненного приёма не сбрасывается отменой других действий или сменой оружия.

### 6.3. Лук

- Cooldown начинается при фактическом выпуске стрелы.
- Частичное и полное натяжение запускают одинаковый cooldown выбранного выстрела.
- Следующее натяжение можно начинать только после его окончания.
- Отменённое натяжение без выпуска стрелы не запускает cooldown выстрела.

Это сохраняет обязательный интервал после каждого выпуска и исключает предварительное накопление следующего выстрела во время cooldown.

Одинаковый cooldown не гарантирует, что короткое натяжение всегда хуже по урону в секунду. В принятой модели начальный урон растёт как `sqrt(charge)`, а время натяжения — линейно; на близкой дистанции частичные выстрелы могут оказаться выгодными. Это вопрос последующих игровых проб; минимальный charge 0.10 уже выбран, дополнительные скрытые штрафы не вводятся.

### 6.4. Скорость действий и управляемое завершение лука

**Утверждено:** в первой фазе длительность выполнения топора, время полного натяжения лука и cooldown задаются definitions, без ускорения от STR/AGI или бафов. Изменение скорости действий эффектами отложено. Длительность выполнения определяется `execution.ticks` и фактическим серверным tick duration.

Для лука стандартный прогрессбар показывает степень натяжения. При 100% персонаж продолжает удерживать полностью натянутый лук и расходовать stamina до отпускания кнопки. Завершение прогресса не вызывает автоматического выпуска. При отпускании сервер проверяет условия выпуска, затем создаёт снаряд, списывает зарезервированную стрелу и запускает cooldown; урон наносится при столкновении снаряда.

После выпуска занятость снимается сразу: обычное движение, смена экипировки и другое доступное действие не требуют дополнительного ожидания. Следующее натяжение того же выстрела нельзя начинать до конца его cooldown. В v0 cooldown обоих приёмов топора равен 2 секундам от выполнения, cooldown лука — 1 секунде от выпуска. Сохранение таймеров определено в разделе 13.7.

## 7. Лук: натяжение, управление и сила выстрела

### 7.1. Утверждённая основа

- Стрела — полноценный отдельный снаряд с маленьким collider.
- Полёт прямолинейный, по заданному вектору, с постоянной фактической скоростью.
- Дальность определяется достигнутой силой натяжения.
- Максимальное натяжение зависит от STR.
- Время полного натяжения задаётся типом лука и не меняется вместе с STR.
- Во время натяжения и удержания готовой стрелы персонаж **стоит на месте**.
- Команда движения отменяет натяжение и позволяет сразу уйти.

«Сразу уйти» означает отсутствие дополнительной задержки от отменённого лука. Обычные ограничения stamina, KO, оглушения и столкновений продолжают действовать.

### 7.2. Принятая модель натяжения и урона

**Утверждено для первого балансного прогона:**

```text
charge = clamp(heldTime / DrawTimeForBowType, 0, 1)
Fmax = min(BowCapacity, F0 × sqrt(EffectiveSTR / S0))
F = Fmax × charge
R = RangeCoefficient × F
Bshot = BaseBowDamage + BaseArrowDamage
Qshot = sqrt(Qbow × Qarrow)
Dlaunch = Bshot × (Qshot / Q0)^0.25 × sqrt(F / F0)
```

- `BowCapacity` — предел конкретного лука. Более мощные луки имеют больший предел; общего cap развития персонажа нет.
- Натяжение растёт линейно со временем до 1. Время полного натяжения задаёт тип лука, оно не растёт вместе с STR.
- Для стандартного прогрессбара время полного натяжения выражается через `execution.ticks` выбранного действия лука: `DrawTimeForBowType = execution.ticks × tickDurationSeconds`. После достижения этого времени прогресс остаётся на 100% до выпуска или отмены, удержание продолжается.
- Дальность пропорциональна достигнутой силе, начальный урон — квадратному корню её нормированного значения.
- Типы лука и стрелы дают базовые вклады в `Bshot`; Quality обоих предметов входит через геометрическое среднее `Qshot`.
- Множитель только `Qbow` заменён множителем `Qshot`; Quality не начисляется второй раз отдельно. STR также не добавляется повторным множителем поверх силы натяжения.
- Для одного стартового лука v0: `BaseBowDamage = 6`, `BaseArrowDamage = 2`, `BowCapacity = 2`, `F0 = 1`, `RangeCoefficient = 120`, полное натяжение за 1.2 секунды. Полная таблица типов луков пока не нужна.

Частичное натяжение уменьшает дальность и начальный урон. Фактическая скорость стрелы остаётся постоянной.

### 7.3. Управление, минимальное натяжение и боеприпас

**Утверждено:**

- Удержание кнопки натягивает лук, затем удерживает его натянутым. До выпуска разрешено свободно менять aim, оставаясь на месте.
- Отпускание кнопки выпускает стрелу при достаточном натяжении после повторной серверной проверки условий: исполнитель может действовать, требуемый лук экипирован, резерв стрелы действителен, charge достаточен и cooldown готов. Достижение максимума не вызывает автоспуск и не увеличивает силу дальше.
- Начальное балансируемое значение `MinBowCharge = 0.10`. Отпускание раньше 10% отменяет действие без стрелы и cooldown; stamina не возвращается. При `F = 0` выстрела нет.
- Движение, stun, KO или исчерпание stamina отменяют натяжение без автоматического выстрела и без возврата stamina. После отмены требуется новая команда начала.
- Боеприпас берётся из личного инвентаря стрелка. Подходящий доступный стек выбирается в фиксированном стабильном порядке слотов; предметы на земле и в сторонних контейнерах не используются. Конкретный порядок адресов слотов закрепляется в реализации, без зависимости от обхода map.
- До оплаты и принятия начала натяжения проверяется наличие доступной стрелы. **Нет стрелы — нельзя начать натяжение**: не списывается stamina, не запускается cooldown и не обновляется LastCombatEventAt.
- При принятом начале натяжения резервируется одна стрела из выбранного стека. При выпуске списывается именно зарезервированная единица; при отмене резерв снимается без потери предмета. Резерв исключает её повторное расходование или перемещение, которое сделало бы оплату выстрела невозможной.
- Подбор уже выпущенных стрел отложен.
- Уже выпущенная стрела продолжает полёт после оглушения, KO или смерти стрелка.

Оплата — начальная стоимость и постоянный расход за время натяжения/удержания, без доплаты при выпуске, по разделу 10.2. Резервирование и списание предмета стрелы — отдельный контракт от невозврата stamina. Конкретные сообщения ввода и структура резерва будут определены при проектировании реализации.

### 7.4. Фиксация параметров при выпуске

Для снаряда сохраняются достигнутая сила, направление, начальный урон и предельная дальность этого выстрела. Последующее движение/поворот стрелка не перенаправляет выпущенную стрелу.

Принятая кинематика:

```text
position(t) = launchPosition + unitDirection × ProjectileSpeed × t
travelLimit = R
lifetime    = R / ProjectileSpeed
```

Управление гравитационной дугой, наведением или фактическим торможением не входит в выбранную модель прямого полёта.

## 8. Столкновения стрелы и попадания

**Утверждено:**

- У объектов есть отдельный признак/фильтр projectile collision: проходимость для персонажа не определяет проходимость для стрелы.
- В v0 объекты с collider по умолчанию блокируют стрелы; отдельный фильтр projectile collision задаёт исключения. Блокируют персонажи, животные/монстры, стены, закрытые двери, стволы, **контейнеры и мебель**. Отсутствие категории в перечислении само по себе не делает её пропускающей.
- **Булыжники (`boulder`) пропускают стрелы** по явному уточнению пользователя. Трава и мелкий декор также пропускают; трупы не являются препятствиями.
- Проверяется весь отрезок перемещения стрелы за серверный шаг с учётом её маленького collider и относительного движения цели за этот шаг.
- Среди блокирующих пересечений выбирается первый контакт. Объект получает урон по своей модели здоровья и останавливает стрелу; уничтожение объекта этим попаданием не даёт стреле пробивание.
- Цель получает урон один раз; дальнейшего пробивания или скольжения стрелы нет.
- Проверяется отрезок до точки появления стрелы, чтобы нельзя было выпустить её сквозь близкую стену. **Если на нём находится преграда, выстрел считается состоявшимся:** боеприпас списан, cooldown запущен, действие стрелка завершено; ближайшая преграда получает попадание и стрела прекращает существование. Нельзя бесплатно отменить выпуск из-за близкой стены или создать снаряд за ней. Для этого контакта также действуют предельная дальность и спад урона по пройденному расстоянию.
- Collider стрелка игнорируется только до выхода стрелы из него. Затем действуют обычные правила коллизии; постоянного иммунитета владельца нет.
- Контакт ровно на предельной дальности `R` засчитывается перед удалением снаряда.

При стандартных 10 Hz быстрая стрела может пересечь небольшую цель между двумя серверными состояниями. Поэтому нужны проверка всего пути и учёт перемещения цели внутри того же шага.

Для первой реализации используется серверное состояние **без отката мира по клиентскому времени**. Сервер определяет попадание и урон.

Для v0 выбраны collider 1 × 1 мировая единица и скорость 240 единиц/с. Точное смещение точки появления, формат collision mask и геометрические допуски оформляются при реализации. Право объекта получать урон не означает контакт с любой стрелой: boulder и другие пропускающие объекты не получают урон от пролетающей через них стрелы, но доступны другим попаданиям, в том числе топором.

## 9. Потеря урона стрелы с расстоянием

### 9.1. Почему спад отдельно от скорости

Пользователь хочет передать потерю силы стрелы с дистанцией, хотя фактическая игровая скорость остаётся постоянной. Поэтому уменьшается расчётный урон, а не скорость перемещения collider.

Связь реальной кинетической энергии со скоростью служит мотивацией. Выбранная игровая кривая не заявляется точной физической моделью сопротивления воздуха.

### 9.2. Утверждённые константы

```text
BowDamageFalloffStartFraction = 0.30
BowDamageAtMaxRangeMultiplier = 0.20
```

Имена сохранены как понятные обозначения будущих констант, не как уже существующие поля кода.

Пользователь прямо попросил вынести оба значения в константы для дальнейшей балансировки.

### 9.3. Формула

`s` — пройденное стрелой расстояние до контакта. `R` — максимальная дальность **данного выстрела**, уже рассчитанная из натяжения.

```text
u = s / R
a = BowDamageFalloffStartFraction
b = BowDamageAtMaxRangeMultiplier

p = clamp((u - a) / (1 - a), 0, 1)
distanceMultiplier = 1 - (1 - b) × p
Draw = Dlaunch × distanceMultiplier
```

При выбранных значениях:

```text
0 <= s <= 0.30R: multiplier = 1
0.30R < s <= R:  multiplier = 1 - 0.80 × (s/R - 0.30) / 0.70
s > R:           полёт завершён, попаданий дальше нет
```

Константы при будущей настройке должны оставлять определённую кривую: `0 <= a < 1`, `0 <= b <= 1`; вычисление требует `R > 0`.

| Пройденная доля дальности | Множитель исходного урона |
|---:|---:|
| 0–30% | 100% |
| 50% | 77.14% |
| 65% | 60% |
| 80% | 42.86% |
| 100% | 20% |

### 9.4. Последствия для брони и коротких выстрелов

Спад применяется **перед бронёй**. Поэтому 20% исходного урона на предельной дистанции не означают 20% ближнего урона по бронированной цели.

Иллюстрация: при `Dlaunch = 100`, `A = 100` ближний урон равен 50. На максимальной дальности `Draw = 20`, и после той же брони проходит примерно 3.33. Броня сильнее подавляет ослабевшую стрелу.

У частично натянутого выстрела меньше собственный `R`, поэтому короче и участок полного урона `0.30R`. Не подменять его дальностью полного натяжения или общим радиусом всех луков.

### 9.5. Почему отказались от L50

L50 обсуждалась как отдельная длина, за которую урон падает вдвое, например в кривой вида `2^(-s/L50)`. Это удобный параметр экспоненциального затухания, но он создаёт ещё одну дистанцию помимо дальности самого выстрела.

Пользователь выбрал более явную схему «полный урон до 30%, затем линейно до 20%». **L50 в принятой модели нет.** Не возвращать экспоненциальный спад или реальное замедление снаряда при реализации.

## 10. Stamina и движение

### 10.1. Принятое правило расхода

**Утверждено:** боевые действия могут расходовать stamina до нуля. Обязательного остатка 5%, 10% или другого резерва не вводим.

Это не разрешает отрицательную stamina или бесплатный старт действия с недостающим ресурсом.

### 10.2. Оплата топора и лука

**Утверждено для обоих приёмов топора:** вся стоимость stamina списывается один раз при выполнении на 100% серверного прогресса, в тот же момент начинается cooldown. До завершения ресурс проверяется, но не списывается и не резервируется отдельно от обычных действий.

- Если ресурса на старт недостаточно, действие не начинается.
- Если ресурса ровно хватает, действие может начаться; при сохранении этого запаса до выполнения оплата оставляет ноль.
- Если до выполнения stamina стала меньше стоимости, обычная проверка условий отменяет приём без урона, оплаты и нового cooldown.

Отклонённый старт, добровольная отмена, движение, потеря условий, stun и KO до выполнения не списывают стоимость и не запускают новый cooldown. Выполненный промах оплачивается полностью; наличие попадания не является условием оплаты завершённого приёма.

После выполнения затраты и cooldown сохраняются: последующие stun, KO или смена экипировки не отменяют уже состоявшийся результат. В пресете v0 оба приёма стоят по 60 stamina; это абсолютная стоимость, а не процент максимального запаса.

**Утверждено для лука:**

- Начальная стоимость списывается при принятом начале натяжения.
- Во время натяжения и последующего удержания действует постоянный расход stamina за время. Достижение полного натяжения не прекращает этот расход.
- Выпуск стрелы не требует дополнительной оплаты stamina.

Начальную стоимость нужно иметь к началу действия: её нехватка не позволяет начать натяжение. Для неизменных параметров лука начисленная стоимость описывается так:

```text
BowCost(t) = InitialCost + DrainPerSecond × t
```

Здесь `t` — общее время натяжения и удержания в секундах до выпуска или отмены. Это обозначения для обсуждения, а не выбранные имена полей definitions. Формула описывает расход, не меняя отдельно существующую регенерацию stamina. Начальная стоимость взимается один раз за начатое натяжение; переход к удержанию и выпуск не вызывают повторного начального списания.

**Утверждено:** при исчерпании stamina во время натяжения или удержания персонаж опускает лук. Текущее натяжение/удержание отменяется, автоматического выстрела нет. Это действует и при частичном, и при полном натяжении. Поскольку стрела не выпущена, cooldown выстрела не запускается; ранее запущенные cooldown остаются под общими правилами.

**Утверждено:** при отмене натяжения или удержания уже потраченная stamina не возвращается. Не возвращаются ни начальная стоимость, ни расход за прошедшее время; частичного возврата также нет. Правило действует при отмене движением, станом, KO или исчерпанием stamina. После отмены дальнейший расход за натяжение/удержание прекращается.

**Утверждено:** постоянный расход считается по прошедшему времени на каждом серверном шаге с сохранением дробной части, без округлённых порций раз в секунду. Для v0 `BowStartCost = 20`, `BowDrainPerSecond = 20`; полное натяжение за 1.2 секунды без удержания стоит 44 stamina. Моменты оплаты и общий принцип «разрешить до нуля» сохраняются.

### 10.3. Связь с существующим передвижением

Существующие множители:

| Режим | Скорость относительно Walk |
|---|---:|
| Crawl | 0.5 |
| Walk | 1 |
| Run | 1.5 |
| FastRun | 2 |

При текущей базовой скорости игрока 32 Crawl соответствует 16 игровым единицам в секунду. Эти значения — контекст существующего движения, не новый баланс боевых дистанций.

Текущие ограничения по доле максимальной stamina:

- Ниже 50% недоступен FastRun.
- Ниже 25% недоступны Run и FastRun.
- Ниже 10% остаётся Crawl.
- Ниже 5% движение недоступно.

Разрешение потратить stamina до нуля не отменяет эти пороги. Поэтому отмена лука командой движения может убрать натяжение, но не дать фактически уйти при полностью исчерпанной stamina.

Crawl сейчас не расходует stamina на движение. Само боевое действие при этом может иметь свою стоимость.

### 10.4. Начальные стоимости и дальнейшая настройка

Для первой редакции приняты простые абсолютные стоимости из раздела 17.1: по 60 за удар топора, 20 за начало натяжения и 20/с с луком. Увеличение CON даёт больше действий через рост запаса; расходы не масштабируются процентом этого запаса. При stamina = 1000 без движения и регенерации хватает на 16 ударов либо 22 полных выстрела.

**Утверждено:** сохраняются существующие правила SHP- и stamina-регенерации, без отдельного боевого режима. Расход лука обновляет задержку восстановления stamina по существующему правилу. HHP самостоятельно не восстанавливается. Точная экономика длительного боя и отхода настраивается после реализации, не блокируя v0.

## 11. Friendly fire, союзники и допустимые цели

Пользователь прямо определил игру как хардкорную non-target систему без исключений для союзников.

- Союзник в секторе AoE получает урон.
- Союзник может стать ближайшей целью одиночного удара.
- Союзник на траектории стрелы принимает попадание на общих основаниях.
- Party, clan, friendship и аналогичные социальные признаки не фильтруют попадания и не уменьшают урон.
- Исключение собственного ID для обоих ударов топора — отдельное правило механики самопопадания; оно не распространяется на союзников.

### 11.1. Формальное определение цели

**Утверждено:** боевой урон распространяется на все объекты мира, а не только на игроков, животных и монстров. Постройки, деревья, boulder, контейнеры и прочие неживые объекты не исключаются по категории. Здесь объект мира — самостоятельная сущность, участвующая в пространственных попаданиях; отдельная механика повреждения тайлов ландшафта этим не вводится.

Общий предикат возможности получить урон:

```text
CanReceiveDamage(target) =
	target существует в мире и ещё не уничтожен
	AND (
		у target модель здоровья SHP/HHP и HHP > 0
		OR у target модель здоровья объекта и HP > 0
	)

ValidAxeTarget(attacker, target, sector) =
	target.id != attacker.id
	AND CanReceiveDamage(target)
	AND collider(target) пересекает sector
```

Эти условия проверяются в момент удара. Отсутствие заполненного HP у старого объекта — незавершённая интеграция, которую нужно исправить, а не основание для постоянного иммунитета категории. Для всех повреждаемых объектов требуется запас здоровья и геометрия контакта.

- Живые существа в KO и добровольно лежащие после истечения его таймера остаются целями.
- Умершая сущность с HHP = 0 не получает повторные боевые попадания как живой персонаж. Созданный вместо неё объект трупа относится к общему правилу объектов: имеет собственный HP и может быть разрушен. Запрет на повреждение трупов из ранней редакции отменён вместе с ограничением целей только живыми существами.
- Топор исключает собственный ID до расчёта пересечений и расстояний. При отсутствии других целей происходит обычный оплаченный промах; собственный collider не становится запасной целью.
- AoE наносит урон каждой цели из этого набора по одному разу. Одиночный приём выбирает из него одну цель по метрике раздела 5.3, без приоритета персонажей над объектами.
- Стена внутри сектора сама получает урон. Для AoE она не закрывает цели за собой; одиночный приём может выбрать её как ближайшую цель.

### 11.2. Допустимость урона и столкновение стрелы

`CanReceiveDamage` и блокирование стрелы — разные проверки. Стрела поражает первую блокирующую её сущность по разделу 8. У неё нет отдельного запрета на урон постройкам: стена, дверь или ствол получают урон и останавливают снаряд, даже если этот урон их уничтожает.

Boulder и трупы по-прежнему пропускают стрелы: такое пролетание не является попаданием и не наносит им урон. Они могут быть повреждены топором. Collider стрелка игнорируется только до выхода стрелы из него, как уже установлено в разделе 8; постоянное исключение владельца для стрелы не добавляется.

### 11.3. Здоровье и применимость дополнительных эффектов

После геометрического контакта рассчитывается общий урон D после брони, затем применяется соответствующая модель здоровья. У существ действуют SHP/HHP и правила KO/смерти из разделов 12–13. У остальных объектов D уменьшает HP, а при HP = 0 объект уничтожается (раздел 12.7).

Право получать прямой урон не требует искусственно добавлять объекту STR, SHP или KO. Начальная рана со штрафом STR и состояние stunned предназначены для существ с соответствующими характеристиками и состояниями; общий урон объекту применяется независимо от применимости такого дополнительного эффекта. **Применимость дебафа проверяется до броска chance.** Для обычного объекта без STR начальная рана неприменима: она пропускается без случайного броска и без создания статуса, прямой урон сохраняется. Технический контракт системы эффектов должен выразить совместимость воздействий с компонентами цели.

## 12. SHP, HHP, нокаут и смерть

### 12.1. Значение шкал

- `SHP` — текущее мягкое здоровье; его исчерпание приводит к KO, если персонаж жив.
- `HHP` — оставшееся твёрдое здоровье; его исчерпание означает смерть.
- `MHP` — текущий максимум здоровья.
- Сохраняется инвариант `0 <= SHP <= HHP <= MHP`.

Существующая формула проекта сохраняется как опора для баланса. **Утверждено:** после подключения модификаторов она использует эффективный CON:

```text
MHP = 25 × sqrt(EffectiveCON) × lifeDeathFactor
```

`lifeDeathFactor` — общий множитель максимального здоровья из серверного конфига `game.life_death_factor` (либо `GAME_LIFE_DEATH_FACTOR`). Текущий допустимый диапазон — 0.8–1.2, значение по умолчанию и в пресете v0 — 1.0. Это не характеристика персонажа и не временный эффект.

**Утверждённое ограничение:** значение неизменно на протяжении жизни существующего мира. Его нельзя менять ни на горячую, ни между обычными перезапусками; смена допускается только после полного пересоздания мира (wipe). Это осознанное эксплуатационное ограничение, а не новая механика миграции здоровья. Автоматического пересчёта с компенсацией HHP при смене конфига не вводим.

Причина: снижение множителя уменьшает MHP, после чего обрезка может необратимо уменьшить сохранённый HHP выше нового максимума, в том числе при следующем входе персонажа. Рост множителя не восстановит обрезанное здоровье. Правило динамического пересчёта по модификаторам CON из раздела 14.13 действует при неизменном множителе мира. Ограничение отражается в комментариях к конфигурации и формуле; эти комментарии сами по себе не являются программной защитой от ошибочной смены настройки.

При факторе 1 и эффективном CON 1 это 25 MHP. **Утверждено:** при изменении MHP сохраняются абсолютные HHP/SHP с обрезкой по новым пределам: сначала HHP ограничивается новым MHP, затем SHP — полученным HHP. Увеличение MHP само по себе не восстанавливает здоровье. Формулы и примеры приведены в разделе 14.13.

### 12.2. Обычное попадание по персонажу в сознании

**Утверждено:** весь рассчитанный после брони урон уменьшает SHP, а его доля повреждает HHP уже с каждого обычного попадания.

При достаточном остатке SHP:

```text
SHP damage = D
HHP damage = alpha × D
```

**Утверждено:** `alpha = 0.20` (20%) как начальное настраиваемое балансное значение. Его следует хранить отдельно от логики расчёта. Это доля урона после брони, а не доля максимального здоровья цели. Превышение остатка SHP и урон по уже нокаутированному продолжают обрабатываться по отдельным правилам ниже.

### 12.3. Превышение остатка SHP

**Утверждено:** часть попадания сверх оставшихся SHP полностью переносится в HHP.

Для персонажа, находившегося в сознании до попадания:

```text
softPart = min(D, SHPbefore)
overflow = D - softPart
hardDamage = alpha × softPart + overflow

SHPafter = max(0, SHPbefore - D)
HHPafter = max(0, HHPbefore - hardDamage)
SHPafter = min(SHPafter, HHPafter)
```

Эквивалентная запись:

```text
hardDamage = alpha × D + (1 - alpha) × max(0, D - SHPbefore)
```

Не использовать `alpha × D + overflow`: это повторно начисляет долю HHP на ту же часть превышения.

### 12.4. Урон по уже нокаутированному

**Утверждено:** весь `D` повреждает HHP. Броня применяется до этого распределения как обычно.

**Утверждено:** KO определяется отдельным состоянием/таймером. Внутри KO продолжается обычная SHP-регенерация с существующими условиями Energy. Пока действует KO, рост SHP не сокращает таймер и весь D по-прежнему идёт в HHP. Через 60 секунд KO завершается независимо от положения тела: у добровольно оставшегося лежать персонажа последующие попадания распределяются по обычным правилам SHP/HHP из раздела 12.3. Признак «лежит» сам по себе не включает полный HHP-урон.

### 12.5. Пример распределения

Примеры используют выбранное значение `alpha = 0.20`; исходные количества здоровья и величины попаданий — иллюстративные.

| До попадания | D после брони | Урон HHP | Результат |
|---|---:|---:|---|
| SHP 40, HHP 60, в сознании | 10 | 2 | SHP 30, HHP 58 |
| SHP 10, HHP 50, в сознании | 30 | 2 + 20 = 22 | SHP 0, HHP 28, KO |
| SHP 0, HHP 28, уже KO | 12 | 12 | HHP 16, KO продолжается |
| SHP 10, HHP 20, в сознании | 30 | 22 | HHP 0, смерть |

Обрабатывать смерть раньше обычного перехода в KO. Не предоставлять обязательный промежуточный нокаут персонажу, который уже получил смертельный HHP-урон.

### 12.6. Повреждение здоровья, раны и граница лечения

**Утверждено:** удар непосредственно уменьшает SHP и HHP, а также может с некоторой вероятностью наложить рану-дебаф с собственными эффектами. Неудачное наложение раны не отменяет уже рассчитанный урон здоровью. Подробности общей системы бафов/дебафов приведены в разделе 14.

Следовательно, HHP в Origin не вычисляется просто как MHP минус сумма активных ран. Потеря HHP возможна и при отсутствии дебафа-раны. Само наложение раны не должно повторно списывать основной урон попадания; дополнительные последствия определяются её эффектами.

**Утверждено:** HHP восстанавливается только лечением. Лечение будет взаимодействовать с дебафами, но пользователь явно исключил его механику из scope текущего обсуждения. Не выбирать сейчас лекарства, скорость восстановления, условия применения или связь снятия дебафа с возвратом ранее потерянного HHP. Эта граница не отменяет уже выбранное отсутствие самостоятельной HHP-регенерации.

Отдельное повреждение за сам факт нокаута и случайное сотрясение как в H&H не приняты. Для начального теста выбрана одна бессрочная рана со штрафом STR -10% и `chance = 0.15` на попадание каждым из двух ударов топора. Кровотечение в текущей фазе не требуется. Рана не меняет уже выбранную формулу прямого урона.

### 12.7. HP объектов и уничтожение

**Утверждено:** у неживых объектов мира есть собственный запас HP. После расчёта урона D по общим правилам:

```text
HPafter = max(0, HPbefore - D)
if HPafter == 0: уничтожить объект
```

Объект не проходит через SHP, HHP, нокаут или смерть персонажа. Разделения урона по alpha нет: весь D списывается из HP. В v0 у всех таких объектов A = 0; дробный урон и остаток HP сохраняются в расчётах, как и у существ.

Достижение нуля запускает уничтожение ровно один раз и исключает объект из дальнейших попаданий. Удаление из мира, коллизий и сохранения должно использовать согласованный жизненный цикл объекта. Содержимое контейнеров, выдача ресурсов и прочие последствия уничтожения требуют привязки к существующим правилам объектов; из формулы HP они автоматически не следуют.

## 13. Нокаут: 60 секунд и будущий Hearth Fire

### 13.1. Вход в состояние

Нокаут наступает при исчерпании SHP, если HHP остаётся положительным. Персонаж теряет возможность действовать; выполняемый приём топора или натяжение лука прерывается.

Отсчёт идёт от момента входа в KO.

### 13.2. Временная схема

| Время с начала KO | Правило Origin |
|---|---|
| 0 секунд | Персонаж падает, действия прекращаются, начинается независимый таймер |
| 0–30 секунд | Лежит; может получать урон и погибнуть |
| 30 секунд | Становится доступен будущий возврат к Hearth Fire |
| 60 секунд | KO заканчивается, живой персонаж приходит в сознание и получает возможность добровольно подняться; может продолжить лежать, изображая нокаут |
| После 60 секунд до добровольного подъёма | KO не действует, урон распределяется по обычным правилам SHP/HHP; персонаж продолжает лежать и не может действовать, кроме добровольного подъёма |

**Утверждено:** `KnockoutDuration = 60 seconds` и `HearthReturnAvailableAfterKO = 30 seconds`. Это обозначения правил, а не уже существующие имена настроек.

### 13.3. Окончание KO и добровольный подъём

**Утверждено:** истечение 60 секунд завершает обязательный KO, но не заставляет персонажа физически вставать. Игрок может продолжать лежать, изображая нокаут, и подняться позднее по своему выбору.

**Утверждённое поведение добровольно лежащего:** до подъёма персонаж не может выполнять игровые действия. Запрещены любое перемещение, включая Crawl, выполнение приёмов топора, натяжение/удержание лука, взаимодействия с объектами, использование предметов, изменение инвентаря/экипировки и другие действия персонажа. Единственное исключение — добровольный подъём после окончания KO, если ему не препятствует stun или другое блокирующее состояние. Команда движения или атаки не заменяет команду подъёма: она отклоняется, не ставится в очередь и сама персонажа не поднимает.

Для v0 положение лёжа не меняет collider: сохраняются его размеры, смещение относительно персонажа и фильтры столкновений, используемые при стоянии. Это относится и к активному KO, и к изображению нокаута после его окончания. Персонаж остаётся неподвижной целью для сектора и стрел; визуальная анимация лежания не уменьшает область попадания.

Запрет действий не останавливает пассивные процессы: продолжаются регенерация по обычным условиям, сроки статусов и cooldown, обработка входящего урона и эффектов. Сам факт лежания не продлевает KO и не меняет выбранное распределение урона после 60 секунд.

Для реализации нужно различать два независимых факта:

- **Активный KO:** действует обязательное ограничение до `KOUntil`; весь входящий D идёт в HHP.
- **Положение лёжа после KO:** персонаж уже в сознании, таймер не продлевается; обычное распределение урона по SHP/HHP действует даже до подъёма, но сама поза блокирует движение и все действия, кроме разрешённого подъёма.

В момент окончания KO живому персонажу обеспечивается минимум 1 SHP в пределах HHP:

```text
if HHP > 0 and KO истёк:
	SHP = min(HHP, max(SHP, 1))
	завершить активный KO
	сохранить положение лёжа до добровольного подъёма
```

- Обычная регенерация SHP не завершает активный KO раньше 60 секунд.
- HHP при окончании KO не восстанавливается; низкая Energy не делает обязательный KO бессрочным.
- Минимальный SHP обеспечивается один раз при завершении KO. Позднейшая команда подъёма не выдаёт здоровье повторно.
- При HHP = 0 наступает смерть; ни окончание KO, ни подъём не выполняются.
- После 60 секунд попадание по всё ещё лежащему обрабатывается по формуле раздела 12.3. Если оно снова исчерпывает SHP, начинается новый обязательный KO; если исчерпывает HHP — смерть.
- Сохраняющийся stun остаётся отдельным ограничением и не снимается окончанием KO. Добровольный подъём не обходит активный stun или новый KO.

Конкретная команда/кнопка подъёма оформляется при проектировании ввода. Автоматического подъёма только из-за истечения таймера нет. Визуальная поза не должна подменять серверную проверку активного KO.

### 13.4. Уязвимость и Hearth Fire

Нокаут не даёт иммунитета к урону. Ожидание 30 секунд до Hearth Fire не гарантирует выживание. В активном KO весь D идёт в HHP; после его окончания оставшийся лежать получает обычный SHP/HHP-урон и также может погибнуть.

Пользователь отметил Hearth Fire как **будущую механику**. Сейчас зафиксирована только доступность возврата после 30 секунд. Ещё не выбраны:

- Ручной запуск или автоматический выбор по умолчанию.
- Длительность самого переноса и возможность его прервать.
- Условия доступности Hearth Fire, ограничения локаций, отсутствие/уничтожение точки.
- Состояние персонажа после переноса и судьба оставшейся части KO-таймера.

Правила выхода из игры при KO уже выбраны отдельно в разделе 13.6 и не являются частью ещё не спроектированного переноса к Hearth Fire.

Не переносить из H&H автоматически меню из трёх опций, автоматический hearth, logout или ограничения Murderous Rage.

### 13.5. Повторный KO и временные границы

**Утверждено:** попадания по уже нокаутированному не продлевают текущие 60 секунд. После окончания KO новое исчерпание SHP запускает новый полный срок 60 секунд, даже если персонаж ещё не вставал. Защитного иммунитета после окончания KO или подъёма нет.

События обрабатываются по серверному времени. При точном совпадении попадания и окончания KO сначала применяется полный HHP-урон по цели с ещё активным KO, затем обрабатывается его окончание. Для последующих попаданий уже действует обычная формула SHP/HHP, независимо от лежачей позы. Смерть имеет приоритет.

**Утверждено для нескольких попаданий в одном тике:** обработка последовательная, сначала по времени события, затем по стабильному серверному порядковому номеру. Порядковый номер задаётся упорядоченной серверной очередью, а не случайным порядком обхода map/объектов. Следующее попадание видит уже изменённые здоровье, KO, stun и другие эффекты предыдущего; общего одновременного расчёта по снимку здоровья до всех ударов нет. Геометрия попадания по-прежнему проверяется по правилам соответствующей атаки.

Если несколько попаданий точно совпадают с KO-дедлайном, эти попадания обрабатываются в выбранном порядке до события окончания KO. Смерть исключает дальнейшую обработку как живой цели; начало нового KO или stun может отменить незавершённый приём топора по обычным правилам. Уже выпущенная стрела от этого не исчезает.

### 13.6. Выход или потеря соединения в бою

**Утверждено:** выход или потеря соединения не удаляют тело немедленно. В бою оно остаётся до окончания KO и минимум 30 секунд после последнего боевого действия или полученного удара, по более позднему сроку:

```text
EarliestCombatDespawnAt = max(KOUntil, LastCombatEventAt + 30 seconds)
```

Здесь `KOUntil` участвует, если активный KO ещё не закончился. Добровольное лежание после 60 секунд само по себе не продлевает задержку выхода. Число 30 секунд — начальное балансируемое значение задержки выхода, отдельное от будущего Hearth Fire.

**Определение `LastCombatEventAt`:** серверное время последнего принятого боевого события для участника. Срок обновляется только следующими событиями:

| Событие | У кого обновляется LastCombatEventAt |
|---|---|
| Принятое начало выполнения топора или натяжения лука, после всех проверок старта | У атакующего |
| Фактический удар топором, включая промах | У атакующего |
| Фактический выпуск стрелы | У атакующего |
| Состоявшееся боевое попадание по существу, включая союзника и живую цель в KO | У атакующего и получателя |
| Состоявшееся боевое попадание по обычному объекту мира | У атакующего; обычному объекту таймер выхода персонажа не нужен |

Попадание выпущенной стрелы является отдельным событием относительно её выпуска. AoE обновляет срок каждого получателя и атакующего; несколько событий одного времени не прибавляют по 30 секунд, а задают тот же последний момент. При обработке более старого события срок не сдвигается назад: `LastCombatEventAt = max(LastCombatEventAt, eventTime)`.

**Не обновляют срок:** отклонённые команды, прицеливание, движение, регенерация, течение cooldown, обновления прогрессбара, ожидание при натяжении/удержании и сама отмена действия. При отмене топора или лука уже состоявшееся событие принятого старта сохраняется. Голод и другие небоевые источники потери здоровья не считаются боевым попаданием. Истечение дальности стрелы без контакта не добавляет событие после её выпуска. Отсутствие боевых событий не запускает самостоятельную 30-секундную задержку; остальные условия выхода, включая активный KO, сохраняются.

Последовательность проверок важна: попытка начать натяжение без стрелы или без достаточной начальной stamina не становится принятым стартом и не обновляет LastCombatEventAt.

Потеря соединения отменяет незавершённое действие через стандартный жизненный цикл. Топор прекращается без урона, оплаты и нового cooldown. Натяжение или удержание лука отменяется без выстрела и без возврата уже потраченной stamina; резерв невыпущенной стрелы освобождается. Отмена не стирает LastCombatEventAt принятого старта и не удаляет тело раньше определённого выше срока.

Пока тело остаётся в мире, оно подчиняется обычным попаданиям, KO и смерти. Переподключение не сбрасывает таймеры. Эти правила предстоит интегрировать с существующим жизненным циклом сессии; изменения кода пока не выполнены.

### 13.7. Сохранение состояний, перезапуск и смена зоны

**Утверждено:** сохраняются раны, временные статусы, KO, cooldown и LastCombatEventAt. Длительности опираются на абсолютные сроки окончания, которые продолжают идти при переподключении и перезапуске. Перезаход не удаляет бессрочные раны, не начинает заново уже идущие таймеры и не сбрасывает время последнего боевого события.

Переход между обычными зонами не сбрасывает состояния и сроки. При перезапуске сервера незавершённый топор отменяется без урона, оплаты и нового cooldown; ранее выполненные приёмы сохраняют свои cooldown. Незавершённое натяжение лука отменяется без возврата уже потраченной stamina, резерв невыпущенной стрелы освобождается. Прогресс незавершённого действия после загрузки не возобновляется.

**Выпущенные стрелы:** при перезапуске сервера существовавшие снаряды удаляются и не восстанавливаются. Боеприпасы и stamina не возвращаются; уже начатый cooldown выстрела сохраняется. Это отдельное правило от отмены ещё не завершённого натяжения, при которой снимается резерв невыпущенной стрелы.

Обычный переход между зонами не удаляет летящую стрелу. Переход самого стрелка также не влияет на ранее выпущенный снаряд. При пересечении границы снарядом сохраняются его положение, направление, пройденная дистанция, исходные параметры выстрела и оставшаяся дальность; переход не создаёт новый выстрел и не повторяет оплату. Владение снарядом между серверными зонами/системами — техническая задача реализации.

После загрузки учитываются фактически истёкшие сроки; смерть по-прежнему имеет приоритет над окончанием KO. Восстановление должно различать активный KO и положение лёжа после его завершения, не выдавать минимум SHP повторно при каждом входе и не поднимать персонажа автоматически. Формат хранения и восстановления определяется при проектировании реализации. Поведение будущего DoT вне игры отложено вместе с самим DoT.

## 14. Бафы, дебафы, эффекты и оглушение

### 14.1. Приёмы, статусы и их эффекты

**Утверждено:** вводится общая система бафов и дебафов по образцу L2J. Рана представляется дебафом, который накладывает определённые эффекты.

Для дальнейшего проектирования различаем:

- **Приём/действие** — выполняемый боевой приём: например, удар топора. Он определяет попадание, прямой урон и возможные дополнительные последствия.
- **Баф/дебаф** — наложенный на персонажа статус, объединяющий один или несколько эффектов. Рана является одним из видов дебафов, а не отдельным типом урона.
- **Эффект** — конкретное воздействие статуса, например изменение характеристики, периодическое повреждение или запрет действий. Периодическое повреждение — пример будущего расширения; в текущей фазе выбрана рана только со штрафом STR.

Определение статуса и его активный экземпляр на конкретной цели следует различать при проектировании. **Утверждено:** у каждого бафа/дебафа есть свой ID. В уточнении пользователя «эффект (баф или дебаф)» ID относится ко всему такому статусу, включая его составные воздействия. Это не ID приёма и не имя обработчика отдельного воздействия, например изменения STR.

На одной цели по одному ID действует один экземпляр статуса. Новое успешное применение с тем же ID безусловно заменяет его; при разных ID замены нет. ID — положительное целое число. Основной формат definitions определён в разделе 14.16; конкретные значения ID, структуры компонентов и способы хранения предстоит оформить при реализации. Полное правило замены приведено в разделе 14.14.

**Утверждено:** приём может накладывать несколько дебафов, например отдельный stun и отдельную рану. У каждого наложения есть фиксированный `chance` из definitions. Дебаф может объединять несколько эффектов: один успешный бросок накладывает весь дебаф и включает их вместе.

Первая редакция v0 включает два приёма топора (удар по области и усиленный удар по одной цели), лук с натяжением и отдельными стрелами, общую систему бафов/дебафов, начальную рану и поддержку состояния `stunned`. Лук входит в текущую реализацию по пресету раздела 17.1. Оглушение относится к отдельному специальному приёму; обычные удары топора и стрелы не получают автоматического stun. Конкретный оглушающий приём ещё не выбран и остаётся за scope v0.

**Утверждено: кровотечение в текущей фазе не требуется.** Конкретный DoT отложен целиком: его урон по SHP/HHP, смертельность, броня, период, первый тик, замена и поведение вне игры будут отдельным пакетом. Упоминания кровотечения ниже только поясняют будущие возможности составных статусов. Тип урона по-прежнему один.

### 14.2. Независимый фиксированный chance дебафа

**Утверждено:** для каждого применимого дебафа на каждой задетой цели выполняется отдельная проверка его `chance`. Сначала проверяется применимость по разделу 11.3; неприменимый дебаф пропускается без броска. Внутри одного дебафа дополнительных бросков на включение его составных эффектов нет.

- Если stun и рана — разные дебафы, у одной цели может наложиться stun и не наложиться рана; у другой — наоборот.
- Если будущий составной дебаф объединит снижение STR и кровотечение, успешное наложение включит оба воздействия вместе. Это пример архитектуры, а не включение кровотечения в текущую фазу.
- Не используется один общий бросок на весь список дебафов приёма.
- В AoE результат на одной цели не определяет результат на остальных.
- Шанс берётся непосредственно из definitions; STR, CON, уровень, Quality, броня, сопротивления и разница развития не пересчитывают его в выбранной модели.
- Шанс наложения stun и шанс снятия уже действующего stun уроном — разные проверки.

**Утверждён формат:** `chance` — число от **0 до 1 включительно**, например `0.35` означает 35%. Для начальной раны у обоих приёмов топора выбран `chance = 0.15`; шансы будущих специальных приёмов ещё предстоит подобрать. `0` означает никогда, `1` — всегда. Неконечные числа и значения вне диапазона должны отклоняться при загрузке definitions, а не молча нормализоваться. Место хранения и runtime-структуры оформляются при реализации.

Это уточняет раннюю формулировку обсуждения «независимый шанс каждого эффекта»: после введения составных статусов единицей вероятностного наложения выбран **дебаф целиком**, а независимость сохраняется между разными дебафами и разными целями.

### 14.3. Прерывание и отдельное состояние stunned

Пользователь принял разделение обычного попадания и отдельного эффекта оглушения.

| Воздействие | Выполнение топора | Натяжение/удержание лука |
|---|---|---|
| Обычное попадание, персонаж остаётся в сознании | Продолжается | Продолжается |
| Специальный эффект оглушения | Прерывается | Прерывается |
| Нокаут | Прерывается | Прерывается |
| Смерть | Прекращается | Прекращается |
| Принятая команда движения самого игрока | Отменяет выполнение без оплаты и нового cooldown | Отменяет натяжение без возврата потраченной stamina |

Активное оглушение блокирует движение и выполнение действий. Успешное наложение прерывает текущее выполнение топора или натяжение лука; неудачная проверка `chance` сама по себе действие не прерывает. Незавершённый топор отменяется без оплаты и нового cooldown; потраченная stamina лука не возвращается. Ранее запущенные cooldown выполненных приёмов сохраняются и продолжают отсчитываться.

Причина выбора: если каждое попадание сбивает действие, быстрые атаки или группа стрелков могут непрерывно мешать завершить медленную атаку. Выбранная модель позволяет выдержать попадание и ответить, пока персонаж не оглушён и не потерял сознание.

**Stun и KO остаются разными состояниями с независимыми сроками.** Истечение или снятие stun не завершает KO. Восстановление SHP не снимает stun и не будит раньше KO-дедлайна. Если действуют оба ограничения, возможность действовать возвращается только после завершения всех блокирующих состояний. После KO также требуется добровольный подъём: окончание stun не снимает лежачую позу и её запрет действий. Смерть имеет приоритет над ними.

### 14.4. Повторное оглушение

После успешной проверки наложения дебафа со stun новое применение заменяет прежний дебаф **с тем же ID** по общему правилу:

```text
stunEndsAt = now + newStunDuration
```

Оставшийся срок старого экземпляра не учитывается:

- Если у текущего stun с этим ID осталось 5 секунд, новый stun на 2 секунды заменяет его: остаётся 2 секунды.
- Если осталось 2 секунды, новый stun на 5 секунд оставляет цель оглушённой ещё на 5 секунд от текущего момента.
- Длительности не складываются: во втором примере не получается 7 секунд.

Это позднее решение заменяет прежнее правило максимума дедлайнов; исключения для stun нет. Числа в примерах иллюстрируют правило и не задают длительность будущего приёма. При повторном применении сначала проверяется `chance` наложения дебафа stun; неуспех не заменяет активный экземпляр и не обновляет дедлайн.

### 14.5. Снятие оглушения уроном

**Утверждено:** обычный входящий damage-вызов даёт отдельный **10% шанс** снять уже действующий stun.

- Проверка относится к одному событию обычного входящего урона.
- Разделение одного попадания на SHP- и HHP-части не создаёт два броска.
- Периодический урон (DoT) не вызывает эту проверку.
- Расход собственного HP как стоимости действия не вызывает эту проверку.
- Успешное снятие завершает только stun; KO, смерть и cooldown остаются под своими правилами.

**Утверждено:** промах и отклонённый запрос не создают damage-событие. Принятый обычный damage-вызов, включая нулевой результат, выполняет выбранную проверку 10%; фактическая положительная потеря HP не является дополнительным условием. Периодические источники, включая голод, и расход собственного HP не выполняют эту проверку.

Проверка при нулевом damage — контракт обработчика, а не отдельный вид атаки v0. При положительных стартовых параметрах и выбранной формуле брони обычные попадания дают положительный D; искусственно создавать нулевые попадания ради этой ветки не нужно. При явном принятом обычном damage-вызове с D = 0 правило 10% всё равно сохраняется.

**Несколько оглушений:** stunned сохраняется, пока активно хотя бы одно оглушающее воздействие. На обычное damage-событие выполняется один общий бросок `0.10`, а не бросок на каждый статус. При успехе прекращаются все существовавшие до новых эффектов этого попадания воздействия stun. Другие воздействия составных дебафов сохраняются. Значит, runtime должен различать сам статус и ещё активные воздействия внутри него; снятие stun не означает удаления всех остальных частей этого дебафа.

### 14.6. Порядок обработки попадания

**Утверждённый порядок:**

```text
попадание по геометрии
--> расчёт и применение урона
--> проверка 10% снятия старого stun при обычном damage-вызове
--> проверка применимости каждого нового дебафа к цели
--> независимые проверки chance применимых дебафов
--> включение всех эффектов каждого успешно наложенного дебафа
```

Основной урон попадания обрабатывается **ровно один раз**. Под «новыми эффектами» в этой последовательности понимаются остальные последствия попадания, включая наложение дебафа-раны; повторного нанесения основного урона при обходе их списка нет. Основной урон представлен отдельным полем действия, а дополнительные статусы — отдельным списком. Основной урон не дублируется как внутреннее воздействие каждого статуса.

Проверка снятия относится к оглушению, существовавшему **до новых эффектов этого попадания**. Поэтому удар с эффектом stun не снимает собственный только что наложенный stun своим же уроном.

Новый успешно применённый дебаф stun начинает собственный срок от `now`. Если старый дебаф с тем же ID остался после проверки снятия уроном, новый безусловно заменяет его; если старый уже снят, новый просто накладывается. В обоих случаях старый дедлайн не сохраняется. Если новый эффект не сработал, он не заменяет оставшийся старый stun и не восстанавливает уже снятый.

Переходы здоровья из разделов 12–13 сохраняют приоритет: смертельный урон завершает жизнь персонажа, последующие эффекты не заменяют смерть на stun или KO и не возвращают возможность действовать.

### 14.7. Эффекты по KO, текущая фаза и отложенные эффекты

**Утверждено:** новые дебафы могут накладываться на живую цель в KO по обычным шансам, без специального иммунитета. На мёртвую цель новые боевые статусы не накладываются.

Для v0 выбраны два удара топора, лук с отдельными стрелами и одна бессрочная рана со штрафом STR -10% и `chance = 0.15` на попадание обоими приёмами топора. Включение лука в v0 само по себе не добавляет эту рану стрелам. Состояние stunned и его правила предусмотрены системой, но конкретный станящий приём, его длительность и шанс отложены. Обычные удары топора и стрелы не получают автоматического stun.

Замена по ID, снятие всех оглушающих воздействий одним успешным броском 10%, сохранение прочих частей составного дебафа и стандартная отмена незавершённого действия при прерывании уже определены. Их не следует возвращать в список открытых вопросов.

Кровотечение и другие конкретные DoT пока не реализуются. Их тики и дальнейшие виды воздействий будут отдельным расширением. Новая шкала stagger, автоматический stun от большого урона и зависящее от характеристик сопротивление не приняты. Лечение остаётся за scope.

### 14.8. Рана как дебаф: выбранная последовательность

```text
контакт удара
--> прямой урон SHP/HHP по выбранным формулам
--> проверка снятия старого stun обычным уроном
--> проверка применимости раны к цели
--> для применимой раны проверка chance
--> при успехе на цели появляется дебаф-рана со своими эффектами
```

Это детализация общего порядка из раздела 14.6. Проверки выполняются для каждой задетой цели отдельно; смерть сохраняет приоритет. Для обоих начальных приёмов топора выбрана одна бессрочная рана: процентный штраф STR -10%, `chance = 0.15` на каждое попадание по цели. Это принятые начальные балансируемые параметры, а не универсальные значения всех будущих ран. ID этой раны назначается при создании definitions; в обоих приёмах используется один и тот же ID.

Например, при `SHP = 100`, `HHP = 100`, `D = 20` и выбранном `alpha = 20%` прямое попадание оставляет `SHP = 80`, `HHP = 96`. При неуспешном наложении раны эти потери всё равно остаются. При успешном — дополнительно появляется дебаф и начинают действовать его эффекты. Числа примера, кроме выбранного `alpha`, не задают баланс предмета или приёма.

**Утверждено:** рана сохраняется до явного снятия. Течение времени само по себе не удаляет этот дебаф. Способы снятия и связь лечения с восстановлением ранее потерянного HHP будут определяться отдельно, за рамками текущего обсуждения.

Слабый численный эффект начальной раны осознанно допустим в v0. При STR выше нижней границы и неизменных остальных параметрах штраф -10% даёт множитель исходного melee-урона `0.9^0.25 ≈ 0.974`, то есть уменьшение примерно на 2.6% **до брони**. Из-за нелинейной брони изменение конечного урона может быть больше. При STR = 1 нижняя граница эффективного атрибута полностью поглощает штраф; тестировать пересчёт следует также на профиле STR > 1. Это не повод менять утверждённые числа перед реализацией.

Игровое лечение остаётся за scope, поэтому рана не снимается игровыми средствами в v0. Для проверки механик нужен **служебный административный способ снять статус по ID**, используя обычный путь удаления статуса и пересчёта характеристик. Он не является лечением, не выдаёт HHP и не вводит расходники или рецепты. Конкретный интерфейс этой операции определяется при реализации; её наличие здесь пока является требованием для тестирования.

### 14.9. Срок существования дебафов

Общая система поддерживает два выбранных варианта:

| Вид дебафа | Завершение |
|---|---|
| Рана | Только явное снятие; автоматического таймера окончания нет |
| Временный дебаф, например stun | Истечение заданной длительности; досрочное снятие возможно по отдельно выбранному правилу этого дебафа |

Для stun действуют общее правило замены по ID со сроком нового применения и отдельный 10% шанс снятия обычным damage-вызовом. Проверка снятия stun не снимает раны и не меняет независимый таймер KO.

Общее правило замены бафа или дебафа с тем же ID приведено в разделе 14.14. Оно не вводит общих условий досрочного снятия.

**Утверждено:** в definitions `durationMs` принимает `null` для бессрочности либо положительное целое число миллисекунд для временного статуса. Ноль, отрицательные, дробные и нечисловые значения отклоняются при загрузке definitions; они не обозначают бессрочность или мгновенный эффект. Конкретные длительности будущих дебафов остаются балансными параметрами.

### 14.10. Повторное наложение раны с тем же ID

**Утверждено:** на цели действует один экземпляр дебафа-раны с данным ID. Если очередное попадание успешно накладывает рану с тем же ID, новый экземпляр безусловно заменяет прежний по общему правилу. Рана не получает автоматического срока окончания: новый экземпляр также сохраняется до явного снятия или следующей замены.

Это ограничение относится к дебафу, а не к урону попадания. Новый удар по-прежнему уменьшает SHP/HHP по обычным правилам, даже если его рана уже присутствует на цели.

Например, повторное наложение раны с тем же ID и тем же штрафом `STR -5` оставляет `STR -5`, а не `STR -10`: старый и новый экземпляры не действуют одновременно. Если параметры нового применения отличаются, действуют новые параметры без сравнения силы. Штраф -5 приведён только для объяснения замены; принятая начальная рана использует процентный штраф STR -10%.

Раны с разными ID не заменяют друг друга; для их модификаторов действует правило суммирования из раздела 14.11. Замена раны не отменяет ранее нанесённый прямой урон и сама по себе не является лечением. Прежнее решение сохранять старый экземпляр одинаковой раны отменено общим правилом замены по ID.

### 14.11. Штрафы характеристик от разных дебафов

**Утверждено:** штрафы от разных активных дебафов к одной характеристике суммируются. Не применяется правило «оставить только самый сильный штраф».

Разные дебафы определяются разными ID. При одинаковом ID новый экземпляр заменяет старый; при разных ID сходство названий, типов воздействия или силы не приводит к замене — раздел 14.15.

Например, одна рана даёт `STR -3`, другая — `STR -5`: суммарный штраф равен `STR -8`. Числа условные и поясняют совместимость будущих разных ран; начальная рана первой фазы использует STR -10%. Повторное наложение первой раны не добавляет ещё `STR -3`, поскольку одинаковая рана сохраняется в одном экземпляре.

Решение относится к сумме штрафов характеристик. Оно не задаёт автоматически правила объединения DoT, контроля или иных эффектов. Поддержка фиксированных и процентных модификаторов, порядок их совместного расчёта, нижние границы и сохранение дробной части выбраны в разделе 14.12.

### 14.12. Фиксированные и процентные модификаторы

**Утверждено:** definitions эффектов поддерживают оба вида изменения характеристики:

- **Фиксированное значение**, например `STR -5`.
- **Процент**, например `STR -10%`.

Вид модификатора определяется описанием конкретного эффекта. Эти варианты доступны общей системе бафов и дебафов, включая раны. Значения примеров не назначают баланс конкретной раны.

**Утверждённая формула совместного расчёта:**

```text
PercentMultiplier = max(0, 1 + PercentSum)
ModifiedAttribute = max(1, (BaseAttribute + FlatSum) × PercentMultiplier)
```

`BaseAttribute` — значение до применения рассматриваемых модификаторов; `FlatSum` — сумма фиксированных изменений, `PercentSum` — сумма процентных изменений, выраженная долей. Знак сохраняется: штрафы отрицательны, прибавки положительны. Сначала применяются фиксированные изменения, затем к полученному значению применяется общий процентный множитель.

Процентные модификаторы складываются, а не последовательно перемножаются. Расчёт не зависит от порядка наложения статусов. Например, при `STR = 100`, фиксированном штрафе `-10` и процентных штрафах `-10%` и `-20%` результат равен `(100 - 10) × (1 - 0.10 - 0.20) = 63`.

**Утверждённые нижние границы:** эффективный атрибут персонажа (STR, CON, AGI и другие) не может стать меньше **1**, процентный множитель не может стать меньше **0**. Ограничение множителя предотвращает ситуацию, когда два отрицательных промежуточных значения дают положительное усиление.

Примеры граничных случаев:

- `STR = 8`, фиксированный штраф `-20`, процентных изменений нет: итог **1**.
- Суммарное процентное изменение `-100%` или ниже: множитель **0**, итоговый атрибут **1**.
- `STR = 10`, фиксированный штраф `-20`, процентное изменение `-120%`: итог **1**, а не положительный результат от перемножения двух отрицательных чисел.

**Утверждено:** дробная часть эффективных атрибутов сохраняется в расчётах. Например, `STR = 7` со штрафом `-10%` даёт **6.3**, и зависимая игровая формула получает именно это значение, а не 6 или 7. Не округлять до целого ни промежуточные значения модификаторов, ни результат перед его использованием в других формулах. Минимум итогового атрибута 1 сохраняется.

**Утверждено:** внутренние расчёты используют `float64`, интерфейс показывает дробные показатели с одним знаком после запятой. Положительные значения меньше 0.1 отображаются как `<0.1`, а не как ноль. Форматирование не меняет значения расчётов. Имена полей фиксированных/процентных модификаторов оформляются в полной схеме definitions; `PercentSum` в формулах — доля, а формат `chance` отдельно и однозначно задан диапазоном 0–1.

### 14.13. Эффективный CON и максимумы ресурсов

В формулах этого раздела `lifeDeathFactor` — неизменный множитель мира из раздела 12.1. Пересчёт от бафов/дебафов CON не разрешает менять этот конфиг; изменение множителя требует полного wipe.

**Утверждено:** бафы и дебафы CON влияют на MHP и максимум stamina. Оба максимума рассчитываются от эффективного значения по правилам раздела 14.12, с сохранением дробной части:

```text
EffectiveCON = max(1, (BaseCON + FlatSum) × max(0, 1 + PercentSum))
MHP = 25 × sqrt(EffectiveCON) × lifeDeathFactor
MaxStamina = 1000 × sqrt(EffectiveCON)
```

Коэффициенты 25 и 1000 взяты из существующих формул проекта. Например, CON 7 со штрафом `-10%` даёт EffectiveCON 6.3: оба максимума используют `sqrt(6.3)`, без предварительного округления CON до целого. Наложение и снятие модификатора требуют пересчёта зависимых максимумов.

**Утверждено:** замена статуса с тем же ID пересчитывает итоговый набор модификаторов как одну логическую операцию. Нельзя временно удалить старый баф CON, обрезать здоровье/stamina по промежуточному максимуму и затем добавить новый. Обрезание применяется только к окончательному максимуму после замены.

**Утверждено для здоровья:** при изменении MHP сохраняются абсолютные текущие значения с обрезкой по новым пределам, без пропорционального масштабирования:

```text
HHPafter = min(HHPbefore, MHPafter)
SHPafter = min(SHPbefore, HHPafter)
```

Формулы применяются к исходно корректному состоянию здоровья и сохраняют инвариант `0 <= SHP <= HHP <= MHP`. Если текущие значения уже укладываются в новые пределы, они не меняются. Рост MHP, включая снятие дебафа CON, не добавляет HHP или SHP.

Например, при MHP 100, HHP 80, SHP 60 уменьшение MHP до 50 даёт HHP 50 и SHP 50. Если затем без других событий MHP вернётся к 100, HHP и SHP останутся равны 50. При исходных HHP 40 и SHP 30 то же уменьшение MHP до 50 не изменит текущее здоровье.

Следствие выбранного правила: временное снижение CON может оставить потерю HHP после окончания дебафа. Обрезанная часть не хранится для автоматического возврата; HHP восстанавливается только лечением. Обратное изменение CON само по себе не восстанавливает и обрезанный SHP; его обычная регенерация рассматривается отдельно.

**Утверждено для stamina:** применяется то же правило сохранения абсолютного запаса с обрезкой по новому максимуму, без пропорционального масштабирования:

```text
StaminaAfter = min(StaminaBefore, MaxStaminaAfter)
```

Если текущий запас укладывается в новый максимум, он не меняется. Например, при максимуме 1000 и запасе 800 снижение максимума до 500 оставляет 500 stamina. Если затем без других событий максимум вернётся к 1000, текущий запас останется равен 500. Запас 300 при том же снижении максимума остаётся равен 300.

Увеличение максимума, включая наложение бафа или снятие дебафа CON, само по себе не восполняет stamina; обрезанная часть не возвращается автоматически. Поэтому повторное наложение бафа CON не служит способом пополнения stamina. Обычная регенерация ресурса остаётся отдельным процессом; это решение не меняет её скорость или расписание.

### 14.14. Единое правило замены бафов и дебафов по ID

**Актуальное решение пользователя:** у каждого бафа или дебафа есть свой ID. Новое успешно применённое состояние безусловно заменяет активный экземпляр с тем же ID на этой цели. Сравнение силы, уровня или оставшейся длительности не выполняется. Это правило заменяет прежние договорённости о сохранении сильной версии, максимуме дедлайнов и сохранении старого экземпляра одинаковой раны.

Ключ замены — только ID бафа/дебафа на конкретной цели. Другой источник или приём не создаёт дополнительный экземпляр того же ID. Если совпадающего ID на цели нет, новый статус добавляется. Баф/дебаф и его внутренние воздействия заменяются целиком; старые воздействия не продолжают работать рядом с новыми.

Для временного статуса устанавливаются параметры и срок **нового применения**:

```text
EndsAt = now + NewDuration
```

Оставшийся срок старого экземпляра не переносится и не складывается с новым. Например:

- Осталось 8 секунд, новое применение с тем же ID длится 5 секунд: остаётся 5 секунд.
- Осталось 2 секунды, новое применение с тем же ID длится 5 секунд: остаётся 5 секунд, а не 7.
- Новый более слабый эффект с тем же ID также заменяет более сильный; действуют новые величины и длительность.

Старый экземпляр не хранится как подавленный и не возвращается после окончания нового. Рана с тем же ID также заменяется; поскольку раны бессрочны, новый экземпляр не получает таймера автоматического окончания.

«Безусловная замена» относится к уже применяемому новому статусу. Выбранная проверка `chance` перед наложением дебафа сохраняется: неуспех не заменяет старый экземпляр и не обновляет его срок. На одной цели одновременно действует не более одного экземпляра данного ID.

Правило включает stun и раны без исключений. Оно не меняет шанс снятия stun уроном, независимый KO или правила прямого урона попадания. Для периодических воздействий отдельно потребуется определить момент первого тика нового экземпляра; готовой модели DoT это решение не вводит.

### 14.15. Разные ID и сила эффектов

Сила эффекта не является критерием замены. Если активный дебаф даёт `STR -20%`, а новое успешное применение **с тем же ID** даёт `STR -10%`, остаётся новый штраф `-10%`. В обратном порядке результатом будет `-20%`. Это примеры возможных параметров применения, а не утверждённые способы их масштабирования.

Если у дебафов **разные ID**, они не заменяют друг друга, даже когда меняют одну характеристику или названы слабой и сильной версиями. Два разных ID с `STR -10%` и `STR -20%` дают суммарное процентное изменение `-30%` по разделу 14.12.

Таким образом, ID в definitions определяет, какие применения взаимно заменяются. Отдельные группы взаимного вытеснения и приоритет силы не используются в выбранном правиле. Формат ID — положительное целое число — выбран; конкретные значения назначаются definitions. Условия замены уже определены.

### 14.16. Принятый формат definitions

**Утверждено:** определения действий и статусов разделены. У каждого статуса положительный целочисленный ID и список воздействий. Основной урон — отдельное поле действия; дополнительные бафы/дебафы перечисляются отдельно.

- `chance` — вероятность в диапазоне **0–1**, например `0.35` для 35%. Формат 0–100 для этого поля не используется.
- Начальная рана: `chance = 0.15`, процентный штраф STR -10%, `durationMs = null`.
- `durationMs` — `null` для бессрочности либо положительное целое число миллисекунд; 0, отрицательные, дробные и нечисловые значения недопустимы и отклоняются при загрузке.
- Применимость статуса к цели проверяется до `chance`; неприменимый статус не создаёт случайный бросок. Один успешный бросок включает весь статус; внутренних отдельных бросков для его воздействий нет.
- Значения должны валидироваться при загрузке; недопустимый ID или вероятность являются ошибками definitions.

Это контракт основных полей, а не готовая полная JSON-схема или реализация loader. Полные схемы, ссылки между определениями, конкретные ID, runtime и хранение предстоит оформить при проектировании реализации. Сериализация доспехов этим не включается в scope.

## 15. Что дали исследования других игр

Этот раздел сохраняет основания обсуждения. Механики источников отделены от принятых правил Origin.

### 15.1. Lineage 2: выполнение и повторное использование

В официальных материалах издателя различаются время применения и время повторного использования. В [Lindvior, 2013](https://eu.4gameforum.com/threads/11081/) они меняются отдельно. [Описание Sayha's Talisman, 2018](https://eu.4gameforum.com/threads/655325/) показывает общий cooldown для части эффектов на одном уровне, независимые на другом и фиксированный cooldown, не изменяемый бафами.

Вывод для Origin: длительность действия и его cooldown полезно разделять; совместный cooldown — отдельное правило, а не обязательное свойство любых похожих приёмов.

Принятые моменты старта cooldown топора/лука и их связь с выполнением действия или выпуском стрелы — собственные решения Origin. Исследование не установило единый универсальный момент старта cooldown для всех навыков и версий L2.

### 15.2. Дистанционный урон: Rust и New World

В обсуждении сравнивались игровые способы потери урона на расстоянии. [Rust Devblog 119, 21.07.2016](https://rust.facepunch.com/news/devblog-119) описывает изменения поведения снарядов и сопротивления, а [Devblog 120, 28.07.2016](https://rust.facepunch.com/news/devblog-120) — баланс дистанционного спада урона. В [New World: Season 1, 03.04.2023](https://www.newworld.com/en-us/game/releases/season-one-fellowship-and-fire?language-picker=true) присутствуют исправления расчёта дистанционного урона.

Это исторические примеры использования falloff как настраиваемой игровой механики, а не доказательство единой физически правильной формулы или актуальных чисел этих игр.

Схема Origin «30% без спада, затем до 20%» выбрана пользователем. Она не копируется как точная формула одной из перечисленных игр.

### 15.3. Haven & Hearth: таймер, защита и поражение

[Патч разработчиков от 20.04.2017](https://www.havenandhearth.com/forum/viewtopic.php?p=735097) описывает прекращение боевых отношений при KO, запрет новых, возможность ограбления, hearth/logout после 30 секунд и пробуждение ещё через 30. В том же патче база grievous damage отдельного удара ограничена MHP цели: пример `500 damage, 300 MHP, 30% grievous → 90 HHP`.

Это существенно отличается от принятого в Origin полного переноса превышения остатка SHP в HHP. Ограничение grievous через MHP не переносим в нашу формулу.

[Iced Bait, 07.11.2021](https://www.havenandhearth.com/forum/viewtopic.php?f=39&t=71874) добавил явный KO-диалог с возвращением домой по умолчанию; loftar уточнил, что обычные запреты travel/logout продолжают действовать. [Гайд игрока, 2022](https://www.havenandhearth.com/forum/viewtopic.php?t=72160) уточняет подъём на месте с 1 SHP. Это вторичный источник для данного уточнения. Поздней опубликованной замены схемы 30+30 в проверенных материалах не найдено; серверный код таймера не проверялся.

### 15.4. Haven & Hearth: почему KO protection не гарантирует жизнь

[An Arrow to the Knee, 02.02.2020](https://www.havenandhearth.com/forum/viewtopic.php?f=39&t=67070) различает:

- Rage разрешает агрессию и само по себе не отключает защиту.
- Murder позволяет атаковать лежащего, уже не имеющего защиты.
- Murderous Rage снимает собственную KO protection на 24 реальных часа, усиливает grievous damage, сохраняет бой при KO и блокирует hearth/logout в этом состоянии.
- Некоторые животные продолжают нападение на лежащего, получая шанс прекратить его после очередного удара.
- Сам удар, вызывающий KO, может оказаться смертельным. Защита уже лежащего не отменяет нанесённое повреждение.

Это не означает, что Murder позволяет игнорировать защиту любого персонажа. Актуальность снятия защиты через Murderous Rage подтверждена [исправлением от 21.06.2025](https://www.havenandhearth.com/forum/viewtopic.php?p=959565).

По [игровой вики Concussion](https://ringofbrodgar.com/wiki/Concussion), KO также даёт сотрясение на 5–20% MHP. Ни этот случайный дополнительный урон, ни защита лежащего, ни специальные PvP-навыки H&H для Origin не приняты.

Не удалось отдельно подтвердить поведение уже летящей стрелы по защищённому лежащему в H&H. Формулировка о прекращении combat relations не доказывает универсальную невосприимчивость ко всем источникам урона.

### 15.5. Уточнения к старой заметке knocked_dead.md

Не использовать её как единственный источник без следующих поправок:

- Утверждение «публичных таймингов нет» опровергается патчем 2017 года.
- «Нельзя убить с одного нокаута» — неверное обобщение: смертельным может стать удар, вызывающий первый KO после предыдущих повреждений. Число попаданий и число нокаутов — разные вещи.
- Отсутствие специальных строк в просмотренных Java-файлах клиента не доказывает отсутствие KO-интерфейса: официальный клиент поддерживает серверное создание UI и загрузку кода виджетов из ресурсов.
- Эвристики стороннего клиента Hurricane по позам и ресурсу `knockchirp` не являются гарантированным серверным контрактом.
- Общие механизмы следования/переноса объектов не доказывают возможность переносить живого игрока в KO.

Первичные технические источники: [RemoteUI.java](https://github.com/dolda2000/hafen-client/blob/master/src/haven/RemoteUI.java), [Widget.java](https://github.com/dolda2000/hafen-client/blob/master/src/haven/Widget.java). Старую заметку в рамках фиксации этого документа не исправляли.

### 15.6. L2J: определения приёмов, эффекты и оглушение

Исследован предоставленный пользователем клон `/Users/mark/projects/l2j-server-game`: ветка `develop`, commit `abfde0490ac52a2106e884b7242c0276c44cdf76`, версия проекта `2.6.3.0-SNAPSHOT`. Это серверный эмулятор L2J для High Five Part 5, а не исходный сервер NCSoft и не доказательство поведения всех версий Lineage 2.

Определения навыков и обработчики эффектов дополнительно проверены в отдельном официальном репозитории `l2j-server-datapack`, commit `3ca488dd2bd0bfaca43e378886a3c2e37968153a`. В предоставленном клоне game-сервера этого datapack нет; для продолжения исследования искать XML только в game-репозитории недостаточно.

**Устройство:**

- `DocumentEngine` загружает `data/stats/skills`; `DocumentSkill` и `DocumentBase` разбирают XML-описания и несколько элементов `<effect>`.
- `Skill` хранит `Map<EffectScope, List<AbstractEffect>>`: список эффектов разделён по контекстам применения, включая обычные эффекты, self, start/end и PvP/PvE.
- `EffectHandler` связывает имя эффекта с обработчиком. Конкретный обработчик задаёт поведение эффекта.
- `BuffInfo` хранит состояние конкретного применения: источник, цель, skill, эффекты, длительность и задачи жизненного цикла. Это отделено от определения навыка.

Для Origin принята общая система бафов/дебафов с несколькими эффектами по образцу L2J. Концептуально полезно отделять определение от состояния конкретного применения. Копирование Java-классов, XML-формата, всех scope и всех частных правил L2J не утверждено. Точки входа для повторного чтения: [Skill.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/skills/Skill.java) и [BuffInfo.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/skills/BuffInfo.java).

**Примеры definitions:**

- `Stun Attack` (100): `PhysicalAttack` и `Stun` в одном приёме; `activateRate = 50`, `abnormalTime = 9`, `abnormalType = STUN`, `basicProperty = CON`, `trait = SHOCK`.
- `Stun Shot` (101): `PhysicalAttack`, `TargetCancel` с параметром `chance = 40` и `Stun`.
- `Shield Stun` (92): пример приёма с эффектом `Stun` без `PhysicalAttack`.
- `Bleed` (96): отдельный периодический эффект `TickHp` и модификация скорости передвижения.

Источники: [навыки 100–199](https://bitbucket.org/l2jserver/l2j-server-datapack/src/3ca488dd2bd0bfaca43e378886a3c2e37968153a/src/main/resources/data/stats/skills/00100-00199.xml), [навыки 0–99](https://bitbucket.org/l2jserver/l2j-server-datapack/src/3ca488dd2bd0bfaca43e378886a3c2e37968153a/src/main/resources/data/stats/skills/00000-00099.xml). Эти числа принадлежат исследованному datapack, не таблице баланса Origin. `activateRate` навыка L2J не равен гарантированной итоговой вероятности в процентах.

**Что отличается от Origin:**

- В обычной ветке применения L2J выполняет общую проверку `Formulas.calcEffectSuccess` для длительных (`continuous`) эффектов навыка по цели. Затем отдельные эффекты проходят `canStart`. Есть специальные ветки, в частности toggle и self. В Origin один приём может отдельно проверять несколько дебафов; каждый из них при успешном наложении включает весь свой набор эффектов.
- Для мгновенных (`instant`) эффектов вызывается индивидуальный `calcSuccess` перед `onStart`. Базовая реализация возвращает успех, поэтому сам вызов ещё не означает случайный бросок.
- Итоговая вероятность длительного эффекта L2J зависит от параметров навыка, уровней и характеристик/сопротивлений; есть ветки гарантированного успеха. В Origin выбран фиксированный `chance` без такого пересчёта.
- В исследованном `CharEffectList.add` L2J при `abnormalType = NONE` старый эффект удаляется через `stopSkillEffects(true, skill)` по ID навыка. Для эффектов с `abnormalType` есть другая ветка: сравниваются `abnormalType` и `abnormalLvl`, более слабый эффект отклоняется; существуют специальные случаи. В Origin пользователь выбрал единое правило для всех бафов/дебафов: новый безусловно заменяет старый с тем же ID. Это использует идею замены по ID, но не копирует все правила исследованного L2J и не утверждает универсальное поведение всех версий Lineage 2.

Для проверки формул и замены: `model/stats/Formulas.java`, `model/CharEffectList.java` в указанном снимке game-сервера; [CharEffectList.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/CharEffectList.java).

**Stun и снятие уроном:** обработчик [Stun.java](https://bitbucket.org/l2jserver/l2j-server-datapack/src/3ca488dd2bd0bfaca43e378886a3c2e37968153a/src/main/java/com/l2jserver/datapack/handlers/effecthandlers/custom/Stun.java) устанавливает состояние `STUNNED`; `L2Character.startStunning()` прекращает атаку, cast и движение. В `CharStatus` и `PcStatus` проверка `Rnd.get(10) == 0` снимает оглушение при обычном входящем damage-вызове, исключая DoT и HP consumption. Она не требует в своём блоке положительного фактического урона здоровью: [CharStatus.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/actor/status/CharStatus.java).

Из этого исследования для Origin приняты общая модель бафов/дебафов с несколькими эффектами, отдельное состояние stun и 10% снятия stun обычным damage-вызовом. Независимые фиксированные вероятности разных дебафов, единая безусловная замена по ID и порядок «урон/снятие старого stun → новые эффекты» — выбранные правила Origin. Прежний максимум дедлайнов stun отменён уточнением о замене по ID. Правила кровотечения L2J, включая различие смертельных и несмертельных периодических обработчиков, автоматически не переносим.

## 16. Текущее состояние проекта и точки интеграции

Снимок по состоянию на дату документа. Перед реализацией перепроверить код: рабочая копия развивается параллельно.

### 16.1. Здоровье и смерть

- `internal/entityhealth/health.go`: расчёт MHP, clamp SHP/HHP, применение раздельно переданных soft/hard damage, формула SHP-регенерации.
- `ApplyDamage` пока самостоятельно не вычисляет ни `alpha`, ни overflow: получает две уже рассчитанные величины.
- Проверенные источники повреждений пока относятся к голоду и административным командам. Их правила не следует автоматически менять при подключении формулы боевого попадания.
- `internal/game/player_death_system.go`: голод, SHP-регенерация, обнаружение KO и запуск перманентной смерти.
- `internal/ecs/components/entity_health.go`: текущее состояние здоровья и KO.
- `internal/game/shard.go`: обработка перманентной смерти и превращение игрока в объект трупа; персонаж помечается удалённым в БД.

Сейчас восстановление любого положительного SHP может снять KO. Поле `KOUntilTick`, несмотря на название, записывается как момент начала KO, а не утверждённый будущий дедлайн пробуждения.

Новое правило требует независимого состояния KO и дедлайна, а также отдельного положения лёжа. Через 60 секунд KO заканчивается и урон снова распределяется по SHP/HHP, но физический подъём остаётся добровольным. Пока персонаж лежит, сервер запрещает движение и любые действия, кроме доступного подъёма, сохраняя обычный collider и пассивные процессы. Проверка старта действия должна учитывать позу отдельно от KO/stun. Нельзя ограничиться переименованием поля или оставить прежнюю проверку «SHP > 0 → встать».

`game.life_death_factor` загружается из конфига (значение по умолчанию 1.0; допустимо 0.8–1.2). Для существующего мира он неизменен, включая перезапуски. Ограничение «смена только после полного wipe» пояснено в комментариях `internal/config/config.go`, `internal/entityhealth/health.go` и примере конфигурации в README. Автоматическая блокировка смены по сохранённому идентификатору/параметрам мира этими комментариями не реализуется.

Текущий код использует `StateStunned` для обездвиживания при KO и снимает его при положительном SHP. Самостоятельного временного stun с собственной длительностью нет; его потребуется отделить от KO.

Сейчас KO очищает ряд pending-действий, циклические действия и crafting. Полноту отмены будущего боевого действия и `ActiveGameAction` нужно проверить отдельно.

### 16.2. Регенерация

Текущая SHP-регенерация:

| Energy | Прибавка за интервал |
|---|---:|
| >= 900 | 0.2% MHP |
| >= 800 и < 900 | 0.1% MHP |
| < 800 | 0 |

Интервал по умолчанию — 100 ticks; при 10 Hz это 10 секунд. Это глобальное расписание. Урон его не сдвигает; запрета регенерации в бою и отдельной задержки после попадания пока нет.

HHP-лечение и полноценная система ран в проверенном игровом цикле не реализованы. Административные команды здоровья не являются игровой медициной.

### 16.3. Stamina

- `internal/entitystats/stamina.go`: максимум сейчас `1000 × sqrt(CON)`.
- `internal/entitystats/regen.go`: восстановление 5 stamina за 1 Energy.
- Интервал восстановления по умолчанию — 50 ticks, то есть 5 секунд при 10 Hz.
- Списание stamina переносит срок её следующей регенерации; непрерывный положительный расход может удерживать восстановление от срабатывания.
- `internal/entitystats/movement.go`: пороги режимов движения и отдельные helpers длительных действий.

Не смешивать два существующих контракта: часть long-action helpers требует резерва 10%, а generic ActionService уже допускает точную оплату доступной stamina. Боевой расход до нуля не требует автоматически менять экономику всех небоевых действий.

### 16.4. Действия, движение и прицеливание

- [game-actions/spec.md](../../openspec/specs/game-actions/spec.md): generic actions, выбор цели, отмена и успешная оплата.
- `internal/game/action_service.go`: текущая реализация generic actions.
- `internal/ecs/systems/directional_movement.go`: взаимодействие WASD с активными действиями.
- `internal/ecs/systems/movement.go` и `internal/entitystats/movement.go`: движение и ограничения.

Существующие правила generic actions позволяют отмену и смену действия, а списание привязано к успешному завершению/циклу. WASD отменяет `ActiveGameAction` в любой фазе, кроме `selecting`, включая подход к цели. **Эта стандартная механика выбрана и для топора:** `execution.ticks` ведёт общий прогрессбар; при завершении выполняются повторная проверка, оплата и запуск cooldown, затем применяется результат приёма. Потеря требований и движение отменяют незавершённое выполнение без затрат за действие.

Переиспользовать `ActionService.beginExecution`, `AdvanceCycle`, существующие `ActiveGameAction`/`ActiveCyclicAction`, сообщения `S2C_CyclicActionProgress`/`S2C_CyclicActionFinished` и клиентский `ActionHourGlass`. Боевой handler добавляет проверку направления, геометрию сектора и применение урона; отдельного боевого планировщика или прогрессбара не требуется. Направленный target нужно подключить к общему запуску и финальной проверке.

Лук переиспользует общие проверки, отображение прогресса, отмену и завершение, сохраняя управляемый выпуск: 100% означает полное натяжение, удержание продолжается до отпускания. Начальная оплата, расход stamina за время и резерв стрелы остаются особенностями лука. Движение, stun и KO отменяют его без возврата потраченной stamina. Урон стрелы применяется при столкновении, после завершения действия стрелка.

Направление персонажа сейчас в основном связано с движением. Для независимого прицеливания, свободного aim лука и фиксации сектора топора потребуется явное разделение направления движения и атаки.

### 16.5. Чего ещё нет в готовом виде

В проверенном коде нет законченных боевых атак по описанным правилам, нужных таблиц weapon damage/armor и полной системы стрел. Definitions `axe_sweep`/`axe_strike` и сетевые структуры направления, сектора и результата удара уже подготовлены, но обработчики боевого выполнения ещё не подключены. В текущих definitions и loader остаётся прежнее поле `execution.recoveryTicks`; при реализации нового решения его нужно удалить из контракта и валидации, а не сохранять с нулевым значением. Имеющиеся компоненты коллизий, действий и анимаций — точки опоры, а не подтверждение реализации нового дизайна.

Рекомендуемый подход реализации: сервер проверяет возможность начала, фиксирует параметры действия, ведёт существующий цикл прогресса, при выполнении рассчитывает контакт, броню и здоровье; клиент отображает прицеливание, стандартный прогрессбар и полученное состояние. Общий жизненный цикл и сообщения прогресса уже выбраны. Детали управления луком, резервирования боеприпаса, доставки здоровья и статусов предстоит оформить при реализации.

### 16.6. Геометрия и эффекты

`internal/ecs/components/collider.go` описывает прямоугольный collider через `HalfWidth` и `HalfHeight`. Для выбранного удара нужен контакт сектора с фактическим collider, а не только проверка центра объекта.

`internal/core/spatial.go` хранит объекты по позиции центра; `QueryRadius`/`QueryAABB` дают предварительный набор из пространственных ячеек. Поэтому будущий поиск кандидатов должен учитывать размеры collider: крупная цель с центром вне сектора может пересекать его краем. После предварительного отбора нужна точная проверка пересечения. Проверку стен в этот путь добавлять не следует.

Базовый формат definitions принят в разделе 14.16: отдельные определения действий и статусов, положительные целочисленные ID, `chance` от 0 до 1, `durationMs = null` для бессрочности. Полные схемы, runtime-состояние и хранение ещё предстоит спроектировать. Контракт требует независимых проверок по паре «дебаф–цель», совместного включения эффектов успешного дебафа и безусловной замены активного экземпляра с тем же ID. Срок нового временного статуса считается от нового применения. Stun сохраняет отдельное от KO состояние: один успешный бросок снимает все прежние воздействия stun, сохраняя прочие воздействия составных статусов. Два обновления здоровья — SHP и HHP — не превращают один удар в два события для снятия stun.

`internal/characterattrs/attributes.go` сейчас хранит исходные атрибуты как целые значения; `Get` также возвращает целое. При подключении модификаторов нужен отдельный путь расчёта эффективного значения с сохранением дробной части. Пропуск такого результата через прежнее целочисленное API с усечением нарушит выбранное правило. Это точка будущей интеграции, а не уже выполненное изменение кода.

`MaxHHPFromCon` и `MaxStaminaFromCon` сейчас принимают целочисленный CON. Их будущий путь расчёта должен учитывать дробный эффективный CON по разделу 14.13. Для здоровья и stamina выбран пересчёт без масштабирования текущих значений с обрезкой по новым пределам; этот контракт нужно связать с изменением модификаторов. При замене статуса CON пересчёт выполняется атомарно по итоговому набору модификаторов. Увеличение максимумов не восполняет текущие запасы.

Жизненный цикл сессии, сохранение и переходы зон должны поддержать задержанное исчезновение тела, абсолютные сроки и отмену незавершённых действий при перезапуске по разделам 13.6–13.7. Эти требования приняты для будущей реализации.

### 16.7. HP и разрушение объектов

В текущем проекте поле здоровья объектов уже предусмотрено:

- `internal/objectdefs/types.go`: `ObjectDef.HP` — целое поле `hp` из definitions.
- `internal/persistence/queries/object.sql` и сгенерированные модели репозитория: сохранение `hp`, в моделях оно представлено как nullable integer.
- `internal/game/chat_admin_commands.go`: путь административного создания читает `def.HP`.
- `data/objects/containers.jsonc` и `trees.jsonc`: у части объектов уже есть значения hp.

Однако `data/objects/objects.jsonc` содержит boulder и другие объекты, у которых hp не задан. Наличие поля в типе/БД не подтверждает готовность общего runtime повреждений и уничтожения. До подключения боя нужно обеспечить положительный начальный HP у всех обычных объектов, геометрию контакта и корректное восстановление состояния из сохранения. Отсутствующий hp нельзя молча трактовать как категориальный иммунитет или уже уничтоженный объект.

Общий боевой путь должен сохранить дробный остаток HP; существующее целочисленное сохранение нельзя использовать с потерей дробной части. Способ хранения, заполнение старых записей и связь с общим уничтожением объектов — задачи реализации, а не уже внесённые изменения. Отдельно проверить контейнеры с содержимым, деревья/ресурсы, объект трупа и освобождение пространственных коллизий. Эти вопросы не требуют идеального баланса их HP перед первой реализацией.

## 18. Отклонённые варианты и опасные неверные интерпретации

- Жёсткий общий cap развития ради равенства новичка и ветерана — отвергнут.
- Гарантия «новичок обязательно переживает первый удар» — не принималась.
- L50 / экспоненциальный спад стрелы — заменён принятой кусочно-линейной кривой.
- Реальная потеря скорости стрелы — не входит в выбранный полёт с постоянной скоростью.
- Блокирование стрел объектами boulder — исключено уточнением пользователя; они пропускают стрелы.
- `chance` в диапазоне 0–100 — исключён; definitions используют 0–1, например `0.35` для 35%.
- Кровотечение как обязательная часть первой фазы — исключено; конкретные DoT отложены.
- Рост времени полного натяжения вместе с STR — не выбран; время задаёт тип лука.
- Движение Crawl во время натяжения лука — пользователь выбрал стоять.
- Предварительный target lock для одиночного топора — не соответствует выбору цели в момент удара.
- Более узкий сектор одиночного топора — пользователь оставил те же 90°.
- Проверка попадания топора только по центру цели — заменена пересечением collider с сектором.
- Выбор ближайшей цели по центру или части collider вне сектора — не соответствует принятой метрике.
- Заслонение удара топора стенами, объектами или другими целями — пользователь выбрал отсутствие проверки преград для обоих приёмов.
- Обязательное завершение начатого топора и запрет добровольной отмены — заменены стандартной отменяемой механикой действий.
- Сохранение выполнения топора при движении на Crawl — отменено: принятая команда движения прерывает приём.
- Отдельные подготовительная и восстановительная фазы топора — исключены; длительность задаёт `execution.ticks`, отображение использует стандартный прогрессбар.
- Отмена обычным попаданием / автоматический hit-stun — отвергнута; отдельный успешный эффект stun может прервать действие.
- Один общий бросок на все дебафы приёма или все цели AoE — заменён независимыми проверками.
- Отдельные броски на внутренние эффекты одного дебафа — после уточнения выбрано совместное включение всего дебафа по одному `chance`.
- Пересчёт chance дебафа через STR, CON, Quality или сопротивления по аналогии с L2J — не входит в выбранную модель.
- Максимум дедлайнов временного статуса, включая stun, и сохранение сильной версии при более слабом новом наложении — отменены позднейшим решением: новый статус с тем же ID безусловно заменяет старый со своим сроком и параметрами. Более короткий новый stun теперь может сократить прежний остаток.
- Сохранение старого экземпляра раны при повторном успешном наложении с тем же ID — отменено: действует новый бессрочный экземпляр вместо старого.
- Сложение длительностей при замене и дополнительные экземпляры одного ID — не соответствуют выбранному правилу замены.
- Замена статусов с разными ID только из-за одинакового типа воздействия, похожего имени или большей силы — не входит в выбранную модель.
- Гарантированное снятие stun каждым ударом и полностью неснимаемый уроном stun — не выбраны; утверждён отдельный шанс 10%.
- Две проверки снятия stun на SHP- и HHP-части одного damage-события — не соответствуют выбранному правилу.
- Общее состояние/таймер stun и KO — прямо отвергнуто.
- Смена lifeDeathFactor в существующем мире, включая смену конфига перед обычным перезапуском, не допускается; нужен полный wipe.
- Суммирование попаданий одного тика по общему снимку здоровья не используется: каждое обрабатывается последовательно.
- Отмена состоявшегося выпуска стрелы из-за стены перед точкой появления и возврат оплаты за него не допускаются.
- Автоматическая компенсация выпущенных стрел после перезапуска не предусмотрена; обычная граница зоны при этом не удаляет снаряд.
- Обязательный резерв stamina для боевого действия — отвергнут.
- Исключения friendly fire для союзников — прямо отвергнуты.
- Общая задержка между завершёнными боевыми действиями — исключена; новое действие ограничивают собственный cooldown, ресурсы и состояние исполнителя.
- Оплата и запуск cooldown топора при старте — заменены оплатой при выполнении на 100%, включая промах. Незавершённое действие не оплачивается.
- Автоматический выпуск лука на 100% прогресса — не выбран; управление сохраняет удержание и отпускание.
- Возврат начальной стоимости или расхода stamina за время при отмене натяжения/удержания лука — отвергнут.
- Пробуждение сразу после положительного тика SHP-регенерации — заменено независимым KO.
- KO protection, Murderous Rage, Concussion и grievous cap H&H — исследованы, но не приняты для Origin.
- Вычисление HHP только из суммы активных ран по аналогии с H&H — не соответствует выбранному прямому HHP-урону и отдельной вероятности раны.
- Самостоятельная HHP-регенерация — пользователь выбрал восстановление только лечением.
- Прежние демонстрационные числа не становятся настройками автоматически. Для v0 отдельно утверждены B = 6, множитель одиночного удара 1.5, тестовые A = 0/4/12 и остальные значения раздела 17.1; alpha = 20% также принята.
- Самопопадание обоими ударами топора исключено на уровне отбора по ID.
- Ограничение урона только живыми существами и иммунитет построек/объектов отменены: применяется общий HP-контракт.
- Автоматический физический подъём через 60 секунд отменён: KO заканчивается, положение лёжа может сохраняться по выбору игрока.
- Движение, ползание, атака или взаимодействия из добровольного положения лёжа не разрешены; сначала нужно встать. Поза не уменьшает collider и не даёт иммунитета к попаданиям.
- Полный HHP-урон только из-за лежачей позы после окончания KO не применяется: пользователь выбрал обычное распределение SHP/HHP.

## 19. Оставшаяся работа и границы текущей фазы

Пакет из 30 рекомендаций принят пользователем. Уточнения к пунктам 8, 24 и 27 включены в основные разделы: кровотечение пока не нужно; boulder пропускают стрелы; `chance` хранится как число 0–1, например `0.35`. Закрытые вопросы из прежнего списка не требуют повторного выбора.

### 19.1. Числа первой редакции зафиксированы

Пользователь утвердил стартовый пресет v0 и расчёты из раздела 17.1. Для реализации основных механик не требуется предварительно доводить до идеала PvP, экономику stamina или late game. Уже выбраны базовый урон, броня тестовых предметов, множители приёмов, времена, cooldown, дальности, расходы и параметры стрелы.

Позднее проверяются равные соперники, несколько ступеней развития, усиленный персонаж против новичка и сильные монстры. Около двух попаданий до KO новичка остаётся допустимым ориентиром, не гарантией. Полный ассортимент оружия/брони, параметры конкретных монстров и долговременная экономика боя будут наполняться после реализации. Базовые HP старых объектов необходимо заполнить для общего контракта разрушения; отдельная идеальная балансировка построек не требуется.

### 19.2. Детализация будущей реализации

Основные правила боя и стартовые числа приняты; следующая техническая работа должна опираться на них:

- Согласовать существующие definitions и loader с жизненным циклом из разделов 5–7, удалить поле восстановительной фазы, оформить полные схемы статусов, оружия и стрел; назначить конкретные числовые ID и правила ссылок. Базовый формат из раздела 14.16, валидация durationMs и проверка применимости до chance уже приняты.
- Подключить боевые обработчики к существующему циклу действий и прогрессбару, сохранив повторную проверку на 100%, оплату топора при выполнении, стандартную отмену и управляемый выпуск лука. Оформить недостающие сообщения ввода лука, runtime-состояние отдельных воздействий составного статуса и хранение абсолютных сроков/LastCombatEventAt. Порядок попаданий, события таймера и поведение стрел на границах зон/при перезапуске уже определены.
- Подключить детерминированный выбор стека стрел в личном инвентаре, резервирование до принятия старта и служебное снятие статуса по ID для тестирования. Это не расширяет игровое лечение.
- Выбрать численные допуски геометрии, конкретное стабильное правило сортировки равных кандидатов и маски столкновений с утверждённым набором препятствий.
- Подключить HP и уничтожение всех объектов, проверить отсутствующие hp и геометрию контакта в старых definitions, сохранение дробного HP и существующий жизненный цикл контейнеров/ресурсов.
- Разделить активный KO и добровольное положение лёжа после 60 секунд; запретить действия и движение до подъёма, сохранить collider, оформить отдельную команду подъёма.
- Подготовить реализацию и проверки сценариев раздела 20 отдельным этапом. Раздел 16 описывает точки интеграции, а не готовность новой боевой системы.

### 19.3. Что остаётся за scope

**В первую редакцию v0 входят** два удара топора, лук с натяжением и отдельными стрелами, общий расчёт урона и брони, стоимость stamina и cooldown, здоровье/KO и добровольный подъём, повреждение и уничтожение объектов по HP, общая система бафов/дебафов с начальной раной и поддержкой stunned. Лук реализуется по утверждённому пресету раздела 17.1 и не отложен на следующую редакцию. Приёмы монстров используют ту же систему; конкретный набор монстров и их параметры наполняются отдельно.

За scope v0 остаются:

- Лечение и способы взаимодействия с ранами; сериализация доспехов.
- Конкретный оглушающий приём, его шанс и длительность; кровотечение и прочие DoT, включая их период, урон, взаимодействие с бронёй и поведение вне игры.
- Полная механика Hearth Fire: запуск переноса, прерывание, требования к точке и состояние после переноса. Принятые 30 секунд доступности и 60 секунд KO сохраняются.
- Разделение областей обитания новичков и ветеранов и снижение выгоды от убийств новичков, без искусственного общего ограничения поздней прогрессии.
- Подбор выпущенных стрел. Урон постройкам и неживым объектам уже включён в общую механику HP; прежнее исключение отменено.
- Моменты старта и значения cooldown небоевых действий, включая ремесло и сбор. Общее требование собственного cooldown у каждого действия сохраняется.

Активный блок, парирование, перекат, критические удары, headshots, износ брони, пробитие отдельных слотов, PvP-флаги и отдельные правила AI добивания не были приняты как механики этой фазы. Не добавлять их как договорённые.

## 20. Сценарии для проверки будущей реализации и баланса

Это список проверок дизайна для будущей реализации; выполнение игровых тестов здесь не заявляется. Стартовые числа v0 и их арифметика приняты в разделе 17.1; полная балансировка прогрессии отложена. Обычная SHP-регенерация не сокращает активный KO; после его окончания урон распределяется по SHP/HHP даже при сохранении лежачей позы.

1. Цель уходит из сектора до выполнения: при 100% серверного прогресса происходит промах, списывается вся стоимость stamina и запускается cooldown. Действие сразу завершается, другое готовое действие можно начать без дополнительного ожидания.
2. Атакующий нажимает WASD до 100%: приём отменяется без попадания, оплаты и нового cooldown; начинается обычное разрешённое движение. Старый callback не выполняет отменённую атаку.
3. Две цели меняются местами во время выполнения: одиночный приём выбирает ближайшую в момент выполнения на 100%, направление сектора остаётся зафиксированным при старте.
4. В секторе союзник и противник: социальная принадлежность не меняет отбор и урон.
5. AoE задевает несколько целей: по каждой одно попадание, урон не делится на число целей, броня считается отдельно.
6. Попадание по атакующему не вызывает KO, смерть или отдельный эффект stun: выполнение топора или натяжение лука продолжается при сохранении условий действия.
7. Специальное оглушение прерывает выполнение топора до 100%: попадания, оплаты и нового cooldown нет. Ранее начатые cooldown выполненных действий продолжают идти. После окончания stun отменённое действие само не возобновляется.
8. Игрок чередует два приёма: следующий готовый можно начать сразу после выполнения текущего, каждый соблюдает собственный cooldown от момента выполнения. Для v0 старты A/B возможны в `0.0 / 0.6 / 2.6 / 3.2` секунды.
9. Stamina ровно на стоимость топора: старт не списывает ресурс. Если на 100% его по-прежнему хватает, выполняется приём, полная оплата оставляет ноль и запускает cooldown.
10. Движение отменяет лук: невыпущенный снаряд не появляется; обычные ограничения движения остаются.
11. Быстрая стрела пересекает тонкую цель за один шаг: контакт не теряется.
12. На траектории несколько препятствий: обрабатывается ближайшее; неблокирующие объекты пропускают стрелу.
13. Урон стрелы на 30%, 65% и 100% её дальности: 100%, 60% и 20% до брони.
14. Два разных натяжения: спад считается по собственной дальности каждого выстрела.
15. Попадание пересекает остаток SHP: overflow полностью идёт в HHP без повторного начисления `alpha`.
16. Попадание сразу обнуляет HHP: возникает смерть, а не временный защищённый KO.
17. Регенерация увеличивает SHP раньше 60 секунд KO: персонаж не просыпается досрочно.
18. Живой голодный персонаж достигает конца KO: отсутствие естественной регенерации не мешает окончанию KO и получению минимального SHP в пределах HHP. Положение остаётся лежачим до добровольного подъёма; последующие попадания используют обычную формулу SHP/HHP.
19. Персонаж, лежащий в активном KO, получает удар до будущего возврата к Hearth Fire: весь D идёт в HHP, возможна смерть. После окончания KO применяется обычное распределение SHP/HHP по сценариям 79–80, даже если персонаж продолжает лежать.
20. Большая разница STR/Quality/CON: формулы сохраняют пользу прогрессии и не вводят скрытую нормализацию ради новичка.
21. Полное и частичное натяжение на близкой дистанции: сравнить не только урон попадания, но и урон в секунду с учётом полного цикла и стоимости.
22. Центр большой цели вне угла или дальности, но collider пересекает сектор: цель попадает в общий набор кандидатов обоих ударов.
23. Между атакующим и существом стена, оба collider пересекают сектор: AoE повреждает стену и существо. Одиночный удар выбирает ближайшую допустимую цель, в том числе стену; отдельной проверки заслонения нет. Стрела повреждает и останавливается на стене, а не поражает существо за ней.
24. Одна цель находится перед другой: AoE поражает обе по одному разу, передняя не заслоняет заднюю.
25. Центр первой цели ближе, но пересекающая сектор часть collider второй ближе к атакующему: одиночный удар выбирает вторую. Близкая часть collider вне сектора не даёт преимущества при выборе.
26. Приём может наложить два дебафа и задевает несколько целей: каждый дебаф проверяется отдельно на каждой цели; неуспех одного не запрещает другой. Внутренние эффекты успешно наложенного дебафа включаются вместе.
27. У ещё действующего stun осталось 5 секунд, новый успешно наложенный stun с тем же ID длится 2 секунды: старый заменяется, новый дедлайн `now + 2`. При остатке 2 и новом сроке 5 секунд дедлайн становится `now + 5`, а не `now + 7`.
28. Обычное попадание снимает SHP и HHP: проверка 10% снятия старого stun выполняется один раз на damage-событие. DoT и собственная стоимость HP её не вызывают.
29. Удар наносит урон и успешно накладывает новый stun: его damage не выполняет проверку снятия только что наложенного эффекта. Новый stun с тем же ID начинает собственный срок независимо от того, сняло ли попадание старый экземпляр: сохранившийся старый безусловно заменяется.
30. У персонажа одновременно stun и KO: снятие stun не будит его; пробуждение из KO не снимает ещё действующий stun. SHP-регенерация не заменяет ни один таймер.
31. Смертельное попадание имеет дополнительные эффекты: смерть не заменяется на временный stun/KO, действия персонажа не возобновляются.
32. Рана не выпала при попадании: рассчитанное уменьшение SHP/HHP сохраняется, отсутствие дебафа не отменяет повреждение здоровья.
33. Рана выпала: прямой урон учитывается один раз, затем дебаф включает свои эффекты; второй копии основного урона нет.
34. У живого персонажа не хватает HHP, активного лечения нет: обычное течение времени и SHP-регенерация не восстанавливают HHP.
35. После наложения раны проходит время без её явного снятия: дебаф сохраняется; отсутствие таймера окончания не заменяется условной длительностью по умолчанию.
36. У персонажа одновременно рана и временный stun: истечение или досрочное снятие stun не удаляет рану.
37. На цели уже есть рана, и новое попадание успешно накладывает рану с тем же ID: новый бессрочный экземпляр заменяет старый, одновременно действует один набор воздействий. Прямой урон нового попадания применяется как обычно.
38. Две раны с разными ID дают условные штрафы `STR -3` и `STR -5`: суммарный штраф равен `STR -8`; повторное наложение одной из этих ран с теми же параметрами заменяет её экземпляр и не увеличивает сумму.
39. При базе STR 100 и модификаторах `-10`, `-10%`, `-20%` получается STR 63 независимо от порядка наложения статусов; процентные модификаторы не перемножаются отдельно.
40. Фиксированные штрафы превышают базовый атрибут или суммарное процентное снижение достигает 100%: итог не опускается ниже 1. Одновременные отрицательные промежуточные значения не превращаются в усиление, поскольку процентный множитель ограничен снизу нулём.
41. STR 7 со штрафом `-10%` даёт эффективное значение 6.3; зависимые расчёты используют 6.3 без предварительного округления до 6 или 7.
42. CON 7 со штрафом `-10%` даёт эффективный CON 6.3: MHP и максимум stamina рассчитываются через `sqrt(6.3)`. При снятии штрафа оба максимума пересчитываются через `sqrt(7)`. Текущие HHP/SHP и stamina сохраняются с обрезкой по новым пределам, без восстановления при росте максимумов.
43. MHP 100, HHP 80, SHP 60: при снижении MHP до 50 получаются HHP 50 и SHP 50. Возврат MHP к 100 без других событий оставляет HHP 50 и SHP 50; обрезанная часть не возвращается автоматически.
44. MHP 100, HHP 40, SHP 30: при снижении MHP до 50 текущие HHP 40 и SHP 30 сохраняются, поскольку укладываются в новые пределы.
45. Максимум stamina 1000, текущий запас 800: при снижении максимума до 500 остаётся 500 stamina. Возврат максимума к 1000 без других событий оставляет запас 500; обрезанная часть не возвращается автоматически.
46. Максимум stamina 1000, текущий запас 300: при снижении максимума до 500 запас остаётся равен 300. Последующее увеличение максимума также не пополняет этот запас.
47. У временного бафа или дебафа осталось 8 секунд, новое успешное применение с тем же ID длится 5 секунд: действует новый экземпляр на 5 секунд. При остатке 2 секунды новое применение на 5 секунд также даёт 5 секунд, а не 7.
48. Повторное наложение временного дебафа не прошло проверку `chance`: существующий экземпляр, сила его эффектов и дедлайн не меняются.
49. Активный статус даёт `STR -10%`; новый успешно применённый статус с тем же ID даёт `STR -20%`: действует новый штраф `-20%`, а не сумма `-30%`. Срок берётся из нового применения; старый экземпляр не возвращается после его завершения.
50. Активный статус даёт `STR -20%`; новое успешное применение с тем же ID даёт `STR -10%`: старый безусловно заменяется, действует новый штраф `-10%` с новым сроком.
51. Два дебафа с разными ID дают `STR -10%` и `STR -20%`: оба сохраняются, суммарное процентное изменение равно `-30%`; большая сила одного не вытесняет другой.
52. Другой персонаж успешно накладывает дебаф с ID, уже имеющимся на цели: новое применение заменяет старое; смена источника не создаёт второй экземпляр того же ID.
53. После принятого старта топора stamina уменьшается другим расходом и на 100% её не хватает: финальная проверка отклоняет выполнение без урона, списания стоимости приёма и нового cooldown. Недостающий ресурс не компенсируется отрицательным остатком.
54. Во время выполнения топора исчезает требуемая экипировка или навык: стандартная проверка отменяет приём без урона, оплаты и нового cooldown. Позднее достижение клиентского прогресса 100% не выполняет отменённое действие.
55. При принятом старте топора начинается стандартный прогрессбар с total ticks из `execution.ticks`; оплаты и нового cooldown ещё нет. На 100% сервер повторно проверяет условия, выполняет удар/промах, один раз списывает стоимость и запускает cooldown. Повторная обработка завершения не повторяет урон или оплату.
56. Stun или KO наступает после уже выполненного удара топором: нанесённый урон, оплата и начатый cooldown сохраняются. Отмена нового незавершённого действия не сбрасывает этот cooldown.
57. Принято начало натяжения лука: начальная стоимость списывается один раз, затем stamina расходуется с постоянной скоростью за время натяжения и удержания. Переход к полному натяжению не прекращает расход и не вызывает повторного начального списания.
58. Игрок выпускает стрелу после натяжения или удержания: дополнительного списания stamina за сам выпуск нет. Для v0 полное натяжение без удержания стоит 44, дополнительная секунда натяжения/удержания — 20 stamina.
59. Stamina исчерпывается при частичном натяжении или удержании полностью натянутого лука: действие отменяется, персонаж опускает лук, снаряд не выпускается и новый cooldown выстрела не запускается.
60. Натяжение или удержание лука отменено движением, станом, KO или исчерпанием stamina: уже списанные начальная стоимость и расход за время не возвращаются ни полностью, ни частично; дальнейшее списание за это действие прекращается.
61. Между стрелком и целью стоит boulder: стрела проходит сквозь него без попадания. На том же пути стена или закрытая дверь получает урон по HP и останавливает стрелу, даже если уничтожается этим попаданием. Труп пропускает стрелу; boulder и объект трупа могут быть повреждены топором.
62. Definitions содержат `chance = 0`, `1` и `0.35`: наложение соответственно никогда не происходит, гарантированно проходит проверку вероятности и имеет шанс 35%. Значение `35`, отрицательное или нечисловое значение отклоняется валидацией.
63. Попадание любым из двух ударов топора успешно накладывает начальную рану: один общий ID даёт STR −10% до явного снятия, без кровотечения. Повторное наложение заменяет экземпляр, а не увеличивает штраф. Начальный шанс каждой проверки равен 0.15.
64. Два статуса с разными ID одновременно дают stunned, а один также снижает STR: один успешный бросок 10% снимает оба прежних воздействия stun и сохраняет штраф STR. Новый stun от этого же попадания применяется после проверки и не снимается ею. Промах не вызывает бросок; принятый обычный damage-вызов с нулевым уроном вызывает.
65. Отпускание лука при charge ниже 0.10 отменяет натяжение без стрелы, cooldown и возврата stamina. При charge ровно 0.10 и положительной силе выстрел разрешён при остальных выполненных условиях. Максимальный charge сам по себе не выпускает стрелу.
66. При начале натяжения одна стрела зарезервирована и недоступна для другого расходования. Отмена освобождает её; выпуск списывает ровно одну и сразу завершает действие стрелка. Движение и другое готовое боевое действие доступны по обычным условиям; новое натяжение того же выстрела ждёт собственного cooldown.
67. Несколько попаданий по живой цели в активном KO не сдвигают его срок окончания. При точном совпадении попадания и дедлайна сначала применяется полный HHP-урон; смерть отменяет окончание KO. После завершения KO новое исчерпание SHP запускает новые 60 секунд, даже если персонаж ещё не вставал.
68. При потере соединения персонаж остаётся уязвим в мире до более позднего из сроков: окончания KO и 30 секунд после последнего боевого события. Незавершённый топор отменяется без урона, оплаты и нового cooldown; натяжение лука отменяется без возврата потраченной stamina с освобождением резерва стрелы. Переподключение не сбрасывает сроки.
69. Перезапуск или переход обычной зоны не удаляет рану и не начинает заново временные статусы, KO и cooldown. Истёкшие абсолютные сроки обрабатываются при загрузке. При перезапуске незавершённый топор отменяется без оплаты и нового cooldown; натяжение лука — без возврата потраченной stamina. Cooldown уже выполненных приёмов сохраняются, незавершённый прогресс не возобновляется.
70. Замена статуса CON с тем же ID пересчитывает максимум один раз по итоговому набору модификаторов. Техническое промежуточное удаление старого бафа не обрезает здоровье или stamina, если окончательный максимум этого не требует.
71. Между стартом и выполнением топора меняется STR атакующего: приём использует значение в момент попадания на 100% прогресса. Для уже выпущенной стрелы изменение STR/Quality стрелка не меняет сохранённые параметры выстрела; броня цели учитывается в момент столкновения. Качество выстрела считается через sqrt(Qbow × Qarrow) без повторного множителя Quality.
72. Collider касается границы сектора: контакт засчитывается. При равном расстоянии двух целей одиночный удар выбирает одну по стабильному ID. Движущаяся цель пересекает путь стрелы между серверными состояниями: учитывается относительное движение за шаг; контакт ровно на максимальной дальности засчитывается до удаления стрелы.
73. Расход stamina лука на каждом серверном шаге равен скорости расхода, умноженной на прошедшее время: дробные остатки не теряются. Положительное значение меньше 0.1 отображается как <0.1, сохраняя точное значение для расчётов.

74. В секторе нет никого, кроме атакующего: оба приёма выполняются с промахом, собственное здоровье не меняется, на 100% списывается стоимость и запускается cooldown; занятость сразу снимается. При наличии другой цели собственный collider с расстоянием 0 не участвует в выборе ближайшей.
75. В секторе находятся атакующий, союзник, boulder и контейнер: AoE повреждает всех, кроме атакующего. Одиночный удар выбирает ближайшего по принятой метрике, без приоритета живого существа или противника.
76. Обычный объект с HP = 10 и A = 0 получает D = 6: остаётся HP = 4; второе такое попадание обнуляет HP и уничтожает объект ровно один раз. SHP/HHP, alpha и KO не участвуют.
77. Объект с HP = 1 получает D = 0.4, затем сохраняется и загружается: остаётся HP = 0.6 без округления до 0 или 1. Отсутствующий начальный hp в старом definition выявляется на этапе подготовки/валидации контента, не создавая бессмертную цель.
78. При попадании с D = 30 по существу с SHP = 10 и HHP = 50 hardDamage равен 0.20 × 10 + 20 = 22; итоговый HHP = 28. Сводка и детальный расчёт используют один результат, а не ошибочные 26 hardDamage.
79. На 60-й секунде KO живой персонаж остаётся лежать по своему выбору: активный KO снимается, обеспечивается минимальный SHP, автоматического подъёма нет. При SHP = 5, HHP = 20 следующий D = 2 оставляет SHP = 3, HHP = 19.6, несмотря на лежачую позу.
80. После окончания KO персонаж всё ещё лежит с SHP = 1 и HHP = 20; D = 2 даёт hardDamage = 1.2, SHP = 0, HHP = 18.8 и запускает новый KO на 60 секунд. Отдельного иммунитета или требования предварительно встать нет.
81. Персонаж решил подняться через 90 секунд после начала предыдущего KO: минимум SHP, выданный на 60-й секунде, повторно не начисляется. Переподключение также не выдаёт его снова и не поднимает персонажа автоматически.
82. Монстр запускает определённый для него секторный приём: контакт, броня, здоровье, cooldown, прерывание и эффекты проходят через те же механизмы, что атака игрока; источник команды AI не обходит эти правила.
83. Пресет v0: на цели A = 4 получаются D = 3.6 для AoE, примерно 6.23 для одиночного удара и 5.33 для полного близкого выстрела при исходных характеристиках. Оба приёма топора исключают атакующего, даже если рядом находятся только он и цель.
84. KO закончился, персонаж продолжает лежать: команды движения, Crawl, атаки топором, натяжения лука, взаимодействия с объектом и использования предмета отклоняются без расхода ресурсов, запуска cooldown, скрытой очереди или автоматического подъёма. После явного подъёма новые команды проверяются по обычным правилам; ранее отклонённые не исполняются.
85. Персонаж падает в KO, остаётся лежать после его окончания, затем встаёт: размеры и смещение collider и фильтры столкновений одинаковы на всех трёх этапах. Визуальная поза не позволяет стреле пройти сквозь персонажа или исключить его из сектора.
86. Добровольно лежащий персонаж ждёт: регенерация, сроки статусов и cooldown продолжаются. Пока действует stun, команда подъёма отклоняется; окончание stun само не поднимает персонажа. Получение нового KO снова запрещает подъём до нового дедлайна.

87. Принятое начало топора в t = 0 обновляет LastCombatEventAt атакующего; фактический промах на 100% в t = 0.6 обновляет его до 0.6. Обновления прогресса, движение, прицеливание и отклонённая новая команда не сдвигают срок. При отсутствии других событий и KO 30 секунд отсчитываются от 0.6. Если действие отменено раньше выполнения, сохраняется исходное событие старта в t = 0.
88. Стрела выпущена в t = 5, попала в союзника в t = 5.5: у стрелка LastCombatEventAt обновляется на обоих событиях, у союзника — на попадании. Попадание в обычный контейнер обновляет время стрелка; голод, регенерация и окончание дальности без контакта его не обновляют. Вход после отключения сохраняет исходный момент, а не запускает новые 30 секунд.
89. Два попадания приходятся на один серверный тик: порядок задают время и серверный номер события. Первое переводит цель с SHP = 10, HHP = 50 в KO уроном D = 10 (HHP = 48); второе D = 10 уже полностью снимает HHP (остаётся 38). Эффекты первого попадания видимы второму; это не расчёт двух атак по одному исходному состоянию.
90. У стрелка нет доступных стрел: команда натяжения отклоняется без stamina, cooldown и LastCombatEventAt. При нескольких подходящих стеках выбор стабилен; выпуск расходует зарезервированную единицу, отмена освобождает её. Наличие стрелы в соседнем контейнере не заменяет личный боеприпас.
91. Блокирующая стена находится между началом траектории и желаемой точкой появления стрелы: выпуск расходует одну стрелу, запускает cooldown и обновляет LastCombatEventAt; стена получает попадание, снаряд не возникает за ней. Действие стрелка сразу завершается. Проверка также учитывает дальность и дистанционный спад.
92. Сервер перезапускается после выпуска, но до попадания стрелы: снаряд не восстанавливается, боеприпас и stamina не возвращаются, cooldown сохраняется. Незавершённое натяжение обрабатывается отдельно: его невыпущенная стрела освобождается из резерва без возврата потраченной stamina.
93. Летящая стрела пересекает обычную границу зоны или стрелок переходит в другую зону: снаряд продолжает полёт с прежними параметрами и пройденной дистанцией, без повторного списания стрелы/стоимости и без нового начального участка полного урона.
94. Сразу после выпуска лука смена боевой экипировки разрешена при соблюдении общих условий инвентаря и состояния персонажа. Ещё действующий cooldown выстрела не сбрасывается сменой экипировки, летящая стрела сохраняет параметры выпуска.
95. Definitions с durationMs = null и положительным целым числом загружаются. Значения 0, -1, 1.5 и нечисловое значение отклоняются с ошибкой; мгновенная или бессрочная версия статуса не создаётся как молчаливый fallback.
96. Обычный объект v0 имеет A = 0: получает полный Draw в HP. Приём с начальной раной наносит ему прямой урон, но неприменимая рана не вызывает бросок chance, не добавляет STR и не создаёт статус.
97. Контейнер и мебель с collider блокируют стрелу и получают попадание по HP. Boulder, труп, трава и мелкий декор с пропускающим фильтром не создают контакт снаряда. Геометрия движения персонажа не подменяет фильтр projectile collision.
98. Рана снижает STR с 10 до 9, изменяя исходный melee-урон множителем 0.9^0.25; при базовом STR = 1 итог остаётся 1. Служебное снятие раны по ID удаляет статус и пересчитывает STR по оставшимся модификаторам, но не восстанавливает HHP и не является игровой медициной.
99. Клиент раньше сервера показывает 100% прогресса топора: урон не возникает до серверного завершения и финальной проверки. `execution.ticks = 6` использует шесть серверных ticks, без отдельного боевого таймера или новой шкалы прогресса.
100. Игрок отменяет топор стандартной командой или переключает действие до 100%: старый прогресс и анимация завершаются, урона, оплаты и нового cooldown нет. Следующий запрос проходит обычные проверки; скрытой очереди на последующий запуск нет.
101. Лук достигает 100% натяжения: прогрессбар остаётся полным, удержание и расход stamina продолжаются; стрелы и нового cooldown до отпускания кнопки нет. Отпускание при выполненных условиях выпускает одну стрелу и сразу снимает занятость.
102. Игрок отпускает лук при допустимом частичном charge до 100%: повторная проверка разрешает выпуск с силой и дальностью этого charge; прогресс завершается, резерв превращается в расход одной стрелы. Ожидания полного прогресса нет.
103. При отпускании лука условия выпуска не выполнены: снаряда и нового cooldown нет, невыпущенная стрела освобождается из резерва, уже потраченная stamina не возвращается. Достижение 100% ранее не заменяет эту проверку.
104. Стрела выпущена и ещё летит: стрелок может двигаться или выполнять другой готовый приём. Здоровье цели изменяется при фактическом столкновении, а не при достижении прогресса натяжения 100%.

Позднее для настройки баланса полезно сравнить равных персонажей, ветерана против новичка, тяжёлую броню против слабых и сильных ударов, полное/частичное натяжение и несколько боёв без полного лечения HHP. Эти прогоны не блокируют реализацию механик v0.
