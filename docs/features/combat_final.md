Дата фиксации: 2026-10-03.

Назначение: сохранить решения и рассуждения из обсуждения так, чтобы продолжить проектирование по этому документу без истории чата. Это документ дизайна, а не отчёт о реализованной боевой системе.

## 1. Как читать документ и продолжать работу

В документе используются четыре статуса:

- **Утверждено** — пользователь выбрал правило или принял соответствующее предложение. Не возвращать отвергнутые альтернативы без новой причины.
- **Рабочая модель** — формула или детализация, предложенная в обсуждении для развития выбранного подхода. Сохранена для продолжения; её численные коэффициенты и неоговорённые детали нельзя считать окончательно утверждёнными.
- **Открыто** — решения ещё нет. Не заполнять этот пробел молча.
- **Текущее состояние кода / исследование** — проверенный контекст. Наличие механики в другой игре или в старом коде не означает её принятия для нового боя.

Последние уточнения пользователя имеют приоритет над ранними пожеланиями. Особенно это касается разрыва между новичком и ветераном, движения при натяжении лука, независимого таймера нокаута, правил эффектов и геометрии топора.

Предыдущие обсуждения проходили в режиме explore. Пользователь явно разрешил сохранить их в этом отдельном документе. Создание документа не означает разрешения реализовать боевую систему, менять существующие спецификации или фиксировать невыбранные параметры.

## 2. Краткий реестр принятых решений

| Область | Принятое правило |
|---|---|
| Основа | Non-target: попадание определяется геометрией удара или столкновением снаряда |
| Урон | Один тип урона |
| Friendly fire | Союзники — обычные цели, без исключений для группы или дружбы |
| Прогрессия | Без искусственного общего потолка силы ветерана; late game должен сохранять смысл |
| PvP-разрыв | Около двух ударов ветерана до KO новичка допустимо; это ориентир, не гарантированный минимум |
| Броня | Эффективность зависит от силы конкретного входящего удара |
| Доспехи | Тип и Quality влияют на очки брони; сериализацию сейчас не проектируем |
| Топор | Два отдельных действия: удар по площади и усиленный удар по одной ближайшей цели |
| Текущая фаза | Два приёма топора; состояние stunned и поддержка эффектов могут быть заложены уже сейчас, конкретный оглушающий приём — отдельно |
| Геометрия топора | У обоих действий пересечение collider цели с сектором 90°; направление фиксируется в начале замаха |
| Преграды для топора | Не проверяются: стены и другие объекты не закрывают цель от обоих ударов |
| Выбор одиночной цели | В момент удара, по расстоянию до ближайшей части collider внутри сектора |
| Движение с топором | Во время замаха и удара — Crawl, с учётом остальных ограничений движения |
| Обязательность атаки | Начатый замах обязывает закончить атаку и recovery; добровольной отмены нет |
| Обычное попадание | Не сбивает замах топора или натяжение лука |
| Последствия приёма | Один приём может накладывать несколько дебафов; независимая проверка каждого на каждой задетой цели |
| Шанс дебафа | Один фиксированный `chance` на дебаф целиком; при успехе включаются все его эффекты |
| Бафы и дебафы | Общая система статусов по образцу L2J; статус содержит один или несколько эффектов |
| Рана | Дебаф с собственными эффектами, который может быть наложен попаданием с определённым шансом |
| Оглушение | Отдельный эффект специального приёма; прерывает действие, не тождественен KO |
| Повторный stun | Дедлайн `max(текущий дедлайн, now + новая длительность)`; длительности не складываются |
| Снятие stun уроном | Отдельные 10% на обычный входящий damage-вызов; не DoT и не расход собственного HP |
| Порядок попадания | Урон и проверка снятия старого stun, затем новые эффекты этого попадания |
| Cooldown | Собственный у каждого действия; два удара топора имеют независимые cooldown |
| Начало cooldown топора | При принятом начале замаха |
| Начало cooldown лука | При фактическом выпуске стрелы |
| Лук | Отдельная стрела с маленьким collider, прямой полёт с постоянной скоростью |
| Сила натяжения | Максимум зависит от STR игрока; дальность зависит от достигнутого натяжения |
| Время натяжения | Задаётся типом лука, не растёт вместе с STR |
| Движение с луком | Во время натяжения и удержания персонаж стоит |
| Отмена лука движением | Команда движения отменяет натяжение и позволяет сразу перейти к движению |
| Спад урона стрелы | Первые 30% дальности выстрела — 100%; затем линейно до 20% |
| Stamina | Разрешено расходовать до нуля, без обязательного резерва для боя |
| Здоровье | Обычный урон снимает SHP, а 20% этого урона повреждают HHP; превышение остатка SHP целиком идёт в HHP |
| Урон и рана | Прямое уменьшение SHP/HHP не зависит от успеха наложения дебафа-раны |
| Восстановление HHP | Только лечением; самостоятельного восстановления нет |
| Лечение | Взаимодействие с дебафами; конкретная механика исключена из scope текущего обсуждения |
| Лежащий персонаж | Весь рассчитанный урон идёт в HHP; броня продолжает учитываться |
| KO | Независимый таймер 60 секунд; регенерация не будит раньше |
| Hearth Fire | Через 30 секунд KO доступен будущий возврат к Hearth Fire |
| Пробуждение | Если персонаж жив, минимум 1 SHP в пределах HHP; HHP не восстанавливается |
| Смерть | HHP = 0; возможна сразу от удара, без обязательного промежуточного KO |

Подробные границы этих правил и оставшиеся вопросы приведены далее.

## 3. Цели боя и прогрессии

### 3.1. Non-target и тактика

**Утверждено.** Игрок атакует в направлении взгляда/прицеливания. Ему не требуется предварительно закреплять противника как target. Для топора проверяется область удара, для лука — траектория отдельного снаряда.

Тактическое значение имеют дистанция, положение, направление атаки, момент начала замаха, расход stamina и ошибки противника. Автоматический выбор ближайшей цели у одного приёма топора остаётся частью non-target модели: цель определяется внутри геометрии конкретного удара, а не сопровождается заранее.

### 3.2. Как изменилось требование к разрыву сил

Сначала пользователь выбрал заметное преимущество развития с возможностью победить тактикой, затем попросил умерить разрыв из-за permadeath. Позднее он явно уточнил окончательную позицию:

- Искусственно жёстко ограничивать развитие ветеранов нельзя: это разрушит late game.
- В мире будут более сильные монстры и более сложные условия.
- Допустим ориентир около двух попаданий ветерана до KO новичка.
- В таком столкновении отсутствие у новичка реальных шансов осознанно принимается.
- Снижение угрозы новичкам предполагается решать разными областями обитания и отсутствием смысла их убивать.

**Окончательное правило:** не балансировать весь бой вокруг равных шансов новичка и ветерана. Тактика важна, но не обязана компенсировать произвольно большую разницу развития.

«Два удара» не означает защиту от первого смертельного попадания, принудительный нижний предел TTK или ограничение максимального урона. При достаточно большой разнице сил возможна смерть от одного удара.

Географическое разделение игроков, награды, стоимость агрессии, преступления и экономические стимулы пока не спроектированы. Указанное направление не является уже существующей системой защиты новичков.

### 3.3. Один тип урона

**Утверждено.** Сейчас нет отдельных режущего, колющего, дробящего, магического и других типов урона и соответствующих сопротивлений.

SHP и HHP — два последствия одного рассчитанного попадания. Это не два разных типа урона.

## 4. Урон, STR, Quality и броня

### 4.1. Обозначения

| Обозначение | Значение |
|---|---|
| `B` | Базовый урон оружия/действия в выбранной модели |
| `STR` | Сила атакующего |
| `CON` | Конституция, влияющая на существующие максимумы здоровья и stamina |
| `Qweapon`, `Qbow`, `Qi` | Quality оружия, лука и отдельного предмета брони |
| `S0`, `Q0`, `F0` | Положительные опорные значения для нормировки |
| `Draw` | Сила попадания до применения брони; уже с модификатором действия и дистанции |
| `A` | Суммарные очки брони конкретной цели |
| `D` | Полученный урон после брони, перед распределением по SHP/HHP |
| `alpha` | Доля обычного урона, повреждающая HHP |

Здесь `Draw` означает raw damage, а не натяжение лука. Сила натяжения далее обозначается `F`.

### 4.2. Рабочая формула ближнего урона

В обсуждении использовалась следующая модель:

```text
DmeleeBase = B × (STR / S0)^0.25 × (Qweapon / Q0)^0.25
Draw      = DmeleeBase × ActionDamageMultiplier
```

Рабочие нормировки: `S0 = 1` — исходное значение атрибутов в текущем проекте; `Q0 = 10` — удобное опорное качество. Это нормировки формулы, а не ограничения характеристик.

Идея степенного роста — сохранить непрерывную пользу развития без чрезмерно резкого роста от каждого множителя. При такой формуле:

- Рост только STR в 16 раз даёт двукратный множитель урона.
- Рост только Quality в 16 раз также даёт двукратный множитель.
- Одновременный рост обоих в 16 раз даёт четырёхкратный урон до брони.
- Формула не имеет общего верхнего потолка.

**Статус:** сохранённая рабочая модель. Выбор зависимости от STR, Quality и базового урона принят; конкретные показатели степени и базовые значения необходимо проверить на всей прогрессии. Числа из примеров не являются утверждённой таблицей оружия.

### 4.3. Очки брони от экипировки

Рабочая формула:

```text
Ai = BaseArmor(itemType_i) × sqrt(Qi / Q0)
A  = sum(Ai)
```

Тип предмета определяет базовую защиту, Quality масштабирует её. Считаются предметы, действительно дающие очки брони. Собственная броня рассчитывается для каждой поражённой цели.

**Утверждено:** учитывать тип и качество экипировки. **Рабочая модель:** суммирование вкладов и степенная зависимость качества. **Открыто:** таблицы предметов, слоты, совместимость частей комплекта и точные базовые значения.

Пользователь отдельно исключил из текущего обсуждения сериализацию доспехов. Здесь не задаются JSON-поля, формат сохранения, миграции или изменения item definitions.

### 4.4. Выбранный подход: броня зависит от силы удара

**Утверждён выбранный вариант** «зависимость от силы удара». Его сохранённое математическое выражение:

```text
D = Draw × Draw / (Draw + A)
DamageReductionFraction = A / (Draw + A)
```

Следствия:

- При `A = 0` весь положительный `Draw` проходит в здоровье.
- Одна и та же броня поглощает большую долю слабого удара и меньшую долю сильного.
- При `Draw = A` проходит половина урона.
- При конечной броне и положительном ударе результат положителен; отдельного порога «броню вообще невозможно пробить» эта формула не вводит.
- Для нулевого урона результат должен быть нулём, включая случай `Draw = A = 0`.

Иллюстрация при `A = 50`:

| Урон до брони | Урон после брони | Поглощённая доля |
|---:|---:|---:|
| 25 | 8.33 | 66.67% |
| 50 | 25 | 50% |
| 100 | 66.67 | 33.33% |
| 200 | 160 | 20% |

Таблица объясняет формулу и не задаёт параметры реальной экипировки.

Не вводить по умолчанию минимальный урон 1, жёсткий предел поглощения или дополнительный cap урона: такие правила не выбирались. Порядок округления и точность хранения требуют определения при реализации.

### 4.5. Порядок вычисления

```text
базовый урон + STR/Quality/натяжение
--> множитель конкретного действия
--> спад от дистанции, если это стрела
--> броня конкретной цели
--> распределение D по SHP/HHP
--> смерть либо KO либо продолжение боя
```

Усиление одиночного удара применяется **до брони**. Поэтому множитель силы приёма не равен множителю конечного урона по бронированной цели.

Например, только для иллюстрации: при `A = 50` обычный `Draw = 50` даёт `D = 25`. Если приём увеличивает исходный урон в 1.5 раза, `Draw = 75` даёт `D = 45`, то есть итог вырос в 1.8 раза. Множитель 1.5 не утверждён как балансное значение.

## 5. Топор: два самостоятельных приёма

### 5.1. Общие правила

**Утверждено:**

- Оба приёма используют сектор **90°**.
- Направление фиксируется **в начале замаха**.
- После начала замаха нельзя довернуть сам сектор вслед за новым направлением прицеливания.
- Попадание определяется **в момент удара** по фактическому положению участников.
- Положение сектора связано с фактической позицией атакующего в момент удара. Направление зафиксировано, но персонаж может сместиться разрешённым движением.
- Достаточно пересечения **любой части collider цели** с сектором в пределах дальности. Центр цели не обязан находиться внутри сектора.
- **Преграды не проверяются** для обоих приёмов: стены, другие объекты, персонажи и животные не заслоняют цели от удара.
- Во время замаха и удара разрешено самое медленное передвижение — существующий режим **Crawl**.
- Полный выход collider цели из зоны до момента удара приводит к промаху по этой цели.

Для симметричного сектора 90° это соответствует отклонению до 45° в каждую сторону от зафиксированного направления. Дальность оружия ещё не назначена.

Проверка только по сектору — осознанное правило. Если collider цели пересекает сектор, стена между игроком и целью не отменяет попадание. Это относится и к AoE, и к одиночному удару; для стрел остаются отдельные правила столкновения с препятствиями из раздела 8.

### 5.2. Удар по области

- Поражает все допустимые цели, попавшие в область удара.
- Одна цель получает урон не более одного раза от одного удара.
- Общая сила атаки не делится между числом целей.
- Каждой цели применяется её собственная броня, затем её состояние SHP/HHP.
- Союзники входят в набор целей на общих основаниях.

Идея: удобство против нескольких целей оплачивается меньшей силой отдельного попадания по сравнению с одиночным приёмом.

### 5.3. Усиленный удар по одной цели

- Использует тот же сектор **90°**, а не более узкий луч или конус.
- В момент удара выбирает **одну ближайшую допустимую цель** из того же набора пересечений, который использует AoE.
- Наносит больше исходного урона, чем удар по области.
- Выбор не закрепляется в начале замаха и не сопровождает убегающую цель.
- Ближайшей целью может оказаться союзник.

**Утверждённая метрика:** расстояние от позиции атакующего в момент удара до ближайшей точки той части collider цели, которая находится внутри сектора. Не использовать центр цели или ближайшую точку collider, лежащую вне сектора.

Формально, если `S` — сектор удара с учётом дальности, `C` — collider цели, а `O` — вершина сектора, цель входит в набор кандидатов при непустом пересечении `C ∩ S`. Для одиночного удара сравнивается `distance(O, C ∩ S)`.

Примеры: крупная цель может быть задета краем collider при центре за пределами угла или дальности; маленькая цель с более близким центром не обязательно будет выбрана, если пересекающая сектор часть collider другой цели находится ближе.

**Открыто:** разрешение равных расстояний, численная точность и обработка касания границ. Сам принцип пересечения collider, метрика выбора и отсутствие проверки преград уже выбраны.

### 5.4. Обязательный цикл

```text
действие принято --> замах --> удар/промах --> recovery --> готовность
```

Пользователь прямо выбрал: начатый замах обязывает закончить атаку и восстановление после неё.

- Добровольная отмена, повторное нажатие, переключение действия или смена оружия не должны позволять обходить этот цикл.
- Команда движения меняет допустимое перемещение, но не отменяет замах.
- Промах также требует recovery.
- Обычное попадание по атакующему не отменяет цикл.
- Оглушение и нокаут могут его прервать. Смерть прекращает действия персонажа.
- Уже начатый cooldown при прерывании не возвращается.

Конкретная политика запрета/отложенной обработки смены экипировки ещё не задана. Обязателен результат: смена оружия не создаёт бесплатной отмены или обхода cooldown.

**Открыто:** скорость движения именно во время recovery. Crawl явно выбран для замаха и удара; не считать отдельный режим recovery уже согласованным. Длительности фаз и длительность окна попадания также ещё не заданы.

## 6. Cooldown и recovery

### 6.1. Самостоятельность таймеров

**Утверждено:** у каждого действия собственный cooldown, в том числе у обоих ударов топора.

Формулировка пользователя была широкой: «у каждого действия вводим cooldown». Здесь подробно согласованы боевые действия. Как это распространять на ремесло, сбор и остальные небоевые действия, отдельно не разобрано.

Для боя:

- Cooldown ограничивает повторное применение конкретного действия.
- Recovery ограничивает начало следующего действия после текущего.
- Эти интервалы идут параллельно, а не последовательно суммируются.
- После recovery можно использовать другой приём, если его cooldown готов.
- Для повторения того же приёма должны закончиться и recovery, и его cooldown.
- Удар по площади и одиночный удар можно чередовать, в том числе против одной цели.

Пример времени, не балансная настройка: действие началось в `t = 0`, весь цикл закончился в `t = 1.2`, cooldown этого действия закончится в `t = 3`. Другой готовый приём можно начать в 1.2, тот же — в 3; ждать до 4.2 не нужно.

### 6.2. Топор

- Cooldown начинается при принятом начале замаха.
- Неудачная попытка начать действие не равна начатому замаху.
- Промах не отменяет cooldown.
- Оглушение или KO после начала не отменяют cooldown.

### 6.3. Лук

- Cooldown начинается при фактическом выпуске стрелы.
- Частичное и полное натяжение запускают одинаковый cooldown выбранного выстрела.
- Следующее натяжение можно начинать только после его окончания.
- Отменённое натяжение без выпуска стрелы не запускает cooldown выстрела.

Это сохраняет обязательный интервал после каждого выпуска и исключает предварительное накопление следующего выстрела во время cooldown.

Одинаковый cooldown не гарантирует, что короткое натяжение всегда хуже по урону в секунду. В рабочей модели начальный урон растёт как `sqrt(charge)`, а время натяжения — линейно; на близкой дистанции частичные выстрелы могут оказаться выгодными. Это нужно проверить вместе с бронёй, дальностью и расходом stamina при подборе параметров, не добавляя незаметно минимальное натяжение или отдельный штраф.

### 6.4. Что осталось открытым

Численные cooldown, recovery лука после выпуска, влияние будущих характеристик/эффектов на скорость действий, поведение при переподключении и переходе между зонами не определены. Независимые cooldown не означают разрешение выполнять несколько боевых действий одновременно.

## 7. Лук: натяжение, управление и сила выстрела

### 7.1. Утверждённая основа

- Стрела — полноценный отдельный снаряд с маленьким collider.
- Полёт прямолинейный, по заданному вектору, с постоянной фактической скоростью.
- Дальность определяется достигнутой силой натяжения.
- Максимальное натяжение зависит от STR.
- Время полного натяжения задаётся типом лука и не меняется вместе с STR.
- Во время натяжения и удержания готовой стрелы персонаж **стоит на месте**.
- Команда движения отменяет натяжение и позволяет сразу уйти.

«Сразу уйти» означает отсутствие дополнительной задержки от отменённого лука. Обычные ограничения stamina, KO, оглушения и столкновений продолжают действовать.

### 7.2. Сохранённая рабочая модель натяжения

```text
charge = clamp(heldTime / DrawTimeForBowType, 0, 1)
F      = Fmax(STR, bow) × charge
R      = RangeCoefficient × F
Dlaunch = Bshot × (Qbow / Q0)^0.25 × sqrt(F / F0)
```

Это рабочая математическая модель, а не завершённая таблица баланса.

- `Fmax(STR, bow)` ещё требует точной функции. Линейность по STR отдельно не утверждена.
- Обсуждалось ограничение силы возможностями конкретного лука. Такое ограничение предмета не должно превращаться в общий потолок развития персонажа: более сильные луки могут иметь другие параметры.
- `R ∝ F` и `Dlaunch ∝ sqrt(F)` — сохранённые зависимости предложенной модели.
- Линейное нарастание `charge` удобно как исходный вариант; форму кривой следует считать рабочей.
- STR входит через силу натяжения. Не добавлять тот же вклад STR повторно отдельным множителем поверх этой формулы.
- Состав `Bshot`, вклад типа/качества стрелы, значения `F0`, `RangeCoefficient` и пределы конкретных луков пока не утверждены.

При этой модели частичное натяжение уменьшает и дальность, и начальный урон. Реальная скорость снаряда при этом остаётся постоянной.

### 7.3. Рабочая детализация управления

В обсуждении предложен следующий пакет для продолжения дизайна:

- До выпуска разрешено менять направление прицеливания, оставаясь на месте.
- После полного натяжения можно удерживать стрелу; дополнительное удержание не наращивает силу сверх максимума.
- Стрела выпускается явным действием игрока, а не автоматически по достижении максимума.
- Движение отменяет натяжение; это правило пользователь подтвердил отдельно.
- Оглушение, KO и исчерпание stamina отменяют натяжение без автоматического выстрела.
- Отмена сохраняет невыпущенную стрелу, но не возвращает уже потраченную stamina.
- Уже выпущенная стрела продолжает полёт после оглушения, KO или смерти стрелка.

Свободное прицеливание, удержание без автоспуска, обращение с боеприпасом и расход stamina за время удержания сохранены как рабочая детализация предложенного пакета. Для реализации потребуется явный контракт ввода и жизненного цикла предмета стрелы.

Не определены минимальное допустимое натяжение, реакция на почти мгновенный отпуск и поведение при `F = 0`. Формулы дальности и спада не должны делить на нулевой `R`.

### 7.4. Фиксация параметров при выпуске

Для снаряда сохраняются достигнутая сила, направление, начальный урон и предельная дальность этого выстрела. Последующее движение/поворот стрелка не перенаправляет выпущенную стрелу.

Рабочая кинематика:

```text
position(t) = launchPosition + unitDirection × ProjectileSpeed × t
travelLimit = R
lifetime    = R / ProjectileSpeed
```

Управление гравитационной дугой, наведением или фактическим торможением не входит в выбранную модель прямого полёта.

## 8. Столкновения стрелы и попадания

Сохранённый подход к реализации:

- Не каждый объект является препятствием для стрелы. Нужен отдельный признак/фильтр участия в projectile collision.
- Проходимость объекта для персонажа и препятствие для стрелы — разные свойства.
- Стрела проверяет весь отрезок перемещения за серверный шаг, учитывая свой маленький collider, а не только конечную точку.
- Среди пересечений выбирается первый контакт по направлению полёта.
- Первое блокирующее препятствие останавливает стрелу, даже если само не получает урон.
- При попадании в цель урон применяется один раз, дальнейшего полёта сквозь неё не предполагается.
- Для стрелы не используется скольжение вдоль препятствий.

Причина проверки отрезка: сервер работает с дискретными шагами; при стандартных 10 Hz быстрая стрела может перескочить через небольшую цель между двумя конечными позициями.

Это описание принципа swept collision/CCD, а не готовый формат collision mask. Размер collider, список блокирующих объектов, точка появления стрелы, обработка препятствия вплотную к стрелку и точное правило на границе максимальной дальности ещё требуют определения.

Также открыто, как учитывать перемещение самой цели внутри одного серверного шага и нужна ли компенсация сетевой задержки. Источником истины для попадания и урона должен оставаться сервер; готовой схемы lag compensation в обсуждении не выбрано.

## 9. Потеря урона стрелы с расстоянием

### 9.1. Почему спад отдельно от скорости

Пользователь хочет передать потерю силы стрелы с дистанцией, хотя фактическая игровая скорость остаётся постоянной. Поэтому уменьшается расчётный урон, а не скорость перемещения collider.

Связь реальной кинетической энергии со скоростью служит мотивацией. Выбранная игровая кривая не заявляется точной физической моделью сопротивления воздуха.

### 9.2. Утверждённые константы

```text
BowDamageFalloffStartFraction = 0.30
BowDamageAtMaxRangeMultiplier = 0.20
```

Имена сохранены как понятные обозначения будущих констант, не как уже существующие поля кода.

Пользователь прямо попросил вынести оба значения в константы для дальнейшей балансировки.

### 9.3. Формула

`s` — пройденное стрелой расстояние до контакта. `R` — максимальная дальность **данного выстрела**, уже рассчитанная из натяжения.

```text
u = s / R
a = BowDamageFalloffStartFraction
b = BowDamageAtMaxRangeMultiplier

p = clamp((u - a) / (1 - a), 0, 1)
distanceMultiplier = 1 - (1 - b) × p
Draw = Dlaunch × distanceMultiplier
```

При выбранных значениях:

```text
0 <= s <= 0.30R: multiplier = 1
0.30R < s <= R:  multiplier = 1 - 0.80 × (s/R - 0.30) / 0.70
s > R:           полёт завершён, попаданий дальше нет
```

Константы при будущей настройке должны оставлять определённую кривую: `0 <= a < 1`, `0 <= b <= 1`; вычисление требует `R > 0`.

| Пройденная доля дальности | Множитель исходного урона |
|---:|---:|
| 0–30% | 100% |
| 50% | 77.14% |
| 65% | 60% |
| 80% | 42.86% |
| 100% | 20% |

### 9.4. Последствия для брони и коротких выстрелов

Спад применяется **перед бронёй**. Поэтому 20% исходного урона на предельной дистанции не означают 20% ближнего урона по бронированной цели.

Иллюстрация: при `Dlaunch = 100`, `A = 100` ближний урон равен 50. На максимальной дальности `Draw = 20`, и после той же брони проходит примерно 3.33. Броня сильнее подавляет ослабевшую стрелу.

У частично натянутого выстрела меньше собственный `R`, поэтому короче и участок полного урона `0.30R`. Не подменять его дальностью полного натяжения или общим радиусом всех луков.

### 9.5. Почему отказались от L50

L50 обсуждалась как отдельная длина, за которую урон падает вдвое, например в кривой вида `2^(-s/L50)`. Это удобный параметр экспоненциального затухания, но он создаёт ещё одну дистанцию помимо дальности самого выстрела.

Пользователь выбрал более явную схему «полный урон до 30%, затем линейно до 20%». **L50 в принятой модели нет.** Не возвращать экспоненциальный спад или реальное замедление снаряда при реализации.

## 10. Stamina и движение

### 10.1. Принятое правило расхода

**Утверждено:** боевые действия могут расходовать stamina до нуля. Обязательного остатка 5%, 10% или другого резерва не вводим.

Это не разрешает отрицательную stamina или бесплатный старт действия с недостающим ресурсом.

### 10.2. Сохранённая рабочая модель затрат

- Стоимости задаются абсолютными единицами для действия/типа лука; конкретные суммы не выбраны.
- Для топора предложена фиксированная оплата при принятом начале замаха.
- Если ресурса на старт недостаточно, действие не начинается.
- Если ресурса ровно хватает, действие начинается и оставляет ноль.
- Уже оплаченный замах топора завершается и при нуле stamina, если его не прерывает KO/оглушение/смерть.
- Для лука предложена начальная стоимость и расход за время натяжения/удержания.
- Дополнительная оплата в момент выпуска в этой модели не требуется.
- Исчерпавший stamina лучник опускает лук без автоматического выстрела.
- Потраченная на отменённое натяжение stamina не возвращается.

Моменты оплаты, частота списания за удержание и конкретные расходы сохранены как рабочая детализация. Не путать их с прямо утверждённым принципом «разрешить до нуля».

### 10.3. Связь с существующим передвижением

Существующие множители:

| Режим | Скорость относительно Walk |
|---|---:|
| Crawl | 0.5 |
| Walk | 1 |
| Run | 1.5 |
| FastRun | 2 |

При текущей базовой скорости игрока 32 Crawl соответствует 16 игровым единицам в секунду. Эти значения — контекст существующего движения, не новый баланс боевых дистанций.

Текущие ограничения по доле максимальной stamina:

- Ниже 50% недоступен FastRun.
- Ниже 25% недоступны Run и FastRun.
- Ниже 10% остаётся Crawl.
- Ниже 5% движение недоступно.

Разрешение потратить stamina до нуля не отменяет эти пороги. Поэтому отмена лука командой движения может убрать натяжение, но не дать фактически уйти при полностью исчерпанной stamina.

Crawl сейчас не расходует stamina на движение. Само боевое действие при этом может иметь свою стоимость.

### 10.4. Что ещё требует настройки

Нужно подобрать стоимость действий, чтобы начало боя, чередование приёмов, удержание лука и отход составляли осмысленную экономику ресурса. Новых значений регенерации или специальной боевой регенерации stamina пока не принято.

## 11. Friendly fire, союзники и допустимые цели

Пользователь прямо определил игру как хардкорную non-target систему без исключений для союзников.

- Союзник в секторе AoE получает урон.
- Союзник может стать ближайшей целью одиночного удара.
- Союзник на траектории стрелы принимает попадание на общих основаниях.
- Не фильтровать попадания по party, clan, friendship или аналогичному социальному признаку.
- Не добавлять автоматическое ослабление урона союзникам.

Коллизии и допустимость повреждения определяются физической/игровой природой объекта и состоянием, а не дружественностью.

Не определены самопопадание стрелка при появлении снаряда, повреждение построек и неживых объектов, а также участие трупов в отборе целей и блокировании стрел. Для ударов топора заслонение любыми объектами уже исключено. Эти вопросы не являются поводом возвращать защиту союзников.

## 12. SHP, HHP, нокаут и смерть

### 12.1. Значение шкал

- `SHP` — текущее мягкое здоровье; его исчерпание приводит к KO, если персонаж жив.
- `HHP` — оставшееся твёрдое здоровье; его исчерпание означает смерть.
- `MHP` — текущий максимум здоровья.
- Сохраняется инвариант `0 <= SHP <= HHP <= MHP`.

Текущая формула проекта:

```text
MHP = 25 × sqrt(CON) × lifeDeathFactor
```

При факторе 1 и исходном CON 1 это 25 MHP. Это существующая опора для численного баланса, а не заново спроектированная система характеристик.

### 12.2. Обычное попадание по персонажу в сознании

**Утверждено:** весь рассчитанный после брони урон уменьшает SHP, а его доля повреждает HHP уже с каждого обычного попадания.

При достаточном остатке SHP:

```text
SHP damage = D
HHP damage = alpha × D
```

**Утверждено:** `alpha = 0.20` (20%) как начальное настраиваемое балансное значение. Его следует хранить отдельно от логики расчёта. Это доля урона после брони, а не доля максимального здоровья цели. Превышение остатка SHP и урон по уже нокаутированному продолжают обрабатываться по отдельным правилам ниже.

### 12.3. Превышение остатка SHP

**Утверждено:** часть попадания сверх оставшихся SHP полностью переносится в HHP.

Для персонажа, находившегося в сознании до попадания:

```text
softPart = min(D, SHPbefore)
overflow = D - softPart
hardDamage = alpha × softPart + overflow

SHPafter = max(0, SHPbefore - D)
HHPafter = max(0, HHPbefore - hardDamage)
SHPafter = min(SHPafter, HHPafter)
```

Эквивалентная запись:

```text
hardDamage = alpha × D + (1 - alpha) × max(0, D - SHPbefore)
```

Не использовать `alpha × D + overflow`: это повторно начисляет долю HHP на ту же часть превышения.

### 12.4. Урон по уже нокаутированному

**Утверждено:** весь `D` повреждает HHP. Броня применяется до этого распределения как обычно.

Будущий фиксированный KO должен определяться отдельным состоянием/таймером. Если регенерация во время KO сможет повысить SHP, это не должно ни будить раньше, ни возвращать лежащему обычную мягкую защиту от добивания. Ветка «уже в KO» должна оставаться явной.

Поведение самой регенерации SHP в течение этих 60 секунд ещё открыто; утверждены независимость пробуждения и полный HHP-урон по лежащему.

### 12.5. Пример распределения

Примеры используют выбранное значение `alpha = 0.20`; исходные количества здоровья и величины попаданий — иллюстративные.

| До попадания | D после брони | Урон HHP | Результат |
|---|---:|---:|---|
| SHP 40, HHP 60, в сознании | 10 | 2 | SHP 30, HHP 58 |
| SHP 10, HHP 50, в сознании | 30 | 2 + 20 = 22 | SHP 0, HHP 28, KO |
| SHP 0, HHP 28, уже KO | 12 | 12 | HHP 16, KO продолжается |
| SHP 10, HHP 20, в сознании | 30 | 22 | HHP 0, смерть |

Обрабатывать смерть раньше обычного перехода в KO. Не предоставлять обязательный промежуточный нокаут персонажу, который уже получил смертельный HHP-урон.

### 12.6. Повреждение здоровья, раны и граница лечения

**Утверждено:** удар непосредственно уменьшает SHP и HHP, а также может с некоторой вероятностью наложить рану-дебаф с собственными эффектами. Неудачное наложение раны не отменяет уже рассчитанный урон здоровью. Подробности общей системы бафов/дебафов приведены в разделе 14.

Следовательно, HHP в Origin не вычисляется просто как MHP минус сумма активных ран. Потеря HHP возможна и при отсутствии дебафа-раны. Само наложение раны не должно повторно списывать основной урон попадания; дополнительные последствия определяются её эффектами.

**Утверждено:** HHP восстанавливается только лечением. Лечение будет взаимодействовать с дебафами, но пользователь явно исключил его механику из scope текущего обсуждения. Не выбирать сейчас лекарства, скорость восстановления, условия применения или связь снятия дебафа с возвратом ранее потерянного HHP. Эта граница не отменяет уже выбранное отсутствие самостоятельной HHP-регенерации.

Отдельное повреждение за сам факт нокаута и случайное сотрясение как в H&H не приняты. Конкретные эффекты ран, включая возможное кровотечение, пока не выбраны и не добавляются автоматически в формулу обычного попадания.

## 13. Нокаут: 60 секунд и будущий Hearth Fire

### 13.1. Вход в состояние

Нокаут наступает при исчерпании SHP, если HHP остаётся положительным. Персонаж теряет возможность действовать; начатый замах или натяжение прерывается.

Отсчёт идёт от момента входа в KO.

### 13.2. Временная схема

| Время с начала KO | Правило Origin |
|---|---|
| 0 секунд | Персонаж падает, действия прекращаются, начинается независимый таймер |
| 0–30 секунд | Лежит; может получать урон и погибнуть |
| 30 секунд | Становится доступен будущий возврат к Hearth Fire |
| 60 секунд | Оставшийся живым персонаж пробуждается независимо от естественной регенерации |

**Утверждено:** `KnockoutDuration = 60 seconds` и `HearthReturnAvailableAfterKO = 30 seconds`. Это обозначения правил, а не уже существующие имена настроек.

### 13.3. Пробуждение

- Обычная регенерация SHP не поднимает персонажа до окончания таймера.
- При окончании таймера живой персонаж получает возможность подняться.
- Ему обеспечивается минимум 1 SHP, но не больше оставшегося HHP.
- HHP пробуждение не восстанавливает.
- Низкая сытость сама по себе не превращает фиксированный KO в бессрочный.
- При HHP = 0 наступает смерть, пробуждение отменяется.

Выражение для минимального восстановления без нарушения границ:

```text
if HHP > 0: SHP = min(HHP, max(SHP, 1))
```

Оно не задаёт пока невыбранную скорость регенерации во время KO.

### 13.4. Уязвимость и Hearth Fire

Нокаут не даёт иммунитета к урону. Ожидание 30 секунд до Hearth Fire не гарантирует выживание; лежащего можно добить.

Пользователь отметил Hearth Fire как **будущую механику**. Сейчас зафиксирована только доступность возврата после 30 секунд. Ещё не выбраны:

- Ручной запуск или автоматический выбор по умолчанию.
- Длительность самого переноса и возможность его прервать.
- Условия доступности Hearth Fire, ограничения локаций, отсутствие/уничтожение точки.
- Состояние персонажа после переноса и судьба оставшейся части KO-таймера.
- Правила выхода из игры при KO.

Не переносить из H&H автоматически меню из трёх опций, автоматический hearth, logout или ограничения Murderous Rage.

### 13.5. Граничные случаи

Отдельно предстоит определить: продлевает ли новое попадание текущий KO, что происходит при повторном KO сразу после подъёма, как сохранять таймер при переподключении/перезапуске, и как разрешать попадание и пробуждение на одной временной границе. Таймер 60 секунд не заменяет решения этих вопросов.

## 14. Бафы, дебафы, эффекты и оглушение

### 14.1. Приёмы, статусы и их эффекты

**Утверждено:** вводится общая система бафов и дебафов по образцу L2J. Рана представляется дебафом, который накладывает определённые эффекты.

Для дальнейшего проектирования различаем:

- **Приём/действие** — выполняемый боевой приём: например, удар топора. Он определяет попадание, прямой урон и возможные дополнительные последствия.
- **Баф/дебаф** — наложенный на персонажа статус, объединяющий один или несколько эффектов. Рана является одним из видов дебафов, а не отдельным типом урона.
- **Эффект** — конкретное воздействие статуса, например изменение характеристики, периодическое повреждение или запрет действий. Это примеры возможностей системы; набор эффектов конкретных ран ещё не утверждён.

Определение статуса и его активный экземпляр на конкретной цели следует различать при проектировании. Конкретные поля definitions, структуры компонентов и способы хранения пока не выбраны.

**Утверждено:** приём может накладывать несколько дебафов, например отдельный stun и отдельную рану. У каждого наложения есть фиксированный `chance` из definitions. Дебаф может объединять несколько эффектов: один успешный бросок накладывает весь дебаф и включает их вместе.

Текущая фаза включает два приёма топора: удар по области и усиленный удар по одной цели. Состояние `stunned` и механизм эффектов можно добавить уже на этой фазе. Оглушение относится к отдельному специальному приёму; обычные удары топора и стрелы не получают автоматического stun. Конкретный оглушающий приём ещё не выбран.

Кровотечение сохраняется как пример возможного эффекта для расширения системы. Его урон, периодичность, длительность, взаимодействие с бронёй и здоровьем, возможность убить и правила повторного наложения не утверждены. Несколько эффектов не вводят дополнительные типы урона: тип урона по-прежнему один.

### 14.2. Независимый фиксированный chance дебафа

**Утверждено:** для каждого дебафа на каждой задетой цели выполняется отдельная проверка его `chance`. Внутри одного дебафа дополнительных бросков на включение его составных эффектов нет.

- Если stun и рана — разные дебафы, у одной цели может наложиться stun и не наложиться рана; у другой — наоборот.
- Если одна рана-дебаф содержит снижение STR и кровотечение, успешное наложение включает оба эффекта вместе. Их конкретные величины и правила пока не выбраны.
- Не используется один общий бросок на весь список дебафов приёма.
- В AoE результат на одной цели не определяет результат на остальных.
- Шанс берётся непосредственно из definitions; STR, CON, уровень, Quality, броня, сопротивления и разница развития не пересчитывают его в выбранной модели.
- Шанс наложения stun и шанс снятия уже действующего stun уроном — разные проверки.

Конкретные шансы дебафов отдельных приёмов ещё не назначены. Выбран способ расчёта, а не готовая таблица баланса. Формат definitions, место хранения и единицы записи `chance`, структура runtime-данных остаются задачей дальнейшего проектирования.

Это уточняет раннюю формулировку обсуждения «независимый шанс каждого эффекта»: после введения составных статусов единицей вероятностного наложения выбран **дебаф целиком**, а независимость сохраняется между разными дебафами и разными целями.

### 14.3. Прерывание и отдельное состояние stunned

Пользователь принял разделение обычного попадания и отдельного эффекта оглушения.

| Воздействие | Замах топора | Натяжение/удержание лука |
|---|---|---|
| Обычное попадание, персонаж остаётся в сознании | Продолжается | Продолжается |
| Специальный эффект оглушения | Прерывается | Прерывается |
| Нокаут | Прерывается | Прерывается |
| Смерть | Прекращается | Прекращается |
| Команда движения самого игрока | Не отменяет, действует лимит движения | Отменяет натяжение |

Активное оглушение блокирует движение и выполнение действий. Успешное наложение прерывает текущий замах или натяжение; неудачная проверка `chance` сама по себе действие не прерывает. Уже начатый cooldown сохраняется.

Причина выбора: если каждое попадание сбивает действие, быстрые атаки или группа стрелков могут непрерывно мешать завершить медленную атаку. Выбранная модель позволяет выдержать попадание и ответить, пока персонаж не оглушён и не потерял сознание.

**Stun и KO остаются разными состояниями с независимыми сроками.** Истечение или снятие stun не завершает KO. Восстановление SHP не снимает stun и не будит раньше KO-дедлайна. Если действуют оба ограничения, возможность действовать возвращается только после завершения всех блокирующих состояний. Смерть имеет приоритет над ними.

### 14.4. Повторное оглушение

После успешной проверки нового эффекта:

```text
stunEndsAt = max(stunEndsAt, now + newStunDuration)
```

Правило сравнивает **моменты окончания**, а не исходные длительности эффектов:

- Если у текущего stun осталось 5 секунд, новый stun на 2 секунды не сокращает эти 5 секунд.
- Если осталось 2 секунды, новый stun на 5 секунд оставляет цель оглушённой ещё на 5 секунд от текущего момента.
- Длительности не складываются: во втором примере не получается 7 секунд.

Числа в примерах иллюстрируют правило и не задают длительность будущего приёма. При повторном применении сначала проверяется `chance` наложения дебафа stun; неуспех не обновляет дедлайн.

### 14.5. Снятие оглушения уроном

**Утверждено:** обычный входящий damage-вызов даёт отдельный **10% шанс** снять уже действующий stun.

- Проверка относится к одному событию обычного входящего урона.
- Разделение одного попадания на SHP- и HHP-части не создаёт два броска.
- Периодический урон (DoT) не вызывает эту проверку.
- Расход собственного HP как стоимости действия не вызывает эту проверку.
- Успешное снятие завершает только stun; KO, смерть и cooldown остаются под своими правилами.

Выбрана привязка к обычному damage-вызову. Дополнительное условие «сначала фактически потерять положительное количество HP» не утверждалось. При проектировании API нужно явно определить, какие отклонённые или нулевые вызовы вообще являются событиями входящего урона; не подменять этим открытым техническим вопросом выбранный шанс.

### 14.6. Порядок обработки попадания

**Утверждённый порядок:**

```text
попадание по геометрии
--> расчёт и применение урона
--> проверка 10% снятия старого stun при обычном damage-вызове
--> независимые проверки наложения новых дебафов
--> включение всех эффектов каждого успешно наложенного дебафа
```

Основной урон попадания обрабатывается **ровно один раз**. Под «новыми эффектами» в этой последовательности понимаются остальные последствия попадания, включая наложение дебафа-раны; повторного нанесения основного урона при обходе их списка нет. Будет ли сам урон представлен отдельным элементом в definitions, ещё не определено.

Проверка снятия относится к оглушению, существовавшему **до новых эффектов этого попадания**. Поэтому удар с эффектом stun не снимает собственный только что наложенный stun своим же уроном.

Если старый stun снялся, успешный новый эффект начинает свой срок от `now`: дедлайн уже удалённого эффекта не сохраняется, новый срок может закончиться раньше него. Если старый stun остался, успешный новый эффект использует правило максимального дедлайна из раздела 14.4. Если новый эффект не сработал, он не восстанавливает снятый старый stun.

Переходы здоровья из разделов 12–13 сохраняют приоритет: смертельный урон завершает жизнь персонажа, последующие эффекты не заменяют смерть на stun или KO и не возвращают возможность действовать.

### 14.7. Оставшиеся вопросы эффектов

Не определены конкретные оглушающие приёмы, их длительность и значения `chance`, взаимодействие оставшегося recovery с окончанием stun, а также допустимость новых эффектов по цели, уже находящейся в KO. Правила кровотечения и других будущих эффектов требуют отдельного обсуждения.

Способ повторного stun, независимость проверок разных дебафов, фиксированный `chance` целого дебафа и 10% снятия обычным уроном уже выбраны. Не возвращать их в список нерешённых вопросов. Новая шкала stagger, автоматический stun от большого урона, зависимое от характеристик сопротивление и защита от серии оглушений не приняты.

Для общей системы статусов остаются открытыми длительность и повторное наложение ран, совместимость разных статусов и правила суммирования их эффектов. Формулу продления stun и его снятие уроном нельзя автоматически распространить на все дебафы. Конкретные способы медицинского воздействия на них сейчас не обсуждаются.

### 14.8. Рана как дебаф: выбранная последовательность

```text
контакт удара
--> прямой урон SHP/HHP по выбранным формулам
--> проверка снятия старого stun обычным уроном
--> проверка chance наложения раны
--> при успехе на цели появляется дебаф-рана со своими эффектами
```

Это детализация общего порядка из раздела 14.6. Проверки выполняются для каждой задетой цели отдельно; смерть сохраняет приоритет. Значения `chance` и списки ран для двух начальных приёмов топора ещё не назначены.

Например, при `SHP = 100`, `HHP = 100`, `D = 20` и выбранном `alpha = 20%` прямое попадание оставляет `SHP = 80`, `HHP = 96`. При неуспешном наложении раны эти потери всё равно остаются. При успешном — дополнительно появляется дебаф и начинают действовать его эффекты. Числа примера, кроме выбранного `alpha`, не задают баланс предмета или приёма.

Отсутствие лечения в текущем scope не означает, что все раны уже решено делать бессрочными или что снятие любого дебафа автоматически восстанавливает HHP. Срок существования ран относится к контракту дебафов и ещё требует решения; последствия лечения будут определяться отдельно.

## 15. Что дали исследования других игр

Этот раздел сохраняет основания обсуждения. Механики источников отделены от принятых правил Origin.

### 15.1. Lineage 2: выполнение и повторное использование

В официальных материалах издателя различаются время применения и время повторного использования. В [Lindvior, 2013](https://eu.4gameforum.com/threads/11081/) они меняются отдельно. [Описание Sayha's Talisman, 2018](https://eu.4gameforum.com/threads/655325/) показывает общий cooldown для части эффектов на одном уровне, независимые на другом и фиксированный cooldown, не изменяемый бафами.

Вывод для Origin: длительность действия и его cooldown полезно разделять; совместный cooldown — отдельное правило, а не обязательное свойство любых похожих приёмов.

Принятые моменты старта cooldown топора/лука и их взаимодействие с recovery — собственные решения Origin. Исследование не установило единый универсальный момент старта cooldown для всех навыков и версий L2.

### 15.2. Дистанционный урон: Rust и New World

В обсуждении сравнивались игровые способы потери урона на расстоянии. [Rust Devblog 119, 21.07.2016](https://rust.facepunch.com/news/devblog-119) описывает изменения поведения снарядов и сопротивления, а [Devblog 120, 28.07.2016](https://rust.facepunch.com/news/devblog-120) — баланс дистанционного спада урона. В [New World: Season 1, 03.04.2023](https://www.newworld.com/en-us/game/releases/season-one-fellowship-and-fire?language-picker=true) присутствуют исправления расчёта дистанционного урона.

Это исторические примеры использования falloff как настраиваемой игровой механики, а не доказательство единой физически правильной формулы или актуальных чисел этих игр.

Схема Origin «30% без спада, затем до 20%» выбрана пользователем. Она не копируется как точная формула одной из перечисленных игр.

### 15.3. Haven & Hearth: таймер, защита и поражение

[Патч разработчиков от 20.04.2017](https://www.havenandhearth.com/forum/viewtopic.php?p=735097) описывает прекращение боевых отношений при KO, запрет новых, возможность ограбления, hearth/logout после 30 секунд и пробуждение ещё через 30. В том же патче база grievous damage отдельного удара ограничена MHP цели: пример `500 damage, 300 MHP, 30% grievous → 90 HHP`.

Это существенно отличается от принятого в Origin полного переноса превышения остатка SHP в HHP. Ограничение grievous через MHP не переносим в нашу формулу.

[Iced Bait, 07.11.2021](https://www.havenandhearth.com/forum/viewtopic.php?f=39&t=71874) добавил явный KO-диалог с возвращением домой по умолчанию; loftar уточнил, что обычные запреты travel/logout продолжают действовать. [Гайд игрока, 2022](https://www.havenandhearth.com/forum/viewtopic.php?t=72160) уточняет подъём на месте с 1 SHP. Это вторичный источник для данного уточнения. Поздней опубликованной замены схемы 30+30 в проверенных материалах не найдено; серверный код таймера не проверялся.

### 15.4. Haven & Hearth: почему KO protection не гарантирует жизнь

[An Arrow to the Knee, 02.02.2020](https://www.havenandhearth.com/forum/viewtopic.php?f=39&t=67070) различает:

- Rage разрешает агрессию и само по себе не отключает защиту.
- Murder позволяет атаковать лежащего, уже не имеющего защиты.
- Murderous Rage снимает собственную KO protection на 24 реальных часа, усиливает grievous damage, сохраняет бой при KO и блокирует hearth/logout в этом состоянии.
- Некоторые животные продолжают нападение на лежащего, получая шанс прекратить его после очередного удара.
- Сам удар, вызывающий KO, может оказаться смертельным. Защита уже лежащего не отменяет нанесённое повреждение.

Это не означает, что Murder позволяет игнорировать защиту любого персонажа. Актуальность снятия защиты через Murderous Rage подтверждена [исправлением от 21.06.2025](https://www.havenandhearth.com/forum/viewtopic.php?p=959565).

По [игровой вики Concussion](https://ringofbrodgar.com/wiki/Concussion), KO также даёт сотрясение на 5–20% MHP. Ни этот случайный дополнительный урон, ни защита лежащего, ни специальные PvP-навыки H&H для Origin не приняты.

Не удалось отдельно подтвердить поведение уже летящей стрелы по защищённому лежащему в H&H. Формулировка о прекращении combat relations не доказывает универсальную невосприимчивость ко всем источникам урона.

### 15.5. Уточнения к старой заметке knocked_dead.md

Не использовать её как единственный источник без следующих поправок:

- Утверждение «публичных таймингов нет» опровергается патчем 2017 года.
- «Нельзя убить с одного нокаута» — неверное обобщение: смертельным может стать удар, вызывающий первый KO после предыдущих повреждений. Число попаданий и число нокаутов — разные вещи.
- Отсутствие специальных строк в просмотренных Java-файлах клиента не доказывает отсутствие KO-интерфейса: официальный клиент поддерживает серверное создание UI и загрузку кода виджетов из ресурсов.
- Эвристики стороннего клиента Hurricane по позам и ресурсу `knockchirp` не являются гарантированным серверным контрактом.
- Общие механизмы следования/переноса объектов не доказывают возможность переносить живого игрока в KO.

Первичные технические источники: [RemoteUI.java](https://github.com/dolda2000/hafen-client/blob/master/src/haven/RemoteUI.java), [Widget.java](https://github.com/dolda2000/hafen-client/blob/master/src/haven/Widget.java). Старую заметку в рамках фиксации этого документа не исправляли.

### 15.6. L2J: определения приёмов, эффекты и оглушение

Исследован предоставленный пользователем клон `/Users/mark/projects/l2j-server-game`: ветка `develop`, commit `abfde0490ac52a2106e884b7242c0276c44cdf76`, версия проекта `2.6.3.0-SNAPSHOT`. Это серверный эмулятор L2J для High Five Part 5, а не исходный сервер NCSoft и не доказательство поведения всех версий Lineage 2.

Определения навыков и обработчики эффектов дополнительно проверены в отдельном официальном репозитории `l2j-server-datapack`, commit `3ca488dd2bd0bfaca43e378886a3c2e37968153a`. В предоставленном клоне game-сервера этого datapack нет; для продолжения исследования искать XML только в game-репозитории недостаточно.

**Устройство:**

- `DocumentEngine` загружает `data/stats/skills`; `DocumentSkill` и `DocumentBase` разбирают XML-описания и несколько элементов `<effect>`.
- `Skill` хранит `Map<EffectScope, List<AbstractEffect>>`: список эффектов разделён по контекстам применения, включая обычные эффекты, self, start/end и PvP/PvE.
- `EffectHandler` связывает имя эффекта с обработчиком. Конкретный обработчик задаёт поведение эффекта.
- `BuffInfo` хранит состояние конкретного применения: источник, цель, skill, эффекты, длительность и задачи жизненного цикла. Это отделено от определения навыка.

Для Origin принята общая система бафов/дебафов с несколькими эффектами по образцу L2J. Концептуально полезно отделять определение от состояния конкретного применения. Копирование Java-классов, XML-формата, всех scope и всех частных правил L2J не утверждено. Точки входа для повторного чтения: [Skill.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/skills/Skill.java) и [BuffInfo.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/skills/BuffInfo.java).

**Примеры definitions:**

- `Stun Attack` (100): `PhysicalAttack` и `Stun` в одном приёме; `activateRate = 50`, `abnormalTime = 9`, `abnormalType = STUN`, `basicProperty = CON`, `trait = SHOCK`.
- `Stun Shot` (101): `PhysicalAttack`, `TargetCancel` с параметром `chance = 40` и `Stun`.
- `Shield Stun` (92): пример приёма с эффектом `Stun` без `PhysicalAttack`.
- `Bleed` (96): отдельный периодический эффект `TickHp` и модификация скорости передвижения.

Источники: [навыки 100–199](https://bitbucket.org/l2jserver/l2j-server-datapack/src/3ca488dd2bd0bfaca43e378886a3c2e37968153a/src/main/resources/data/stats/skills/00100-00199.xml), [навыки 0–99](https://bitbucket.org/l2jserver/l2j-server-datapack/src/3ca488dd2bd0bfaca43e378886a3c2e37968153a/src/main/resources/data/stats/skills/00000-00099.xml). Эти числа принадлежат исследованному datapack, не таблице баланса Origin. `activateRate` навыка L2J не равен гарантированной итоговой вероятности в процентах.

**Что отличается от Origin:**

- В обычной ветке применения L2J выполняет общую проверку `Formulas.calcEffectSuccess` для длительных (`continuous`) эффектов навыка по цели. Затем отдельные эффекты проходят `canStart`. Есть специальные ветки, в частности toggle и self. В Origin один приём может отдельно проверять несколько дебафов; каждый из них при успешном наложении включает весь свой набор эффектов.
- Для мгновенных (`instant`) эффектов вызывается индивидуальный `calcSuccess` перед `onStart`. Базовая реализация возвращает успех, поэтому сам вызов ещё не означает случайный бросок.
- Итоговая вероятность длительного эффекта L2J зависит от параметров навыка, уровней и характеристик/сопротивлений; есть ветки гарантированного успеха. В Origin выбран фиксированный `chance` без такого пересчёта.
- При повторном наложении L2J сравнивает `abnormalType` и `abnormalLvl`; равный или более сильный эффект обычно заменяет прежний, более слабый отклоняется, существуют исключения. Это не правило максимального дедлайна Origin и не гарантия сохранения более долгого остатка.

Для проверки формул и замены: `model/stats/Formulas.java`, `model/CharEffectList.java` в указанном снимке game-сервера; [CharEffectList.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/CharEffectList.java).

**Stun и снятие уроном:** обработчик [Stun.java](https://bitbucket.org/l2jserver/l2j-server-datapack/src/3ca488dd2bd0bfaca43e378886a3c2e37968153a/src/main/java/com/l2jserver/datapack/handlers/effecthandlers/custom/Stun.java) устанавливает состояние `STUNNED`; `L2Character.startStunning()` прекращает атаку, cast и движение. В `CharStatus` и `PcStatus` проверка `Rnd.get(10) == 0` снимает оглушение при обычном входящем damage-вызове, исключая DoT и HP consumption. Она не требует в своём блоке положительного фактического урона здоровью: [CharStatus.java](https://bitbucket.org/l2jserver/l2j-server-game/src/abfde0490ac52a2106e884b7242c0276c44cdf76/src/main/java/com/l2jserver/gameserver/model/actor/status/CharStatus.java).

Из этого исследования для Origin приняты общая модель бафов/дебафов с несколькими эффектами, отдельное состояние stun и 10% снятия stun обычным damage-вызовом. Независимые фиксированные вероятности разных дебафов, максимум дедлайнов stun и порядок «урон/снятие старого stun → новые эффекты» — собственные решения Origin. Правила кровотечения L2J, включая различие смертельных и несмертельных периодических обработчиков, автоматически не переносим.

## 16. Текущее состояние проекта и точки интеграции

Снимок по состоянию на дату документа. Перед реализацией перепроверить код: рабочая копия развивается параллельно.

### 16.1. Здоровье и смерть

- `internal/entityhealth/health.go`: расчёт MHP, clamp SHP/HHP, применение раздельно переданных soft/hard damage, формула SHP-регенерации.
- `ApplyDamage` пока самостоятельно не вычисляет ни `alpha`, ни overflow: получает две уже рассчитанные величины.
- Проверенные источники повреждений пока относятся к голоду и административным командам. Их правила не следует автоматически менять при подключении формулы боевого попадания.
- `internal/game/player_death_system.go`: голод, SHP-регенерация, обнаружение KO и запуск перманентной смерти.
- `internal/ecs/components/entity_health.go`: текущее состояние здоровья и KO.
- `internal/game/shard.go`: обработка перманентной смерти и превращение игрока в объект трупа; персонаж помечается удалённым в БД.

Сейчас восстановление любого положительного SHP может снять KO. Поле `KOUntilTick`, несмотря на название, записывается как момент начала KO, а не утверждённый будущий дедлайн пробуждения.

Новое правило требует независимого состояния KO и дедлайна. Нельзя ограничиться переименованием поля или оставить прежнюю проверку «SHP > 0 → встать».

Текущий код использует `StateStunned` для обездвиживания при KO и снимает его при положительном SHP. Самостоятельного временного stun с собственной длительностью нет; его потребуется отделить от KO.

Сейчас KO очищает ряд pending-действий, циклические действия и crafting. Полноту отмены будущего боевого действия и `ActiveGameAction` нужно проверить отдельно.

### 16.2. Регенерация

Текущая SHP-регенерация:

| Energy | Прибавка за интервал |
|---|---:|
| >= 900 | 0.2% MHP |
| >= 800 и < 900 | 0.1% MHP |
| < 800 | 0 |

Интервал по умолчанию — 100 ticks; при 10 Hz это 10 секунд. Это глобальное расписание. Урон его не сдвигает; запрета регенерации в бою и отдельной задержки после попадания пока нет.

HHP-лечение и полноценная система ран в проверенном игровом цикле не реализованы. Административные команды здоровья не являются игровой медициной.

### 16.3. Stamina

- `internal/entitystats/stamina.go`: максимум сейчас `1000 × sqrt(CON)`.
- `internal/entitystats/regen.go`: восстановление 5 stamina за 1 Energy.
- Интервал восстановления по умолчанию — 50 ticks, то есть 5 секунд при 10 Hz.
- Списание stamina переносит срок её следующей регенерации; непрерывный положительный расход может удерживать восстановление от срабатывания.
- `internal/entitystats/movement.go`: пороги режимов движения и отдельные helpers длительных действий.

Не смешивать два существующих контракта: часть long-action helpers требует резерва 10%, а generic ActionService уже допускает точную оплату доступной stamina. Боевой расход до нуля не требует автоматически менять экономику всех небоевых действий.

### 16.4. Действия, движение и прицеливание

- [game-actions/spec.md](../../openspec/specs/game-actions/spec.md): generic actions, выбор цели, отмена и успешная оплата.
- `internal/game/action_service.go`: текущая реализация generic actions.
- `internal/ecs/systems/directional_movement.go`: взаимодействие WASD с активными действиями.
- `internal/ecs/systems/movement.go` и `internal/entitystats/movement.go`: движение и ограничения.

Существующие правила generic actions позволяют отмену и смену действия, а списание привязано к успешному завершению/циклу. WASD отменяет `ActiveGameAction` в любой фазе, кроме `selecting`, включая подход к цели. Это не совпадает с обязательным замахом топора, оплатой в начале предложенной боевой модели и разрешённым Crawl.

Будущий боевой жизненный цикл должен явно выразить разные политики: топор принимает движение без отмены, лук отменяется движением, начатый cooldown переживает прерывание.

Направление персонажа сейчас в основном связано с движением. Для независимого прицеливания, свободного aim лука и фиксации сектора топора потребуется явное разделение направления движения и атаки.

### 16.5. Чего ещё нет в готовом виде

В проверенном коде нет законченных боевых атак по описанным правилам, нужных таблиц weapon damage/armor и полной системы стрел. Имеющиеся компоненты коллизий, действий и анимаций — точки опоры, а не подтверждение реализации нового дизайна.

Рекомендуемый подход реализации: сервер проверяет возможность начала, фиксирует параметры действия, ведёт таймеры, рассчитывает контакт, броню и здоровье; клиент отображает предсказуемое прицеливание и полученное состояние. Форматы сообщений и конкретное разделение систем ещё не выбраны.

### 16.6. Геометрия и эффекты

`internal/ecs/components/collider.go` описывает прямоугольный collider через `HalfWidth` и `HalfHeight`. Для выбранного удара нужен контакт сектора с фактическим collider, а не только проверка центра объекта.

`internal/core/spatial.go` хранит объекты по позиции центра; `QueryRadius`/`QueryAABB` дают предварительный набор из пространственных ячеек. Поэтому будущий поиск кандидатов должен учитывать размеры collider: крупная цель с центром вне сектора может пересекать его краем. После предварительного отбора нужна точная проверка пересечения. Проверку стен в этот путь добавлять не следует.

Определения бафов/дебафов, их эффектов и runtime-состояние применения предстоит спроектировать отдельно. Принятый контракт уже требует независимых проверок по паре «дебаф–цель», совместного включения эффектов успешного дебафа, отдельного дедлайна stun и единственной проверки его снятия на damage-событие. Два обновления здоровья — SHP и HHP — не должны превращать один удар в два события для снятия stun.

## 18. Отклонённые варианты и опасные неверные интерпретации

- Жёсткий общий cap развития ради равенства новичка и ветерана — отвергнут.
- Гарантия «новичок обязательно переживает первый удар» — не принималась.
- L50 / экспоненциальный спад стрелы — заменён принятой кусочно-линейной кривой.
- Реальная потеря скорости стрелы — не входит в выбранный полёт с постоянной скоростью.
- Рост времени полного натяжения вместе с STR — не выбран; время задаёт тип лука.
- Движение Crawl во время натяжения лука — пользователь выбрал стоять.
- Предварительный target lock для одиночного топора — не соответствует выбору цели в момент удара.
- Более узкий сектор одиночного топора — пользователь оставил те же 90°.
- Проверка попадания топора только по центру цели — заменена пересечением collider с сектором.
- Выбор ближайшей цели по центру или части collider вне сектора — не соответствует принятой метрике.
- Заслонение удара топора стенами, объектами или другими целями — пользователь выбрал отсутствие проверки преград для обоих приёмов.
- Добровольная отмена начатого замаха — отвергнута.
- Отмена обычным попаданием / автоматический hit-stun — отвергнута; отдельный успешный эффект stun может прервать действие.
- Один общий бросок на все дебафы приёма или все цели AoE — заменён независимыми проверками.
- Отдельные броски на внутренние эффекты одного дебафа — после уточнения выбрано совместное включение всего дебафа по одному `chance`.
- Пересчёт chance дебафа через STR, CON, Quality или сопротивления по аналогии с L2J — не входит в выбранную модель.
- Сложение длительностей stun или сокращение ещё действующего stun более коротким наложением — не соответствует максимуму дедлайнов.
- Гарантированное снятие stun каждым ударом и полностью неснимаемый уроном stun — не выбраны; утверждён отдельный шанс 10%.
- Две проверки снятия stun на SHP- и HHP-части одного damage-события — не соответствуют выбранному правилу.
- Общее состояние/таймер stun и KO — прямо отвергнуто.
- Обязательный резерв stamina для боевого действия — отвергнут.
- Исключения friendly fire для союзников — прямо отвергнуты.
- Последовательное сложение cooldown после recovery — не соответствует принятой параллельности.
- Пробуждение сразу после положительного тика SHP-регенерации — заменено независимым KO.
- KO protection, Murderous Rage, Concussion и grievous cap H&H — исследованы, но не приняты для Origin.
- Вычисление HHP только из суммы активных ран по аналогии с H&H — не соответствует выбранному прямому HHP-урону и отдельной вероятности раны.
- Самостоятельная HHP-регенерация — пользователь выбрал восстановление только лечением.
- Условные `B = 12`, `A = 12`, коэффициент усиления 1.5 и другие демонстрационные числа — не утверждённый баланс. `alpha = 20%` позднее отдельно выбрана как начальный настраиваемый параметр.

## 19. Что обсуждать дальше

Геометрия обоих приёмов топора, `alpha = 20%`, общая модель бафов/дебафов и один chance на дебаф целиком уже выбраны. Сейчас следует уточнять контракт дебафов и баланс боя. Механика лечения по прямому указанию пользователя исключена из этого обсуждения. Обычное попадание по-прежнему не прерывает атаку; прервать её может отдельный успешный эффект stun, KO или смерть.

Приоритетные открытые решения:

1. **Бафы, дебафы и раны:** длительность, повторное наложение, совместимость, суммирование эффектов; конкретные раны и их эффекты. Один chance на весь дебаф и прямой HHP-урон уже выбраны. Лечение в эти вопросы не включать.
2. **Первичная таблица баланса:** базовые оружие/броня, длительности замаха/recovery/cooldown, дальности и расходы stamina. Проверять их совместно, а не изолированными множителями.
3. **Точная модель лука:** `Fmax(STR, bow)`, пределы предмета, минимум натяжения, вклад стрелы, размеры collider и список препятствий.
4. **Оставшиеся детали геометрии топора:** дальность, равные расстояния, касание границ и численная точность. Пересечение collider, метрика ближайшей цели и отсутствие преград уже утверждены.
5. **Завершение контракта KO:** регенерация внутри KO, повторные попадания/падения, персистентность таймера, будущий перенос к Hearth Fire.
6. **Эффекты и будущие спецприёмы:** конкретный оглушающий приём, его длительность и `chance`, остаток recovery после прерывания, допустимость эффектов по цели в KO, классификация нулевых/отклонённых damage-вызовов и небоевых источников. Формат definitions/runtime ещё не выбран; повторный stun и снятие уроном уже определены.
7. **Кровотечение и другие эффекты:** собственные правила урона, длительности, повторного применения и снятия. Упоминание в качестве примера не делает их утверждёнными приёмами текущей фазы.

Для текущей фазы пользователь назвал два удара топора, возможность уже заложить состояние stunned, а затем выбрал общую систему бафов/дебафов и рану как дебаф от попадания. Конкретный станящий приём не является обязательным дополнением к этим двум ударам. Согласованный дизайн лука сохраняется в документе для дальнейшей работы. Способы лечения будут предметом отдельного обсуждения.

Ещё не обсуждались как принятые механики: активный блок, парирование, перекат, критические удары, headshots, износ брони, пробитие отдельных слотов, PvP-флаги, отдельные правила AI добивания, получение/возврат выпущенных стрел. Не добавлять их как якобы договорённые.

## 20. Сценарии для проверки будущей реализации и баланса

Это список проверок дизайна; тесты боёвки пока не написаны. Сценарии, зависящие от рабочей модели или открытых деталей, условны и не повышают статус этих решений. В частности, проверки стоимости используют модель раздела 10.2, а проверка роста SHP внутри KO нужна, если такой рост будет разрешён.

1. Цель уходит из сектора до удара: происходит промах, стоимость и cooldown не возвращаются, recovery сохраняется.
2. Атакующий смещается на Crawl: сектор переносится вместе с ним, но не поворачивается после начала замаха.
3. Две цели меняются местами во время замаха: одиночный приём выбирает ближайшую в момент удара.
4. В секторе союзник и противник: социальная принадлежность не меняет отбор и урон.
5. AoE задевает несколько целей: по каждой одно попадание, урон не делится на число целей, броня считается отдельно.
6. Попадание по атакующему не вызывает KO, смерть или отдельный эффект stun: обычный замах/натяжение продолжается.
7. Специальное оглушение прерывает замах: попадание прерванного удара не возникает, начатый cooldown сохраняется.
8. Игрок чередует два приёма: следующий доступен после recovery, каждый соблюдает собственный cooldown.
9. Ресурса ровно на старт: stamina может стать нулём; оплаченный топор не отменяется только из-за нуля.
10. Движение отменяет лук: невыпущенный снаряд не появляется; обычные ограничения движения остаются.
11. Быстрая стрела пересекает тонкую цель за один шаг: контакт не теряется.
12. На траектории несколько препятствий: обрабатывается ближайшее; неблокирующие объекты пропускают стрелу.
13. Урон стрелы на 30%, 65% и 100% её дальности: 100%, 60% и 20% до брони.
14. Два разных натяжения: спад считается по собственной дальности каждого выстрела.
15. Попадание пересекает остаток SHP: overflow полностью идёт в HHP без повторного начисления `alpha`.
16. Попадание сразу обнуляет HHP: возникает смерть, а не временный защищённый KO.
17. Регенерация увеличивает SHP раньше 60 секунд KO: персонаж не просыпается досрочно.
18. Живой голодный персонаж достигает конца KO: отсутствие естественной регенерации не мешает подъёму с минимальным SHP.
19. Лежащий получает удар до будущего hearth: получает HHP-урон и может умереть.
20. Большая разница STR/Quality/CON: формулы сохраняют пользу прогрессии и не вводят скрытую нормализацию ради новичка.
21. Полное и частичное натяжение на близкой дистанции: сравнить не только урон попадания, но и урон в секунду с учётом полного цикла и стоимости.
22. Центр большой цели вне угла или дальности, но collider пересекает сектор: цель попадает в общий набор кандидатов обоих ударов.
23. Между атакующим и целью стена: пересечение collider с сектором всё равно допускает попадание обоих ударов топора. Правила блокирования стрел при этом сохраняются.
24. Одна цель находится перед другой: AoE поражает обе по одному разу, передняя не заслоняет заднюю.
25. Центр первой цели ближе, но пересекающая сектор часть collider второй ближе к атакующему: одиночный удар выбирает вторую. Близкая часть collider вне сектора не даёт преимущества при выборе.
26. Приём может наложить два дебафа и задевает несколько целей: каждый дебаф проверяется отдельно на каждой цели; неуспех одного не запрещает другой. Внутренние эффекты успешно наложенного дебафа включаются вместе.
27. У ещё действующего stun осталось 5 секунд, новый успешный stun длится 2 секунды: остаётся прежний дедлайн. При остатке 2 и новом сроке 5 секунд дедлайн становится `now + 5`, а не `now + 7`.
28. Обычное попадание снимает SHP и HHP: проверка 10% снятия старого stun выполняется один раз на damage-событие. DoT и собственная стоимость HP её не вызывают.
29. Удар наносит урон и успешно накладывает новый stun: его damage не выполняет проверку снятия только что наложенного эффекта. Если старый stun снят этим попаданием, его дедлайн не участвует в новом наложении.
30. У персонажа одновременно stun и KO: снятие stun не будит его; пробуждение из KO не снимает ещё действующий stun. SHP-регенерация не заменяет ни один таймер.
31. Смертельное попадание имеет дополнительные эффекты: смерть не заменяется на временный stun/KO, действия персонажа не возобновляются.
32. Рана не выпала при попадании: рассчитанное уменьшение SHP/HHP сохраняется, отсутствие дебафа не отменяет повреждение здоровья.
33. Рана выпала: прямой урон учитывается один раз, затем дебаф включает свои эффекты; второй копии основного урона нет.
34. У живого персонажа не хватает HHP, активного лечения нет: обычное течение времени и SHP-регенерация не восстанавливают HHP.

Для численного прогона полезно сравнить хотя бы: равных персонажей; ветерана против новичка; тяжёлую броню против слабых и сильных ударов; полное и частичное натяжение на разных дистанциях; несколько последовательных боёв без полного лечения HHP.
