# Сетевой протокол двух ударов топора

Дата фиксации: 2026-10-03.

Дата внесения protobuf-схемы: 2026-10-04.

Статус на 2026-10-08: серверные `axe_sweep` и `axe_strike` подключены через общий melee handler. Направленный ввод, definitions, геометрия, получение урона существами/объектами и публикация `attack_result` используют приведённый контракт. Клиент проверяет и подавляет дубли результатов, затем показывает [красные цифры урона](damage_numbers.md), без изменения здоровья и создания объектов. Другие hit FX и новые animation assets в эту реализацию не входят.

Документ определяет минимальные изменения production-протокола для двух ударов топора: по области и по одной ближайшей цели. Основа игровых правил — [combat_final.md](combat_final.md); порядок дальнейшего подключения механик — [combat_phases.md](combat_phases.md).

Последние уточнения пользователя имеют приоритет над прежним планом фаз: полигон и тестовые объекты не создаются; клиент показывает анимацию удара, без отдельного отображения замаха и recovery; углы в definitions задаются в градусах и при загрузке переводятся в радианы. Протокол здоровья, статусов, лука и выхода из боя в этот документ не входит.

## Состав изменений

| Место | Изменение | Необходимость |
|---|---|---|
| `C2S_ActivateAction` | `aim_angle = 2`, `stream_epoch = 3` | Передать выбранное направление вместе с конкретным действием и исключить исполнение в устаревшем мире |
| `ActionDefinition` | `ActionSector sector = 12`; значение `target_kind = "direction"` | Отобразить сектор из серверных параметров и определить направленный способ ввода |
| `CharacterActionAnimationState` | `facing_angle = 9` | Сохранить направление видимого удара при движении персонажа |
| `ServerMessage.payload` | `S2C_AttackResult attack_result = 52` | Сообщить фактические попадания или промах после серверной проверки |

Новый самостоятельный пакет только один — `S2C_AttackResult`. `ActionSector` и `AttackHit` являются вложенными структурами. Нового варианта `ClientMessage.payload` нет.

## Единицы углов

Авторские definitions хранят углы в градусах. Loader проверяет значения и один раз переводит их в радианы при построении runtime definitions. Геометрические расчёты, состояние сервера, сетевые сообщения и расчёты клиента используют радианы. Полученное из протокола значение повторно из градусов не переводится.

Для стартового топора полная ширина сектора в definitions равна `90`, а после загрузки — `π / 2`. Дальность равна `18` мировым единицам. Полная ширина отличается от отклонения относительно направления: сектор занимает по `π / 4` с каждой стороны.

Для новых полей направления действуют следующие правила:

- `0` означает направление мировой оси `+X`; положительный угол поворачивает к `+Y`.
- Отправитель нормализует направление в `[0, 2π)`.
- Получатель отклоняет `NaN` и бесконечности, затем нормализует конечное направление. Нормализация после декодирования учитывает округление `float` около границы полного оборота.
- Ширина сектора конечна и положительна, не превышает полный оборот. Ширину не нормализуют как направление: полный оборот не должен превращаться в нулевой сектор.
- В protobuf используется `float`; вычисления сервера выполняются в `float64`, клиента — в `number`. Нормализация направления не означает округления до целых градусов.
- Направление в мире и экранный угол различаются из-за изометрической проекции. Клиент проецирует мировой вектор направления; единицей обоих углов остаётся радиан.

Существующий `Position.heading` уже передаёт радианы. Текущее хранение heading в БД в целых градусах остаётся существующим адаптером сохранения и загрузки; этот протокол не требует миграции БД.

## Запрос начала удара

```protobuf
message C2S_ActivateAction {
  string action_id = 1;
  optional float aim_angle = 2; // Мировое направление в радианах.
  uint32 stream_epoch = 3;
}
```

Для действия с `target_kind = "direction"` клиент выбирает приём через Actions или hotbar и локально показывает сектор. Движение указателя не отправляет сообщения. Подтверждение отправляет один `C2S_ActivateAction` с ID приёма, выбранным углом и текущим epoch. Этот ввод не должен дополнительно отправлять обычный `MapClick`.

Направленный запрос самодостаточен: ему не нужна ранее подтверждённая сервером фаза `selecting`. Отмена локального прицеливания также не требует сетевой команды. Локальное прицеливание не является разрешением начать удар.

Для направленного действия наличие `aim_angle` обязательно. Значение `0` является допустимым направлением, поэтому поле имеет presence через `optional`. `stream_epoch` должен быть ненулевым и совпадать с текущим миром активного соединения. При обработке очереди сервер повторно проверяет принадлежность команды текущему соединению и миру.

Сервер проверяет существование приёма, экипировку, stamina, cooldown и ограничения текущего действия. После успешной проверки он фиксирует направление и начинает обычный timed action с progressbar; стоимость и cooldown при старте не списываются. На 100% сервер повторно проверяет состояние, получает текущие STR/оружие/броню, рассчитывает весь набор попаданий и резервирует admission летальных объектов. Только после успешной подготовки списываются stamina и cooldown, включая промах; затем применяются все подготовленные результаты. Отказ до commit и отмена незавершённого действия не наносят урон и ничего не списывают; причина передаётся через существующий mini-alert.

У запроса нет ID цели, позиции атакующего, дальности, урона или времени попадания. Эти значения и выбор поражённых целей определяет сервер. Направление фиксируется при принятом старте; положение сектора следует за фактической позицией атакующего.

Для существующих ненаправленных действий сохраняется прежний запрос без `aim_angle`; добавление нового поля не меняет их способ выбора цели. Поле направления у ненаправленного действия считается некорректным запросом.

Идентификатор запроса — существующий `ClientMessage.sequence` в пределах соединения. Повтор той же команды сохраняет sequence; новый sequence означает новую попытку, которая снова проходит обычные проверки. Новые `request_id`, `request_revision` и `selection_generation` не вводятся.

Повторные и устаревшие команды должны отбрасываться перед игровыми побочными эффектами, включая дубли, уже находящиеся в одной очереди. Текущей проверки только при enqueue недостаточно для этой гарантии. Усиление обработки и корректное сравнение sequence при переполнении относятся к реализации существующего механизма, а не к новым полям протокола. Клиент не переносит незавершённые попытки в новую сессию.

## Параметры сектора в каталоге

```protobuf
message ActionSector {
  float range = 1;        // Мировые единицы.
  float sector_angle = 2; // Полная ширина в радианах.
}

// Добавление в существующий ActionDefinition:
// ActionSector sector = 12;
```

Оба приёма имеют `target_kind = "direction"` и присутствующий `sector` с дальностью `18` и шириной `π / 2`. Для них отсутствие геометрии или некорректные числа являются ошибкой definitions. У прочих действий блок отсутствует.

Каталог передаёт геометрию предпросмотра после преобразования definitions в радианы. Клиент не содержит вторую авторскую копию этих параметров. Общий загрузчик может использовать одни параметры оружия для обоих приёмов; конкретная схема хранения definitions этим документом не задаётся.

В текущем объёме используется стартовый топор с одинаковой дальностью двух приёмов. Персональная геометрия от разных видов оружия не подменяется фиктивной готовностью статического каталога: её доставка потребует отдельного уточнения при появлении таких предметов.

Существующие `stamina` и `cooldown_ms` сохраняются. Клиенту не передаются боевые формулы, параметры выбора ближайшей цели или авторитетный набор объектов внутри сектора.

## Анимация удара

```protobuf
message CharacterActionAnimationState {
  string generation = 1;
  uint64 revision = 2;
  string animation_key = 3;
  uint32 total_ticks = 4;
  uint32 elapsed_ticks = 5;
  double tick_duration_ms = 6;
  int64 server_time_ms = 7;
  Position target_position = 8;
  optional float facing_angle = 9; // Мировое направление в радианах.
}
```

Единственное новое поле — `facing_angle`. Для удара сервер передаёт принятый угол; клиент не меняет его при движении персонажа или указателя. Поля `facing_angle` и `target_position` одновременно не передаются. Ненаправленные действия могут продолжать использовать существующее наведение на `target_position`.

`animation_key` выбирается через существующие definitions анимаций, если для приёма есть binding. Новые клипы, bindings топора и hit FX этим изменением не добавляются. Клиент использует существующую серверную шкалу воспроизведения; завершение timed action очищает её. В стартовом пресете выполнение занимает 6 тиков (`0.6 с` при 10 Hz). Отдельной recovery-фазы, её индикатора и таймера нет.

Существующие generation, revision, elapsed ticks и серверное время сохраняют свои правила. Публичное обновление получают исполнитель и текущие наблюдатели; `ObjectSpawn.action_animation` содержит тот же snapshot. Поздний наблюдатель присоединяется к текущему месту доступной анимации; после окончания действия состояние пустое. Дубликат состояния не перезапускает клип.

При прерывании удара сервер также очищает анимацию. Клиентская анимация, её последний кадр и callbacks не определяют попадание и не разрешают следующую атаку.

`windup_ticks`, отдельные сроки recovery и новая публичная структура боевого execution не вводятся.

## Занятость игрока и cooldown

Существующий `S2C_ActionStateChanged` используется без новых полей и без новых значений `phase`:

- При принятом старте сервер отправляет `action_id`, `phase = "executing"` и актуальный список cooldown.
- `executing` сохраняется до завершения длительности `execution.ticks`.
- При завершении сервер отправляет `phase = "idle"` и пустой `action_id`; начатый в момент completion cooldown остаётся в списке.
- Отмена до completion, в том числе принятое движение, снимает занятость без урона, stamina и нового cooldown. Уже существующие cooldown других завершённых действий сохраняются.

Сервер проверяет допустимость каждого нового действия. Изменившиеся до completion оружие и Quality перечитываются; исчезновение требуемой экипировки отменяет выполнение. KO, лежание и stun запрещают направленные действия. Завершение клиентской анимации не разрешает серверный удар.

У двух приёмов независимые cooldown. Их сроки передаются уже существующими `ActionCooldown.started_at_ms` и `expires_at_ms`. Stamina передаётся через `S2C_PlayerStats`. Для этих состояний новые пакеты не нужны.

## Результат удара

```protobuf
message AttackHit {
  uint64 target_id = 1;
  double damage = 2;
}

message S2C_AttackResult {
  uint32 stream_epoch = 1;
  uint64 event_id = 2;
  uint64 attacker_id = 3;
  repeated AttackHit hits = 4;
}

// Добавление в существующий ServerMessage.payload:
// S2C_AttackResult attack_result = 52;
```

Сервер создаёт один результат после успешного commit завершённого приёма. Пустой `hits` означает состоявшийся удар с промахом. У одиночного приёма не более одной записи; у удара по области каждая задетая цель указана ровно один раз, максимум 512. Атакующий исключён по generational handle и EntityID до геометрии и выбора ближайшей цели.

Сектор проверяется по актуальным collider bounds через пространственный индекс. Максимум работы — 1024 cell visits и 4096 raw collider membership visits до дедупликации, включая повторные memberships и fallback traversal; контактный buffer вмещает 4096 записей. Переполнение лимита, повреждённое здоровье/экипировка или отказ destruction admission отклоняют весь completion без частичного урона, оплаты и результата. Допустимые контакты упорядочены по расстоянию до задетой части collider и затем EntityID; предметы без здоровья, dropped items, мёртвые и pending destruction цели не выбираются.

`damage` — конечный рассчитанный `D` после брони, до распределения по модели здоровья и ограничения оставшимся запасом цели. Значение конечное, неотрицательное, с дробной точностью. Оно не означает отдельно потерю SHP, HHP или фактический остаток HP. Нулевой урон не превращает геометрическое попадание в промах.

`event_id` — ненулевой серверный ID разрешения удара, монотонно выделяемый общей для всех shard последовательностью одного server instance. Переполнение отклоняется; ID не переиспользуются. Неудачная подготовка после выделения ID может оставить пропуск. Копии одного события для разных получателей и повторная доставка сохраняют ID. В текущем потоке соединения сервер отправляет события в возрастающем порядке; ID независим от клиентского sequence и анимации. Значения `uint64` на клиенте обрабатываются без потери точности.

Клиент хранит один highwater `event_id` для текущего `stream_epoch`; сообщения с другим epoch, нулевым/некорректным ID или ID не выше принятого отклоняются. Он проверяет полный список до обновления highwater: максимум 512 записей, уникальные ненулевые target IDs без атакующего, конечный неотрицательный damage. Некорректное сообщение не расходует ID. Highwater сбрасывается при смене мира, leave, disconnect и начале новой сессии; payload после обработки не сохраняется.

Результат получают атакующий и текущие наблюдатели атакующего через обратный visibility index, без дублирования получателя. Для каждого соединения проверяются текущие персонаж, layer, world attachment и ненулевой epoch; packet содержит epoch именно этого соединения. Передаётся полный список попаданий события, включая неизвестные наблюдателю target IDs: его нельзя фильтровать до пустого списка и превратить попадание в промах. Неизвестный ID не создаёт объект. Сериализация синхронно создаёт собственные bytes до очистки scratch buffers; асинхронная отправка не получает изменяемые ECS/protobuf buffers. Результат не переигрывается при последующем входе в область видимости и не является snapshot мира.

Отмена до completion не создаёт `S2C_AttackResult`. После commit ошибка доставки не отменяет и не повторяет нанесённый урон. Этот receiver пока только проверяет и подавляет дубли; hit FX не подключены. Событие не обновляет здоровье вычислением `HP -= damage`; актуальное здоровье приходит отдельным существующим путём состояния.

## Последовательность одного удара

Времена показаны относительно принятого сервером старта при текущем пресете.

| Момент | Сервер | Сообщения |
|---|---|---|
| Подтверждение направления | Проверяет запрос | `C2S_ActivateAction` содержит приём, угол и epoch |
| `0.0 с` | Фиксирует угол и начинает 6-tick выполнение | `S2C_ActionStateChanged` с `executing`, обычный progressbar и доступная definition-анимация |
| `0.6 с` | Перечитывает параметры, рассчитывает и подготавливает весь удар; списывает 60 stamina, начинает cooldown 2 с, применяет урон и завершает действие | `S2C_AttackResult`, обычные stats updates, `S2C_ActionStateChanged` с `idle`; другой готовый приём разрешён сразу |
| `2.6 с` | Истекает cooldown первого приёма | Клиент использует уже полученный `expires_at_ms`; отдельное событие истечения не требуется |

Точное число тиков определяется серверным tick duration. Анимация использует фактически переданные ticks, без жёстко заданного клиентского tick rate. Вся проверка попаданий и моментов оплаты выполняется сервером.

## Границы и внедрение

Добавления protobuf сохраняют существующие номера и типы полей. Новый код приёмов требует обновлённых клиента и сервера; возможность декодировать неизвестные поля сама по себе не гарантирует правильного боевого поведения старого клиента. Существующий каталог определяет наличие доступных приёмов; отдельный `combat_supported` не вводится.

В этой итерации отсутствуют пакеты непрерывного aim, отдельные команды hit или miss от клиента, тестовые состояния целей, новый протокол HP/SHP/HHP, stun, KO, снарядов и восстановления сессии. KO, смерть и уничтожение используют уже существующие серверные получатели и lifecycle. Система статусов, модификаторы эффективных атрибутов, ranged combat и hit FX остаются следующими изменениями.

Общий melee handler не содержит ветвлений по топорам, мечам, ножам или пикам: selector, sector, hitMode и multiplier задаёт definition. Каждый shard имеет собственные storages, receivers и scratch buffers; неизменяемый catalog и prepared selectors совместно используются shards. Нового ECS component, SQL/protobuf поля или balance change для этого подключения не требуется. Prepared completion завершается в том же shard-locked вызове: подготовка всех расчётов и lethal reservations → стоимость → полный health commit → завершение действия → quarantine/уведомления. После первого авторитетного изменения не остаётся fallible admission.

## Проверка схемы

Схема проверена сериализационными тестами Go и клиента: отсутствие угла отличается от нуля, старый запрос активации декодируется, сектор сохраняет радианы, анимация передаёт угол в обновлении и spawn snapshot, результат сохраняет промах, нулевой и дробный урон и точные ID больше `2^53`. Общий бинарный пример запроса с нулевым углом проверяется обеими реализациями. Клиентский тест также проверяет маршрутизацию `attack_result`.

При внесении схемы выполнялись `go test ./internal/network/...`, `npm --prefix web_new run test:combat-protocol`, `npm --prefix web_new run type-check` и `CGO_ENABLED=0 go build ./cmd/gameserver ./cmd/load_test`. Эти первоначальные проверки относятся к сетевому контракту. Runtime дополнительно покрывается ECS integration tests melee completion, damage receivers, bounded spatial query и проверками client result receiver; результаты текущего запуска приводятся в отчёте изменения.
