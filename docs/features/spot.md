# Споты в Origin: генерация и начальное состояние

`cmd/mapgen` создаёт ресурсные споты отдельным этапом после сохранения окончательных
тайлов, деревьев, валунов и `last_used_id`. Конфиг хранится в
[`etc/mapgen/spots.yaml`](../../etc/mapgen/spots.yaml); флаг `-spots-config`
переопределяет путь. PNG-only и интерактивный preview не создают споты.

| Тип | Допустимые тайлы центра по умолчанию |
| --- | --- |
| `www` | Леса, трава, `Swamp1`: 20, 25, 35, 50 |
| `clay` | `Clay`: 64 |
| `soil` | Трава и `Dirt`: 35, 60 |
| `sand` | `Sand`: 68 |
| `water` | Леса и трава: 20, 25, 35 |

`water` — подземный источник качества воды для будущего колодца. Водные тайлы
не могут быть центрами ни одного типа. Ограничение относится только к центру:
круг спота может пересекать воду, соседние районы, другие споты и границы мира.

По умолчанию район имеет сторону 512 тайлов, радиус спота — 64 тайла, базовое
качество — 10, пиковое — случайное целое 20–50 включительно. Каждый район получает
не более одного спота каждого типа; при отсутствии допустимого тайла тип пропускается.
Неполные крайние районы обрабатываются теми же правилами.

Диапазон пикового качества задаётся отдельно для каждого типа: обязательные
целочисленные `peak_quality_min` и `peak_quality_max` находятся в соответствующем
элементе `spots` в YAML. Границы включаются и должны удовлетворять
`base_quality <= peak_quality_min <= peak_quality_max <= 32767`; общий
`base_quality` остаётся 10. В стандартном конфиге у всех типов диапазон 20–50.
Изменение диапазона одного типа не меняет центры, вероятности появления или
качество остальных типов. В собственных конфигах прежние верхнеуровневые границы
пикового качества нужно перенести в каждый элемент `spots`.

Для каждого типа задаётся `spawn_chance` от 0 до 1. Если поле отсутствует,
используется 1; в стандартном конфиге WWW имеет 0.15, остальные типы — 0.5.
Одна детерминированная проверка seed, типа и координат района решает, будет ли
в нём спот этого типа. Число подходящих тайлов не увеличивает вероятность.
0 отключает тип, 1 создаёт спот при наличии подходящего тайла; 0.25 означает
25% вероятность для каждого подходящего района, а не точную квоту по миру.
Проверка использует отдельный хеш и не меняет центр или качество сохранённых
спотов. Лог отдельно считает отсутствие подходящего тайла и пропуски по вероятности.

Центр выбирается по минимальному детерминированному хешу seed, типа и координат
допустимого тайла; при равенстве используется порядок `(tileY, tileX)`.
Качество использует отдельный хеш seed, типа и индексов района. Изменение порядка
типов в YAML и количества workers не меняет результат. Генерация спотов не
расходует RNG деревьев и валунов и хранит только пять кандидатов текущего района.

## Хранение

DDL находится в [миграции](../../migrations/20261010_spots.sql) и
[`schema.sql`](../../migrations/schema.sql). Единственная таблица `origin.spot` содержит:

| Поля | Назначение |
| --- | --- |
| `id` | `BIGSERIAL`, постоянный ID конкретного спота |
| `region`, `layer`, `spot_type` | Регион, поверхность (`layer = 0`), тип ресурса |
| `district_x`, `district_y` | Неотрицательные индексы района сетки генерации |
| `center_x`, `center_y`, `radius` | `INTEGER`, абсолютные мировые координаты и радиус |
| `peak_quality` | `SMALLINT`, начальное пиковое качество |
| `state` | `JSONB`-объект, первоначально `{}` |
| `last_runtime_seconds` | `BIGINT`, сохранённое время работы сервера |
| `revision` | `BIGINT`, первоначально `1` |

Уникальность задаётся по `(region, layer, district_x, district_y, spot_type)`.
Отдельной таблицы генерации, snapshot, hash, seed и дублирующих тайловых координат нет.
Размеры в конфиге заданы в тайлах; преобразование центра и радиуса всегда использует
`_const.CoordPerTile`. Размеры чанков используют `_const.ChunkSize` либо
`_const.ChunkWorldSize`. Арифметика проверяется на переполнение и диапазон SQL `INTEGER`.
Обратное преобразование отрицательных координат округляет вниз.

Mapgen validates configuration and geometry before resetting the world. Full
generation atomically truncates all world tables, including spots and world
globals, across all regions and layers, while preserving account and character
rows. The shared entity ID checkpoint is reseeded above every retained character
ID. SQL sequences continue. New spots use runtime `0` in the fresh world.
Spot insertion uses batches of at most 1000 rows. The same final transaction
creates mature WWW objects, writes their spot manifests, updates affected chunk
counts and saves the final entity ID checkpoint. An error rolls back that stage,
but not the preceding world reset and terrain generation.

## SpotManager

Поверхностный shard при старте один раз загружает все типы спотов своего
`cfg.Game.Region`. Ошибка загрузки останавливает запуск; пустой каталог допустим.
`SpotManager` хранит один канонический экземпляр каждого спота и неизменяемый
индекс `ChunkCoord → SpotID` пересекающих чанк кругов. Выгрузка чанка не удаляет
спот и не меняет его состояние. Запросы к каталогу не загружают чанки и не читают БД.

`FindAtTile(layer, tileX, tileY, type, dst)` принимает абсолютные тайловые
координаты и возвращает все совпадения по возрастанию ID. Пустой `type` означает
все типы. Проверяется центр тайла и условие `distance² <= radius²`; пересечение
прямоугольника тайла с кругом само по себе не означает принадлежность. При
отрицательных координатах используется округление вниз. `IntersectingChunk`
возвращает только кандидатов; геометрия и пиковое качество доступны через `Get`.
Оба запроса используют переданный буфер без аллокаций при достаточной ёмкости.

`GetState` возвращает собственную копию JSON и подтверждённую revision.
Менеджер не навязывает схему ресурса. WWW хранит актуальную коллекцию
`www.objects`: ключи — десятичные EntityID, значения — мировые координаты `{x,y}`.
Сбор, рост и выгрузка её не меняют. Все данные, включая большие целочисленные ID,
сохраняются без преобразования через `float64`. Для остальных типов исходное
состояние — `{}`; WWW после mapgen имеет хотя бы `{"www":{"objects":{}}}`.

`SaveState(id, expectedRevision, state, runtimeSeconds)` принимает самостоятельную
запись состояния через существующие workers сохранения чанков. Успешный возврат
означает принятие записи, а не commit. До подтверждения БД `GetState` возвращает
прежние данные, а повторное изменение того же спота получает `ErrSpotSaveBusy`.
При заполнении очереди новая запись не принимается. `SpotManager.Update`
под блокировкой shard ограниченно обрабатывает только незавершённые записи.

Условный SQL обновляет существующую revision на единицу. Повтор того же снимка
после неоднозначного результата считается успешным при совпадении следующей
revision, JSONB и runtime-времени, без повторного увеличения revision. Временные
ошибки сохраняют исходный снимок и повторяются с backoff от 100 мс до 5 секунд.
Конфликт revision сохраняет ошибку и блокирует запись только затронутого спота;
ошибка доступна через `Err`. Остальные споты продолжают сохраняться.

Workers не изменяют каноническое состояние. Только owning shard применяет
подтверждения; обычное сохранение чанков споты не записывает. При остановке
закрывается приём новых изменений и до остановки workers выполняется drain
принятых записей с пределом 30 секунд. Ожидание I/O не удерживает shard lock;
незавершённые записи явно отражаются в журнале ошибок.

## WWW: размещение и актуальный список

Mapgen размещает зрелые WWW внутри кругов, только на тайлах 20, 25, 35, 50.
Водные тайлы исключаются для каждого растения, а не только для центра спота.
Начальная цель — 1% площади круга в тайлах с округлением вниз: 128 при радиусе 64.
До координат любого другого объекта, включая соседние чанки и новые WWW,
должно быть не меньше 20 мировых единиц. Коллайдеры в проверке не участвуют.
Количество может быть меньше цели из-за террайна и занятых позиций.

Уничтожение WWW удаляет объект и его ключ из `www.objects` одной транзакцией
существующего persister. SQL меняет текущий JSON точечно; одновременные удаления
не теряют записи друг друга. Повтор не увеличивает revision/runtime второй раз.
Подтверждённый снимок применяется через `ApplyCommittedState` только owning shard;
старые revision не заменяют новые. Тот же путь используется административным
`/destroy`. Самостоятельный `SaveState` для runtime-изменений списка WWW не вызывается.

Растения сохраняют свой `spot_id`, стадию и runtime-срок роста обычным объектным
путём. Полные правила и проверки — в [плане WWW](wild_windsown_plan.md).

## Последующие этапы

Вероятностное пополнение уничтоженных WWW, колодцы, истощение и использование
остальных типов качества не подключены; правила `Dig` сохраняются. Записи о
сроках восстановления уничтоженных WWW и очереди замен не создаются. Старые
миры автоматически растениями не заполняются.

# TL;DR

В Haven & Hearth «споты» — это **quality nodes**: локальные максимумы скрытых **шумовых полей качества**, отдельных для каждого типа ресурса. Слово «Spot» в игре — это ещё и отдельная механика *обнаружения* ресурса игроком (Perception × Exploration). Качество источника задаётся узлом при генерации мира, падает от сбора и (после World 16) дрейфует со временем.

# Официальная модель (от разработчиков)

Единственное прямое официальное описание — в [Prelude: World 16](https://www.havenandhearth.com/forum/viewtopic.php?f=39&t=76519) (jorb, окт 2024):

> **«The quality noise fields of foragables and animals drift every new moon, with animal quality drifting faster than herb quality.»**

То есть технически: для каждого типа ресурса (каждой травы, каждого вида животных) есть своё непрерывное шумовое поле качества поверх координат мира. «Узел» — это просто локальный максимум этого поля. Каждую «новую луну» (~месяц) поля дрейфуют, узлы перемещаются. Там же: «Quests no longer yield local quality increases as a potential reward» — раньше квесты могли *поднимать* качество узлов локально (ввели ~W13–14, в W16 убрали).

loftar о генераторе мира ([тред](https://www.havenandhearth.com/forum/viewtopic.php?f=7&t=11222)): генератор написан на **Python**, пятна местности рисуются через **libgd**, и правила расстановки он сознательно не публикует — «it might potentially reveal some secrets that can currently only be found by exploring». Но сам **`patch.py`** он приложил — я скачал его с форума (лежит в `/tmp/patch.py`, 224 строки). Это генератор органических «блобов»:
- `gentree()` — случайное ветвящееся дерево точек (углы/радиусы случайные);
- `genoutline()` — вокруг ветвей строится сплайн-полигон с разбросом радиуса ±20%;
- `draw()` — заливка `fillToBorder` + случайные мелкие кляксы вдоль контура.

Так выглядят и пятна местности, и, судя по «prespawned mining points» из треда о сбросе мира 2009 года, области спотов. **Где** ставить пятна — решает невыпущенная часть генератора.

# Структура узла (наблюдения игроков, [t=13760](https://www.havenandhearth.com/forum/viewtopic.php?t=13760))

- У узла есть **пиковая клетка в центре**, качество **спадает по кругу** от центра.
- Чем выше пик, тем **больше радиус** (Q100-узел находить проще, чем Q15) — подтверждено игроками, но точная формула неизвестна.
- Узел **не обязан быть в «правильной» местности**: глиняный узел может лежать не в mudflats, а на суше; «большая часть земли вообще без глиняных узлов».
- Узлы бывают «comically small» — падение с 80 до 60 за 20 тайлов ([t=69940](https://www.havenandhearth.com/forum/viewtopic.php?t=69940)).

# Правила качества по типам источников

| Ресурс | Как задаётся качество |
|---|---|
| **Травы/сбор** | У каждой травы свои узлы; собранное Q = узел, **жёстко ограничено Survival** собирающего ([Foraging](https://ringofbrodgar.com/wiki/Foraging)) |
| **Руда/камень** | Под землёй **3 независимых случайных типа узлов**: рудные жилы, качество породы, твёрдость — «placed randomly and have no relation to each other». Добытое Q = узел качества породы этой области (иначе base); с каждым уровнем вниз base Q и твёрдость растут. Хардкап — Masonry, софткап — Q инструмента; кредо применяются *после* хардкапа. С 2023 разброс качества — на клетку, а не на кусок ([Mining](https://ringofbrodgar.com/wiki/Mining)) |
| **Вода** | Колодец пробивает карту водного стола: Q тем выше, чем ближе к центру подземного источника; **не ограничено навыками**; ищется лозоходством («the table will rise no further from here») ([Well](https://ringofbrodgar.com/wiki/Well)) |
| **Глина/почва** | «Единственные ресурсы, чьё качество игрок поднять не может» — только найти источник. Q почвы читается по травам, растущим на клетке ([гайд Fandom](https://havenandhearth.fandom.com/wiki/Finding_high_quality_water,_clay,_and_soil)) |
| **Рыба** | Тоже узлы — jorb: «Fish are now a limited and localized resource, working in the same way as any other localized resource». Вид рыбы случаен от узла; **у каждого вида своя оптимальная точка внутри узла** (иди туда, где шанс клёва растёт — «аналогично поиску максимума качества в узлах трав»); Q хардкапится Survival ([Fishing](https://ringofbrodgar.com/wiki/Fishing)) |
| **Животные** | **Фиксированные точки спавна с фиксированным Q**, привязанные к quality-нодам — буст «up to +500% depending on the node» ([t=74397](https://www.havenandhearth.com/forum/viewtopic.php?t=74397)). Спавн срабатывает при перезагрузке чанков (проверка ~раз в 15 минут), стадо появляется компактно и разбегается ([t=10431](https://www.havenandhearth.com/forum/viewtopic.php?t=10431)) |
| **Деревья** | Расставляются на фазе генерации мира кластерами по биомам + часть просто случайно, без привязки. Дикое дерево всегда **Q10**; посаженное = Q семени пополам, минимум 10 ([Tree](https://ringofbrodgar.com/wiki/Tree)) |

# Динамика: истощение и регенерация

- Сбор **постепенно истощает узел**: качество падает; «когда должно упасть ниже 10, он просто перестаёт давать что-либо» — до восстановления ([t=13760](https://www.havenandhearth.com/forum/viewtopic.php?t=13760)).
- Глина/почва/вода: восстановление «за несколько дней, если оставить в покое».
- W16: поля трав/животных дрейфуют каждый месяц (животные быстрее) — анти-бот мера против «замингованных» узлов.
- Поверх узлов идут бонусы: реалм-баффы (Woodland +6% на лесных животных/сбор, Marriage of the Sea +15% на рыбу), у урожая — «geographically local variance».

# Механика Spot (обнаружение)

Отдельно от узлов — *видимость* ресурсов ([Foraging](https://ringofbrodgar.com/wiki/Foraging)):
- Оценка = **Perception × Exploration**. У каждого собираемого предмета есть base PER×EXP-порог; минимальный порог = ½ base (начинаешь находить), 2× base (гарантированно видишь всё).
- Сложность конкретного экземпляра **пересчитывается случайно (от base до 4×base) отдельно для каждого персонажа при каждом попадании в радиус зрения** — трава может «мигать» видимостью.
- Примеры порогов: черника 10, крапива 50, Rustroot 1000, Эдельвейс 3200, жемчужница 40 000, Indigo Cap 68 840.
- Редкость не зависит от порога — просто меньше спавнится.

# Эволюция дизайна (важно для origin_go)

Фиксированные узлы → игроки замапили их и-botили («логин, тот же спот, то же животное, каждые 15 минут») → годы просьб рандомизировать Q на спавн ([t=59696](https://www.havenandhearth.com/forum/viewtopic.php?t=59696)) → W16 добавил **дрейф шумовых полей** вместо статики. В обсуждении W16.1 (2025) звучит радикальная идея: «Raw resources should have no Quality until processed (seeds, rocks, ore, live animals, fish)» — сырое качество вообще убрать. Это готовый кейс «как не надо и как чинили» для вашей системы спотов.
