# Minimap / карта мира (Haven & Hearth) — механика и план порта в origin_go

**Актуальный скоуп origin_go (решение 2026-10-02):** миникарта показывает только чанки, уже доступные клиенту в активном состоянии или существующем кэше. Понятия «исследованные территории» и отдельной памяти карты нет. По умолчанию игрок находится в центре. При каждом входе в мир, включая телепорты и переподключения, миникарта очищается. Реализация полностью клиентская. Части 1–2 ниже — справка о других играх, а не требования к origin_go; актуальный план — в частях 3–4.

### 1.2 Источник данных — протокол гридов **[CODE]**

Клиент никогда не получает карту целиком. Мир делится на **гриды 100×100 тайлов** (`MCache.cmaps`), по тайлу 11×11 юнитов.

- **C2S `MSG_MAPREQ` (tag 4)**: запрос грида по координате. Ретраи раз в 1 с, максимум 5 попыток (`MCache.sendreqs`, MCache.java:1195).
- **S2C `MSG_MAPDATA` (tag 5)**: фрагментированный ответ (`pktid:int32, off:u16, len:u16` + байты), до-сборка через `Defrag` (интервальный merge, ≤20 дырок, буферы старше 10 с выбрасываются).
- Формат payload (version 1, именованные суб-чанки, `MCache.Grid.fill`, MCache.java:841):
  - `"m"` — **постоянный int64 grid id** (назначает сервер, ключ всей клиентской памяти);
  - `"t"/"t2"/"t3"` — палитра тайлсетов (имя ресурса + версия) и **массив 10 000 индексов тайлов** (u8, или u16 при ≥256 типов);
  - `"h"` — карта высот, 4 формата квантизации (константная / min+u8×step / min+u16×step / float32), шаг ×11;
  - `"pi"/"p"` — оверлеи (клаймы, дороги) как битовые маски.
- Инвалидация: **S2C `RMSG_MAPIV` (tag 3)** → type 0 = перезапросить грид, 1 = выкинуть гриды вне прямоугольника, 2 = выкинуть всё. Так распространяются правки ландшафта.

`MCache` — только память; дискового кэша сырых гридов нет.

### 1.3 Рендер пикселей: как tile id становится цветом **[CODE]**

Ядро — `MapSource.drawmap(area)`, **1 пиксель на тайл** (MapSource.java:54–109):

1. `t < 0` (неисследовано) → пиксель 0 (прозрачный). Никакого fog-bitmap — **отсутствие = пустота**.
2. Цвет = **сэмпл из базовой текстуры тайлсета** (`Tileset.getres().layer(imgc).img`): `rgb = tex.getRGB(worldTile.x mod tex.w, worldTile.y mod tex.h)`. Фаза сэмплирования — от **мировых** координат тайла, поэтому текстурный узор непрерывен через границы гридов. Никакой таблицы цветов нет — цвет тайла берётся прямо из его тайлсета.
3. **Ridge pass**: если у `RidgeTile`-тайла перепад высот по 4 парам углов > `breakz()` тайлсета — 3×3 окрестность затемняется (`blendcol(cc, BLACK, center?1:0.1)`) — так рисуются контуры горных обрывов. Единственное использование высот в миникарте.
4. **Priority pass**: тайл, у которого любой из 4 соседей имеет **более высокий приоритет тайлсета** — чисто чёрный. Аппроксимация 3D-срезов (стены/полы режут землю). В живых гридах prio = ранг id тайлсета по возрастанию.

Воде, склонам и теням специальной обработки нет.

### 1.4 MapFile — постоянная память исследования **[CODE]**

Ключевое: карта персонажа — **клиентский артефакт**, привязан к машине и персонажу (`map/<genus>/<charid>/` в ResCache = `%APPDATA%\Haven and Hearth` / `~/.haven/data`). Клиент вообще **не знает абсолютных мировых координат** — только grid id + относительные смещения.

- **Commit**: `GameUI.mapfiletick()` — каждый тик игрок в грид-координате `gc`: при смене `gc` или `grid.seq` (свежие данные) → `MapFile.update(map, gc)` сохраняет **окрестность 3×3 гридов** в фоновом Processor-потоке.
- **Merge (сердце системы)**, MapFile.java:1553–1645: грид, уже известный → пересохранить, только если `seq` изменился; неизвестный → вставить в сегмент по смещению `moff = segCoord − gridCoord`, вычисленному из первого известного соседа; если вставляемые гриды согласуются с **другим** сегментом — сегменты сливаются (`merge()`: больший поглощает меньший, все позиции перебазируются, маркеры переносятся). Так разрозненные сессии сшиваются в одну карту.
- **`norepl`**: тайлсеты с этим флагом (игроковые правки) при пересохранении грида берутся из старой копии, а не из новых данных (`mergeprev`).
- **Файлы**: `index` (список сегментов + маркеры), `gi-<id>` (grid id → сегмент + позиция), `grid-<id>` (палитра + компактный remap тайлов + квантизованные высоты + оверлеи, zlib через ZMessage), `zgrid-<seg>-<lvl>-<x>-<y>` (кэш зумов). Рост ≈ один маленький файл на посещённый грид 100×100.
- **Экспорт/импорт**: `MapFile.export()` → `"Haven Mapfile 1"` + чанки `"grid"/"mark"` с фильтрами; импорт ребейзится и сливается той же `merge()` — так сообщество делит совместные карты.

### 1.5 Зум **[CODE]**

- **zoomlevel (dlvl)**: 1 px на 2^dlvl тайлов. Реализован пре-вычисленными **ZoomGrid** 100×100, покрывающими (2^lvl)² базовых гридов: `ZoomGrid.from` берёт у 4 детей **мажоритарный тайл 2×2** (по счёту, ничья → меньший индекс), z = min. Палитры детей мержатся по имени ресурса. Кэшируются слабо в памяти и **на диск**; инвалидация при добавлении гридов идёт вверх по дереву.
- **maglevel**: 1/2/4/8 — целочисленное увеличение текстуры текущей клетки (зум внутрь ближе 1px/тайл).
- Колесо: наружу — mag/2, иначе dlvl++ (только если есть данные на границе; CornerMap ≤5); внутрь — dlvl--, иначе mag×2 (≤8).

### 1.6 Маркеры и иконки **[CODE + WIKI]**

- **PMarker** (игроковые: имя, цвет, флаг «на карте»); **SMarker** (серверные объекты: gob UID + сохранённый ресурс + байты состояния — так natural wonders/quest givers метятся автоматически, `GameUI.uimsg "map-mark"`). Все в `index`, счётчик `markerseq` инвалидирует кэш отрисовки.
- PMarker с `onmap` дополнительно рисуется **в 3D-мире** флагом (`gfx/hud/mmap/markobj`) в пределах 2 cuts.
- **GobIcon**: объекты с атрибутом `GobIcon` (животные, игроки) показываются иконками на уровне dlvl==0, с настройками show/notify (pulse через ColorMask); опционально конвертируются в постоянные SMarker.
- **Партия**: каждый член (включая себя) — повёрнутая стрелка `plp`, цветная по члену партии.
- Тултип — имя ландшафта из `tooltip`-слоя тайлсет-ресурса. Клик по миникарте транслируется в **клик по миру** (`posres` — суб-тайловая точность 11/1024): в H&H миникартой даже ловят гусениц.
- Рулётки/линейки в официальном клиенте **нет**; постоянного координатного HUD нет — `Location` печатается как `(x,y) @ <segment hex>`.

### 1.7 Ограничения модели (зачем порту это учитывать)

1. Нет абсолютных координат → вся «магия» MapFile (сегменты, offsets, merge) существует **только чтобы обойти это отсутствие**.
2. Карта — на машине игрока: не переносится между компьютерами, не видна серверу (нельзя сервером нарисовать «вы уже здесь были»), решается export/import или сетевым `mapbase`.
3. Исследование = «что сервер прислал» (окрестность 3×3 гридов, т.е. видимость ~сотни тайлов), а не честная фог-оф-вар по линии взгляда.
4. ZoomGrid-инвалидация периодически лагала (багфиксы 2021–2022 в ченджлогах).

## Часть 4. Клиентская реализация — 2026-10-02

### Поведение

Миникарта показывает только **сейчас доступные клиенту чанки**: активные и удерживаемые существующим `ChunkCache`. Понятия «исследованной территории», отдельных копий тайлов, накопительной истории карты, IndexedDB, сохранения местности в localStorage и экспорта нет. После вытеснения чанка его пиксели исчезают на следующем кадре, даже если игрок стоит на месте. Чтение миникартой не продлевает TTL и не меняет порядок LRU.

Проекция подтверждена: **вид сверху, квадратные тайлы, фиксированная ориентация**. Положительный мировой X направлен вправо, Y — вниз. Стрелка находится в центре и поворачивается по мировому heading игрока; карта не вращается. До первого движения используется spawn-позиция, затем — уже вычисленное сглаженное положение. Панорамирование и масштаб основной камеры на миникарту не влияют.

`MinimapWindow.vue` размещён справа сверху после инициализации renderer. Canvas по умолчанию 200×200 CSS px; до ширины 1024 px окно опускается под hotbar, до 640 px Canvas уменьшается до 160 px, на низких экранах — до 96–160 px. Учтены safe-area и место для чата. Кнопки `−`/`+` и вертикальное колесо меняют только масштаб миникарты: **0.5, 1, 2, 4**, по умолчанию **1**. При 1× один тайл занимает один CSS-пиксель. Увеличение nearest-neighbor, backing Canvas учитывает DPR. Нажатия не отправляют команды движения; `keyup` проходит наружу, чтобы ранее зажатая клавиша движения корректно отпускалась.

Панорамирования миникарты, большого окна карты, кликов для движения, постоянных маркеров и дополнительных серверных данных в этой реализации нет. `TILE_VOID` и недоступные чанки прозрачны; через них виден фон виджета.

### Источники и жизненный цикл

- `ChunkManager.getMinimapChunk()` возвращает заимствованный активный payload, включая ещё не готовый графически чанк; при его отсутствии — запись `ChunkCache.peek()`. Tile-массивы не копируются. Существующий active-only метод `getTileTypeAtWorld()` не изменён.
- `MoveController.getVisualPosition()` возвращает spawn или текущее сглаженное положение без повторного шага интерполяции. `GameFacade` остаётся границей между Vue и игровым renderer.
- `Render` рисует миникарту после обновления движения. Ссылки на чанки живут только внутри синхронного вызова рисования. Хранятся статический атлас и переиспользуемые буферы текущего viewport; изображений чанков и кэшей зумов нет.
- Принятые обновления тайлов видны на следующем кадре. Пакеты сначала проходят существующий `ChunkStreamGuard`; у миникарты нет собственного сетевого пути.
- **Каждый `playerEnterWorld` безусловно очищает прежний мир и миникарту**, даже без предшествующего leave. `resetWorld`, disconnect и detach тоже очищают Canvas. Отложенная загрузка статического атласа никогда сама не рисует кадр, поэтому не может вернуть старую местность или стрелку.
- **Контракт будущих шахт:** вход/выход из шахты и переход между подземными слоями должны проходить через существующий world-entry/reset путь. Даже одинаковые координаты чанков принадлежат новому входу; показываются только заново принятые данные. Тесты моделируют поверхность → шахта → более глубокий слой → поверхность. Отдельные карты слоёв не сохраняются.

Изменения сервера, API и protobuf для механики не нужны.

### Атлас: контракт и рецепт

Поставляются `web_new/public/assets/game/minimap_base.png` и `minimap_base.json`. PNG имеет размер **80×64 RGBA**, сетку 5×4 ячеек; первые 17 ячеек — непрозрачные текстуры **16×16**, последние три не используются. JSON — прямое соответствие десятичного ID объекту `{ "x": 0, "y": 0, "width": 16, "height": 16 }`, координаты в пикселях PNG. Областей для `255` нет.

| Строка | ID слева направо | Материалы |
|---|---|---|
| 1 | 1, 3, 12, 14, 20 | Глубокая вода, мелководье, каменное мощение, пашня, хвойный лес |
| 2 | 25, 30, 35, 40, 45 | Лиственный лес, заросли, трава, пустошь, вересковое болото |
| 3 | 50, 53, 56, 60, 64 | Три варианта болот, земля, глина |
| 4 | 68, 120 | Песок, горы |

Текстуры **сгенерированы агентом встроенным ImageGen через навык `imagegen` 2026-10-02**. Референсы: `art_source/tiles/grass/base_1.png`, `wald/base_1.png`, `water_deep/base_1.png`. Исходный результат генерации: `exec-05824ace-66a8-4744-9d93-6d1539e947ec.png` (1402×1122 RGB). Для итогового атласа применено только детерминированное уменьшение nearest-neighbor до 80×64 и упаковка RGBA с alpha 255 через stdlib PNG-кодек. Художественные цвета/рисунок не заменялись программной генерацией.

Рецепт для повторной генерации: один лист 5:4, ровная сетка 5×4 без полей и промежутков; каждый материал заполняет квадрат целиком. Просить плоские top-down pixel-art поверхности в приглушённой природной палитре, крупные цветовые группы и редкую фактуру, рассчитанные на уменьшение до 16×16. Исключить изометрические ромбы, подписи, объекты, деревья, направленный свет, тени и прозрачные углы. Порядок материалов — как в таблице. Для пашни — горизонтальные борозды; болота различать как серо-зелёное, тёмное бирюзовое и жёлто-оливковое; воду — тёмно-синюю и светло-синюю. После генерации проверить совпадение сетки с JSON и читаемость каждого материала в финальном размере. Генерация не выполняется при сборке или запуске игры.

Сэмплирование: `color(tileId, tileX, tileY) = atlas[rect.x + mod(tileX, 16), rect.y + mod(tileY, 16)]`. Мировая фаза сохраняется через границы чанков, остаток для отрицательных координат неотрицательный. Размер чанка и мировые единицы на тайл берутся из параметров входа в мир.

При ошибке загрузки или некорректной области используется fallback только для затронутых материалов. Палитра покрывает все 17 типов, включая пашню и три болота; `TILE_VOID` прозрачен, неизвестный ID — диагностический magenta. Диагностика ограничена и не повторяется каждый кадр.

### Проверки

Из корня репозитория:

```sh
python3 tools/validate_minimap_atlas.py
python3 tools/validate_minimap_atlas.py --self-test
python3 tools/tests/roundtrip_test.py --regression
node tools/tests/pixi_semantics_test.mjs
python3 tools/tests/render_sim.py
```

Валидатор читает канонические ID/размер из TypeScript и проверяет точные ключи, целочисленные координаты, размер, границы, отсутствие пересечений и alpha 255. Self-test включает ошибочные fixtures.

Из `web_new` с совместимым Node:

```sh
npm run test:minimap
npm run test:chunks
npm run type-check
npm run build
```

`test:minimap` проверяет raster/loader/Canvas lifecycle и настоящий Vue HUD: отрицательные координаты, швы, fallback, замену и исчезновение чанков, zoom/DPR, отменённые загрузки и изоляцию ввода. `test:chunks` проверяет заимствование тайлов, приоритет активных данных, неизменность TTL/LRU, отбрасывание старых пакетов, начальный spawn, один шаг интерполяции, независимость камеры и сбросы слоёв.
