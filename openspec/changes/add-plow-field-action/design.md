# Design

## Context

The existing game-actions system loads target, requirements, and execution from JSON. It already supports an absolute stamina cost and repeatable target actions. `lift_down` is an existing tile action: its click enters a placement flow and must not acquire automatic movement. The current action service only handles armed clicks in Selecting, and a repeatable action is rearmed only while all requirements, including stamina, hold. The client currently bypasses hand-item dropping only in Selecting; a click during Approaching or Executing can therefore become dropToWorld instead of reaching action routing.

MovementSystem computes intended positions before CollisionSystem and TransformUpdateSystem apply collision-resolved positions. `Movement.HasReachedTarget` uses `StopDistance = 0.2`; the tile width is 12 world units and its center has integer coordinates. Chunks hold tile bytes, passability bitsets, a version, and a dirty flag. Chunk versions are in-memory values and restart when an evicted chunk is loaded again, even within the same client world stream. Initial and AOI chunk-load producers currently copy Tiles and read Version separately without the chunk lock. The client already renders `TilePlowed` and rebuilds a chunk on any chunk-load message; it stores the chunk version but does not compare it, so an older payload can currently overwrite a newer one. Its render cache survives individual chunk unloads. See proposal.md and the delta specs for the behavior contract.

## Goals / Non-Goals

**Goals:**
- A player selects Plow tile from Actions, reaches the selected tile center, completes one cycle, and keeps the cursor armed for another click.
- Terrain is validated by tile coordinate at selection and completion. The center approach uses ordinary movement and collision.
- A hand-held inventory item does not divert an active target action's map clicks into dropToWorld.
- The existing tile placement action retains its behavior. The tile edit persists and reaches current viewers.

**Non-Goals:**
- Acquiring skills, planting crops, terrain growth, and terrain reversion.
- A separate object-occupancy query or a guarantee that every object inside a tile prevents reaching its center.
- Percentage stamina fields or a new tile-update packet.

## Decisions

**D1. Keep the action definition small and use the existing absolute stamina field.**
`data/actions/plow_tile.json` has ID `plow_tile`, label `Plow tile`, icon `/assets/cursor/dig.png`, target kind `tile`, cursor `dig`, `isRepeatable: true`, `execution.ticks: 20`, and `execution.stamina: 250`. Its requirements section is empty. Register `dig` in the client cursor catalog with the existing `/assets/cursor/dig.png` asset and the same hotspot convention as the existing action cursors. The fixed cost is deliberately larger than existing 100-unit craft actions; a new character has 1000 maximum stamina, but the cost does not scale with CON. The action-catalog and map-click protobuf formats remain unchanged; chunk visibility messages are extended separately in D8. The action is registered with a plow handler and checked by existing handler-definition validation.

**D2. Make center approach an opt-in target policy, not a rule for every tile action.**
Add an optional `target.approach: "tile_center"` value to action definitions. Missing `approach` preserves direct tile execution; reject `tile_center` on non-tile targets at load time. Only `plow_tile` sets it, so `lift_down` still uses its placement transition. In ActionService, normalize an armed click to tile indices with floor division (including negative world coordinates) and compute the center as `(tileX*CoordPerTile + CoordPerTile/2, tileY*CoordPerTile + CoordPerTile/2)`. Store that canonical center as the active target. The exact pixel clicked and any clicked entity ID do not affect tile identity. If the player is already within movement arrival tolerance of the center, start the cycle; otherwise set action-owned point movement to the center, even when the player is already inside the tile bounds.

**D3. Confirm arrival after collisions using the actual player position.**
A pre-collision MovementSystem event is not sufficient: an overshoot snap can request the center while CollisionSystem keeps the player outside it. Record a one-shot arrival intent when MovementSystem clears a point target, and publish a movement-stop/arrival event only after TransformUpdateSystem applies the collision-resolved position. Include the player's ID, actual final position, and the target point so ActionService can match its current approach. The service starts the cycle only when the actual position is within `StopDistance` of the remembered center. A stop away from the center fails the attempt; a blocked path that never stops uses the existing timeout. No action tick polls range to detect arrival. Choose the approach expiry from the distance to the center and conservative movement speed, plus a fixed margin, so a reachable distant tile cannot time out solely because it lies beyond the old 15-second reach.

**D4. Give active target actions priority over hand-item dropping and allow approach retargeting.**
On the client, a primary map click becomes MapClick while an object/tile action is Selecting, Approaching, or Executing, including when an inventory item is in hand. It must not become dropToWorld. Resolve this priority from the authoritative action ID, phase, and catalog target kind; an empty visual cursor in Approaching or Executing does not enable hand-item dropping. With no active target action, the existing hand-item drop behavior remains available. This routing rule is generic and has no plow-specific action-ID branch.

For a tile action with `target.approach = "tile_center"`, HandleArmedClick consumes clicks in Approaching. Validate the newly selected tile first. On acceptance replace the remembered tile center and movement point; begin the cycle immediately if the player is already at the new center. On rejection alert and continue toward the old center. Revalidate the selected tile and actual center position immediately before the completion effect. During Executing, do not track departures from the center: leaving and returning within `StopDistance` before completion is allowed, provided the other completion checks pass. Being outside that tolerance at completion fails the attempt. A click during an active 20-tick cycle keeps the existing server map-click routing and does not queue another plow; each later tile needs its own click after the current attempt ends.

**D5. Keep a repeatable target action armed through temporary stamina shortage.**
On activation, the existing affordability rule still applies. After activation, Recheck must not cancel a repeatable Selecting action solely for low stamina. An armed click with less than 250 stamina alerts and stays Selecting without moving. During Approaching or Executing, loss of affordability ends that attempt without the plow effect, then returns to Selecting. Complete re-arms after success or attempt failure regardless of current stamina, provided non-stamina requirements still hold. Explicit cancellation, switching actions, death, or loss of a non-stamina requirement still ends the action. Check affordability immediately before the tile write; the world update and the existing Complete charge occur synchronously in one shard turn, with no asynchronous step between them. A failed tile write must return failure without a charge.

**D6. Validate terrain only; use movement collision to gate physical access.**
The plow handler accepts only TileConiferousForest, TileBroadleafForest, TileThicket, and TileGrass. It looks up the current tile by the canonical tile coordinate at click, arrival, and completion. Already-plowed and all other tile IDs return `BAD_TERRAIN`; missing or unloaded chunks return a target-unavailable alert. It does not inspect spatial objects. A collider that actually blocks the player from reaching the center prevents the action from starting. A collider-less object, or an object elsewhere in the tile that leaves the center reachable, does not prevent plowing. This is the intended physical rule, not an occupancy guarantee.

**D7. Write one tile and publish a versioned chunk snapshot.**
Make `Chunk.SetTile` the single tile mutation point: a bounds-checked single-byte write under the chunk lock that recomputes that tile's passable/swimmable bits by clearing and setting them from the new tile ID, increments Version, and sets tilesDirty; an unchanged ID performs no write. The chunk load path becomes `RestoreTiles`, which installs the persisted Tiles and Version without incrementing. Existing `populateTileBitsets` only sets bits and never clears them (`chunk.go:345`), so repopulating over stale bitsets leaves passable/swimmable bits behind that `CollisionSystem` would trust (`collision.go:598`); restore therefore zeroes both bitsets before repopulating, and `SetTile` writes its tile's two bits instead of OR-ing them. Any tile mutation outside `SetTile` would silently break both the client version guard and the database compare-and-set.

Provide one shared `Chunk.SnapshotTiles` accessor that copies Tiles and reads Version under the same read lock. The returned bytes are detached from the chunk and remain immutable in event payloads. Use it for every S2C_ChunkLoad producer: initial loads in EnableChunkLoadEvents, AOI activation loads in updateEntityAOI, and plow rebroadcasts. These producers must not copy public Tiles and read Version separately. After a successful plow, send the resulting snapshot to active AOI viewers using their current stream epochs. Saving likewise captures bytes, Version, and LastTick together under its existing read lock.

Persist the tile-content version: the save sends the captured snapshot Version with its tiles, and `UpsertChunk` stores that value instead of the SQL-side `version = chunk.version + 1` while rejecting a write whose Version is lower than the stored one; the `chunk.version` column becomes `NOT NULL DEFAULT 0` with no compatibility shims, as there is no existing data. Return the affected-row count from the query and adapt every caller, including `cmd/mapgen`: newly generated chunks supply initial Version 0, and the generator requires one affected row per write, treating zero rows as a rejected write rather than success. A zero row count means the runtime write was superseded and counts as a failed save. On a successful write, clear tilesDirty only if the current Version still equals the saved Version. A failed or superseded save leaves the chunk dirty. safeSaveAndRemove must retain a dirty chunk in the manager and schedule a later save with bounded retry delay; it may remove the chunk only after the current tile version has been stored and its final identity, inactive state, interest, and dirty-state checks permit removal. Recheck after the DB call, including when AOI interest disappears again during an in-flight save. Avoid immediate retry loops and keep failed chunks discoverable for retries and clean shutdown. Durability requires a successful save; abrupt crashes before saving remain outside the guarantee.

On the client, the per-coordinate version guard lasts for the whole world stream and survives chunk unload and server eviction, because the persisted version no longer restarts. One shared acceptance decision runs before updating both gameStore and the renderer, first checking stream and event order as described in D8: a payload with a Version lower than the highest applied for that coordinate is stale and rejected; an equal Version after a reload describes unchanged tiles and permits reusing ready Chunk geometry when its built version and neighbor inputs match (D9); a greater Version rebuilds from the payload. If no matching ready chunk remains, an equal-version load is accepted and built from its payload. A world-stream reset clears all guards and cached terrain, covering a server restart whose unsaved changes never reached the database. Verify two rapid edits leave both plowed tiles visible, that AOI exit and re-entry reuses ready unchanged geometry when retained and valid, that a changed chunk re-entering AOI rebuilds from its greater Version, and that a fresh stream accepts its first chunk after a server restart.

**D8. Order chunk visibility events with a sequence independent of tile Version.**
Extend both S2C_ChunkLoad and S2C_ChunkUnload with `uint32 stream_epoch = 2` and `uint64 event_seq = 3`, and carry the sequence in their internal ECS events. Use one monotonically increasing counter for each client's world stream, starting at 1; it is runtime state, is not stored in the database, and does not reset on chunk unload, eviction, or repeated initialization of the same stream. All initial loads, AOI loads/unloads, and edited-chunk rebroadcasts obtain their sequence through one creation path in authoritative state order. Capture each load snapshot and stamp its event in that order before asynchronous publication; allocate unload sequences with their AOI transition. An obsolete transition or an already captured older snapshot must not acquire a later sequence merely because its worker ran later. Initial enabling and other producers outside the shard tick must enter the same serialized ownership path. Async dispatchers preserve the captured epoch and sequence, and recheck the client's epoch immediately before enqueueing the packet. Regenerate server and client protobuf bindings together; no unsequenced compatibility path is kept.

The client compares uint64 sequences losslessly and keeps `lastEventSeq` per chunk coordinate, rather than rejecting an event based on the latest number seen for another chunk. Reject a different stream epoch, zero sequence, or a sequence less than or equal to that coordinate's last accepted sequence before any store, renderer, or bootstrap side effect. A newer load also passes the tile-Version guard from D7. An accepted unload advances `lastEventSeq`, hides/removes the active client state, and cancels obsolete buffered loads and pending builds for that coordinate; it preserves the event and tile-version guards and any retained render cache. Buffered loads and deferred builds carry stream/event identity and cannot apply after a newer unload or world reset. A fresh stream clears the sequence and version guards and pending work. If a chunk visibility packet cannot enter the client's send queue, end that connection so a new world stream reboots its state instead of silently losing the transition. Sequence numbers handle message reordering and duplication; they do not recover a dropped final event by themselves.

**D9. Retain ready client Chunk instances and bound their lifetime with TTL/LRU.**
ChunkManager owns each Chunk and its ground geometry/GPU resources. Reuse that existing instance after unload; keep associated cache metadata for its built tile Version, readiness, neighbor inputs, and retention time. Do not introduce a separate geometry extraction/reattachment cache. On an accepted unload, remove active gameStore data, hide the Chunk, unregister its culling entries, and cancel its pending work as in D8. Retain only fully built geometry for reuse; incomplete chunks are not valid cache hits. Decorative terrain keeps its existing clear/regenerate lifecycle independently of ground geometry reuse.

After a load passes the stream, event-sequence, and tile-Version guards, reuse the ready Chunk only if its built Version equals the payload Version and its neighbor inputs are still current. Make it visible and restore culling registration without calling buildTiles for unchanged geometry. A greater Version, missing/evicted ready Chunk, or incomplete build requires building from the payload; equal Version must never cause a cache miss to be dropped. Keep gameStore's active tiles in sync with the accepted payload in all cases. Record the presence and tile Version of every neighbor actually used to build borders/corners; presence alone does not detect a neighbor edited in place. Recheck those inputs on reuse, mark affected neighbors when inputs change, and refresh dependent geometry when needed. The existing full chunk rebuild is acceptable for a border refresh; no partial-mesh optimization is required. Every border refresh preserves the chunk's real tile Version instead of using the current version-0 placeholder, and hidden chunks are marked for later refresh rather than rebuilt in the background.

Apply existing CACHE_MAX_ENTRIES (64) and CACHE_TTL_MS (180000 ms) to retained hidden ready chunks; active visible chunks are exempt from cache eviction. Retention starts at unload, and background neighbor checks do not prolong it. Connect TTL/LRU eviction to one ChunkManager disposal path that cancels pending work, detaches/destroys owned Chunk graphics, removes the instance from the manager, and removes its cache metadata exactly once. Keep sequence and tile-version guards after cache eviction. A world-stream reset cancels all pending work, destroys active and retained chunks, clears cache metadata, and clears both guards.

## Risks / Trade-offs

- [An object does not cover the center or has no collider] → Plowing is allowed; the design intentionally has no occupancy rule.
- [An object blocks the center or movement stops short] → The cycle never starts; the attempt fails or times out and the cursor remains armed.
- [A long path needs more than 15 seconds] → Use distance-sized expiry with a safety margin and test a click beyond the old fixed-time reach.
- [A hand-held item diverts an approach click into dropToWorld] → Route primary map clicks for active target actions through MapClick in Selecting, Approaching, and Executing; test hand-item preservation and approach retargeting.
- [Rapid full-chunk updates arrive out of order] → Reject versions lower than the highest applied per coordinate for the whole stream before updating either client consumer.
- [A delayed load/unload reverses a later AOI transition] → Stamp both message kinds at creation with the stream epoch and event sequence; retain a per-coordinate sequence guard after unload and reject older/duplicate events before all client side effects.
- [A buffered load completes after unload or a world reset] → Cancel it and guard deferred application with its captured stream/event identity.
- [A reload has equal tile Version but its ready geometry was evicted] → Accept the event and build from its payload; cache availability does not affect event acceptance.
- [Own tiles are unchanged but a neighbor changed] → Compare the neighbor inputs used for borders/corners and refresh dependent geometry without changing the own tile Version.
- [TTL/LRU removes metadata but leaves hidden graphics allocated] → Evict through one manager disposal path that releases the owned Chunk and metadata together; protect active visible chunks.
- [The client's send queue cannot accept a chunk visibility transition] → End the connection and require a fresh world stream instead of dropping that transition silently.
- [A stale in-flight save reaches the database after newer tiles] → The compare-and-set on the persisted version rejects it; a zero row count keeps the chunk dirty for a bounded-delay retry.
- [A chunk load races a tile mutation] → All initial, AOI, and update sends use the same atomic Tiles + Version snapshot accessor.
- [A save overlaps a tile mutation or fails before eviction] → Retain the dirty flag and chunk, schedule a delayed retry, and remove only after the current tile version is saved.
- [A tile replaced in place keeps stale passability bits (populateTileBitsets only ORs bits in, chunk.go:345)] → `RestoreTiles` zeroes both bitsets before repopulating and `SetTile` clears-then-sets its tile's two bits; regression-test a restore–modify–restore cycle with changed tiles.

## Migration Plan

The definition field and plow action are additive. Existing action definitions omit the approach policy and retain their behavior. Plowed tiles use the existing tile ID and storage format. The `chunk.version` column becomes `NOT NULL DEFAULT 0`; there is no existing data to migrate and no compatibility path is kept, and the load path stops incrementing the version so restored chunks continue from their stored value. Deploy the server and client chunk-message bindings together because both sides require stream epochs and event sequences. Rollback removes the plow definition and handler together; saved plowed tiles remain renderable by the existing client.

## Open Questions

None for this change. Chunk visibility uses stream/event sequencing (D8), and the client cache retains ready Chunk instances with TTL/LRU disposal (D9). Gameplay remains fixed-cost plowing with center arrival, no skill gate, no object-occupancy check, and persistent armed mode until explicit cancellation.
