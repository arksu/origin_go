# Design

## Context

See `proposal.md` and `docs/features/hearth_fire.md`, Part 2, for gameplay. On 2026-10-13 the owner reverted Hearth gameplay/persistence code and requested a simpler design: runtime integrity is required; independent checkpoints and loss of recent progress after a crash are acceptable. The approved synchronous revision requires every Hearth SQL read/save to run on the owning surface path with a five-second context.

The prepared `hearth_fire` definition, seven green-flame frames at 70% scale, and eight approved skull-smoke frames still exist. Tasks 1.1-1.4 provide the ownership migration/schema, sqlc queries and isolated metadata index. The construction stage now connects that index through `hearth.Runtime` and the result's `hearth` behavior; it assigns the actual finisher, replaces their previous home in memory and saves construction synchronously. Login also restores existing home metadata before reattachment or spawning. Task 3.5 adds synchronous pre-activation hydration and orphan normalization. Task 4.1 and the death portion of 4.3a add synchronous permanent-death cleanup; verification is tracked in `tasks.md`. Task 4.2 connects synchronous REST cleanup, completing 4.3a. Tasks 4.4/4.5 add lazy invalid-association repair, recovery/final-save checks and explicit cost boundaries. Section 5 connects ordinary return, interruption and layer-aware login fallback; the KO-window button and FX remain separate. Finisher codecs and lifecycle coordinators are not introduced; previous reverted gameplay is not counted as delivered work.

The database is assumed available. Any Hearth database read, write or commit error must stop the entire server; Hearth adds no SQL retry, reconnect or database-error recovery path. An expected absent row is an ordinary outcome, not a database failure; invalid query results are fatal. Construction waits for its save, orphan normalization waits for commit before activation, and death cleanup waits before the current update/attachment call returns. REST cleanup follows the same synchronous policy; the preceding account-scoped character DELETE preserves HTTP 500 on SQL failure. Independent checkpoints remain acceptable. This is the integration policy, not a claim that the current server already has a universal fatal database-error handler.

Relevant existing mechanisms:

- One shard/World owns each layer. Hearth construction can complete only on the surface, so both sides of a successful replacement belong to one surface World. Ordinary build-site admission does not filter the layer.
- Build cycles already process materials and stamina under the owning shard lock. `TransformObjectToDefInPlace` updates a live object's type, collider, behaviors, appearance and dirty intent without changing its ID or position.
- Chunk persistence has bounded workers, I/O gates and raw cache. `PinPersistenceBlocking` waits for the existing I/O mutex, increments its pin count and releases the mutex before loading; `core.Chunk.UpsertRawObject` marks the replacement row dirty for ordinary saving.
- `finalizeCompletedBuild` now propagates the transform result while keeping ordinary link/window cleanup before transformation.
- Player transfers are asynchronous; accepting `RequestTransfer` is not successful relocation. Action progress, cooldowns, carry snapshots, generation checks and rollback already exist.
- `S2C_Fx` currently carries a key and position. Existing dispatch is local-player-oriented; finite world effects need detached rendering, not a new persistence subsystem.

## Goals / Non-Goals

**Goals:** immediate, unambiguous runtime ownership; ordinary construction/action/transfer reuse; feature-owned policy; simple synchronous Hearth reads and saving; safe restoration of potentially partial saved state.

**Non-Goals:** lossless crash recovery, a globally consistent world checkpoint, a global commit-before-gameplay publication barrier, lifecycle operation journals/coordinators, generic mutation reservations, special corpse/character save barriers, or a new global shutdown protocol. No automatic first-entry hearth, inheritance, backfill, new dependencies, balance changes, or minimap work.

## Decisions

### 1. Keep ownership in the Hearth module

Use `internal/game/hearth` for home lookup, current ownership, conversion policy and association persistence. It owns a current `character -> home` index and reverse object-owner index. Distinguish `Unknown`, `NoHome` and `CurrentHome`; absence never creates an object. Store copied identities and positions, not pointers to live components.

`LoadIfUnknown` installs a copied result only while metadata is unknown. Known runtime state, including `NoHome` and terminal state, wins over SQL data. The owning surface shard serializes reads and association mutations, so no loading flag, optimistic version, save acknowledgment, retain/reference API or eviction lifecycle is needed. Entries remain for the process lifetime; memory grows with the number of characters encountered.

The index retains a short mutex because another layer or REST may mark `PendingTerminal` while the surface owner waits on SQL. Never hold it across SQL, shard locks or ECS callbacks. `ReplaceHome` changes both directions together; `RevokeHome` removes the association on the owner path. `Owner` supplies eligible ownership for collision/return. `SnapshotByObject` returns a copied reverse snapshot including `PendingTerminal` ownership so a pending terminal transition is not mistaken for an orphan during activation.

`MarkTerminalPending` immediately blocks new acquisition/return without mutating the association from a notifying thread. An already admitted owning completion may finish before `ApplyTerminal` revokes the latest home. `Terminal` prevents later rebinding. These states remain in the process-lifetime index; death and REST wiring are described in section 5.

`Runtime.LoadHome(character, hearthType) error` is shared by construction and login. In `spawnAndLogin`, after validating the layer and before `tryReattachPlayer`, load through the surface runtime under its shard lock, including underground login. Known metadata skips SQL; `Unknown` uses `GetCharacterHearth` with an independent five-second context and `LoadIfUnknown`, with `sql.ErrNoRows` entering the lazy repair below before `NoHome` is installed. Missing dependencies or remaining `Unknown` refuse entry; SQL errors and invalid results are fatal. Client cancellation is checked again after the synchronous read and before entry. Release the surface lock before reattachment or spawning, without nesting shard locks. This lookup restores metadata only; it does not create an object or select new spawn candidates.

### 2. Finalize construction immediately, in one surface critical section

Integrate through one optional construction-result wrapper capability using the existing behavior registry. The result behavior prepares its policy before invoking the ordinary completion callback. Shared construction does not check a Hearth key or carry a finisher field.

Preparation runs before the last material and stamina costs. Unknown ownership uses a direct `GetCharacterHearth` with the existing five-second timeout under the surface shard lock, then hydrates the index immediately. A filtered miss first resolves and conditionally repairs the saved association before establishing known absence. An unloaded old chunk is also awaited directly through `WaitPreloaded` with its own five-second context. Successful preparation completes construction in the same call without an extra action cycle, retry result or another click. The wrapper returns ordinary `BehaviorResult`; there is no Hearth preparation queue, completion channel or `Shard.Update` apply hook.

This explicitly chosen blocking tradeoff delays the whole game loop during a slow query, busy I/O gate, chunk load or construction save: `ShardManager` waits for all layers before the next tick, and serial wait latency adds up. Movement/cancel commands arriving during the wait remain queued until the call returns. Expected chunk unavailability during shutdown refuses completion before costs; genuine database/I/O errors remain fatal. Existing chunk workers perform the load, while the owning call waits and then applies gameplay. Do not introduce polling, a special pending-finalization phase or remote-area activation.

When ready, revalidate the exact actor, site handle, current home identity and old source. Under the single surface shard lock, the wrapper invokes ordinary final-branch processing and site completion, converts the previous home to an ordinary unlit campfire, and switches the feature-owned association to the actual finisher. Preserve ordinary completion order: close windows/break links before transforming the site. Propagate the transform's actual `bool` result instead of reporting unconditional success. Prepare the concrete Hearth/campfire definitions and source data before costs; no generic transform transaction or rollback framework is needed.

For a non-active old home, call `PinPersistenceBlocking` before `WaitPreloaded`, then hold the existing pin through the synchronous callback, raw update and construction save with deferred unpin. The small blocking helper reuses the current gate and pin counter: it waits for `ioMu`, increments the counter and releases `ioMu`. The nonblocking pin would return busy; holding `WithPersistence` while waiting would prevent the loader from acquiring that mutex. Apply the prepared campfire row with `UpsertRawObject`; do not spawn or activate the old object. Release the pin after the save returns. There is no new gate, cache-revision change or polling loop.

Runtime changes precede serialization and SQL; the owning call reports success only after commit. Later save snapshots see either previous build progress or the final object, not a paid completed site waiting for a DB commit. The actual finisher is available in this synchronous call and becomes the current owner there. Neither `BuildBehaviorState.HearthFinisherID` nor `behaviors.hearth_construction` is needed. No feature state is added to shared ECS/build contracts.

This construction stage reads saved ownership through the same `Runtime.LoadHome` used by login and saves the completed objects and association in the same call. Pre-activation chunk hydration is described in section 4 and death cleanup in section 5; lazy repair is described in section 4; return is described in section 7 and FX remains a separate stage; collision/terrain rules are described in section 6.

### 3. Save current state, not a history of operations

Keep the simple active-only unpartitioned table:

```sql
CREATE TABLE origin.character_hearth
(
	character_id BIGINT PRIMARY KEY
		REFERENCES origin.character (id) ON DELETE RESTRICT,
	object_region INT NOT NULL,
	object_id BIGINT NOT NULL,
	CONSTRAINT character_hearth_object_unique UNIQUE (object_region, object_id),
	CONSTRAINT character_hearth_object_fk FOREIGN KEY (object_region, object_id)
		REFERENCES origin.object (region, id) ON DELETE RESTRICT
);
```

The keys enforce one saved home per character and one saved owner per object. Coordinates/type/state remain in `object`; Hearth ownership does not use `object.owner_id` or object JSON. There is no first-entry marker, finisher table, pending operation table or cooldown column.

Construction first applies final-branch costs, object transforms and `ReplaceHome` under the surface shard lock, then serializes the final objects. One existing `WithTx` call with a five-second context saves the new Hearth, the previous unlit campfire if present, `character_hearth` and the allocator's durable ID watermark through `UpsertGlobalVarLongMax`. Success is returned only after commit; the index has no dirty version or asynchronous acknowledgment. Keep ordinary object/chunk dirty flags so their normal persistence paths remain intact. Hold an old raw chunk's pin until this save returns.

Serialization, SQL or commit failure, including an unknown commit outcome, stops the entire server. A `SetCharacterHearth` affected-row count other than one is also fatal: no successful completion may omit its association. There is no runtime rollback, SQL retry, completion job queue or commit probing. Normal character, inventory, material, stamina and corpse saving remains independent; this transaction is not an all-or-nothing world checkpoint. Schema, protocol and recipe do not change.

`ConstructionSaverDB.SaveTerminal` synchronously saves an optional campfire conversion and removes the exact `(character, region, object ID)` association in one five-second `WithTx` under `surface.mu`. Removal of zero or one row is accepted. Missing, deleted, changed or quarantined sources pass no object to the writer, so cleanup cannot revive them through `UpsertObject`. The existing chunk pin remains held through saving. No new SQL/schema, ID watermark update, save queue, retry, dirty projection or acknowledgment is introduced. REST reuses this writer after resolving offline Unknown ownership as described below.

Ordinary shutdown and independent character/inventory/corpse persistence retain their current ordering. There is no Hearth-specific dirty flush, worker drain or save-lag instrumentation.

### 4. Hydrate and normalize before exposure

Use `ChunkManager.SetActivationPreparer(func(*core.Chunk) error)` to register `Runtime.PrepareChunkActivation(*core.Chunk) error` after existing gate/state guards and before raw ECS creation. The surface runtime reads the current raw activation candidates, excluding deleted records and IDs already represented by live entities. Existing load generations, chunk I/O gates, ordinary dirty flags and restoration composition remain unchanged. The dead-observer `UnregisterEntityAOI` call must execute under its existing shard lock because it can trigger activation; no new lock or worker framework is required.

Check copied reverse-index snapshots first, including `PendingTerminal`. For unresolved object keys, issue one existing `GetCharacterHearthOwners` query with a five-second context under `surface.mu`; skip SQL for no candidates or fully known ownership. Hydrate eligible owners even when offline, using `LoadIfUnknown` so any known character state wins. Recheck copied current index metadata after the read. Pending terminal ownership is unavailable for return but is not an orphan to normalize ahead of its owner-path cleanup. No per-object query, world scan or new SQL/schema is needed.

For each true orphan, prepare a raw unlit campfire copy using the same `rawCampfire` helper as construction: preserve identity and position, set the campfire definition and HP, clear prior behavior data and set the current last tick. `ConstructionSaverDB.SaveOrphans` saves all converted rows in one synchronous five-second transaction using existing `UpsertObject`. Only after commit call `UpsertRawObject` and allow activation to create entities; failure is fatal and must not publish partial normalization. Subsequent burner/corpse restoration sees the normalized type and data.

After restart, only a saved association to an undeleted surface Hearth with a live character supplies ownership. Known current runtime state supersedes stale saved links. Missing/deleted owners yield true orphans; invalid query results are fatal. Lazy invalid-association repair is limited to Unknown home lookup as described below. Never infer ownership from JSON/`owner_id`, upgrade a saved campfire from its link, replay construction, or recreate missing objects. Independent checkpoints may restore an earlier saved result but cannot publish two runtime homes.

Task 4.4 repairs only an association encountered by Unknown `LoadHome`. After `GetCharacterHearth` returns `sql.ErrNoRows`, use the existing `GetSavedCharacterHearth` with its own five-second context. No saved row means NoHome without writing. Otherwise validate the character/composite key and call `ConstructionSaverDB.RepairInvalidHome` through the existing saver contract. It reuses `WithTx` and `DeleteInvalidCharacterHearth`, accepting zero or one affected row and committing before `LoadIfUnknown(nil)`. The query protects a changed association or a now-valid source. Read/identity/write/commit failures are fatal; no chunk load, object upsert, new SQL/schema or shared-core hook is needed. Valid Unknown still costs one read; true absence costs two reads; invalid ownership costs two reads plus the conditional repair transaction; known state costs no SQL.

This is lazy repair, not global database sanitation. Known NoHome/Terminal are never reread. `SaveOrphans` may leave an old association pointing to its converted campfire; filtered queries still cannot restore it as a home. Unvisited data is not scanned. Recovery tests explicitly preserve these boundaries and independent character/material/stamina checkpoints: a lost terminal operation may restore older saved ownership, and an incomplete saved site never supplies an inferred finisher or replayed costs. Ordinary final-save coverage uses a real character saver and verifies committed ownership/conversions after the unchanged `SaveAll -> CharacterSaver.Stop -> ChunkManager.Stop` path.

Task 4.5 distinguishes operation deadlines from total latency. A five-second context bounds one read or transaction; `PinPersistenceBlocking` waits on the existing I/O mutex outside those contexts, and sequential waits add up. Activation visits the current raw objects/candidates and returned owners, with one unresolved-owner batch and one orphan transaction; there is no fixed numerical Hearth candidate budget. Index memory follows all encountered characters retained for process lifetime, not concurrent players. Existing local microbenchmarks do not establish 30,000-CCU capacity. No additional production metrics, scan, queue or shutdown coordinator is introduced.

### 5. Death uses ordinary lifecycle paths

`HandlePlayerPermanentDeath` calls a registered notification that immediately marks `PendingTerminal` through the synchronized index and records the character ID in the current owning call. `Shard.Update`, `tryReattachPlayer`, `attachClientToWorld` and the immediate attachment path in `spawnTeleportedPlayerWithRuntime` detach those IDs at their unlock boundary, set the source slice to nil, release the source lock and synchronously invoke completion under the surface lock. The outer call returns only after cleanup and commit. A concurrent source call cannot reuse the detached slice. `ShardManager.Update` already waits for shard calls, so the game loop, worker pool and inboxes need no changes. There is no next-tick backlog, new ECS system or nested shard lock.

`NotifyTerminal` touches only the index; `CompleteTerminal` resolves the latest home on the surface owner, including construction already admitted before notification. Login establishes known ownership before entry and entries are never evicted: Unknown at actual death is a fatal invariant violation, not a reason for another SQL lookup. NoHome becomes Terminal without Hearth I/O; repeated Terminal completion is a no-op. CurrentHome uses `PinPersistenceBlocking` and five-second `WaitPreloaded`, validates current live/raw identity, type, layer, chunk tombstones and destruction/reservation state, then reuses `TransformObjectToDefInPlace` or `rawCampfire`/`UpsertRawObject`. It revokes the association and saves before releasing the pin, without activating an unloaded home or reconstructing a missing object.

Two private callbacks are connected after all shards exist. Direct completion from the death handler would nest shard locks; deferring to another tick would violate the synchronous contract. Death integration is limited to notification, wiring, the four existing unlock boundaries and keeping their owning calls alive through the existing shutdown wait. Character/corpse persistence and decomposition retain existing semantics; this feature does not promise atomic status/home/corpse persistence or terminal-commit-before-corpse ordering. REST deletion adds the game adapter described below and reuses synchronous surface completion after the account-scoped delete. No offline body or death FX is fabricated.

Login and transfer goroutines join the existing `Game.wg` before launch and leave it only after the full owning call returns, including terminal completion. Shutdown stops the network and then waits on that group before stopping any shard. Network handlers can no longer launch login work after network shutdown returns; transfer launches occur in shard commands, which the tracked game loop waits for before its own `Done`. This keeps `Add` ordered before the group can drain, without a new admission mutex or Hearth shutdown barrier. Chunk workers remain available for synchronous home loading and saving until these calls finish.

REST injects the required `Game.DeleteCharacter(context.Context, repository.DeleteCharacterParams) error` callback into its handler. The game adapter holds `surface.mu` before the account-scoped `DeleteCharacter :execrows` and through all cleanup; it refuses before SQL if the shard is not Running or its runtime is unavailable. The unchanged SQL predicates prove authorization: zero rows preserve HTTP 204 without touching ownership, one row enters `Runtime.CompleteDeletion`. The delete statement uses the request context bounded to five seconds and preserves HTTP 500 on error. A confirmed deletion completes Hearth work with independent contexts even if the HTTP request is canceled.

The lock must cover the delete statement itself: deleting first could invalidate an admitted construction's subsequent ownership save. It also orders deletion with `Shard.Stop`, which sets Stopping under the same lock before stopping chunk workers. This remains safe after the HTTP shutdown timeout and needs no additional wait-group registration, network changes or lock. REST preserves the living body/session and online policy.

`CompleteDeletion` marks pending, then preserves known CurrentHome/NoHome/Terminal and reuses terminal cleanup. Only Unknown uses `GetSavedCharacterHearth` with a five-second context; its composite LEFT JOIN preserves the exact association plus nullable source metadata after owner soft deletion. A valid source hydrates the index before existing conversion; no association becomes terminal absence; missing/deleted/changed/wrong-layer sources receive exact association-only `SaveTerminal` without chunk I/O. Lookup/malformed-result/cleanup errors are fatal. Actual-death Unknown remains fatal. Known NoHome/Terminal require no Hearth I/O; invalid saved links hidden by known NoHome remain outside lazy repair; orphan-to-campfire links may also remain without providing a usable home.

### 6. Keep object policy separate from geometry

Reuse the prepared definition and existing indestructibility; add the Hearth behavior without burner/fuel runtime or lift capability. Protect removal through a small registered object policy before gameplay/admin deletion, without adding a Hearth branch to the deletion core.

Use identical 1x1 bounds for terrain, collision and structural overlap. Hearth's recipe uses `disallowedTiles: [1, 3, 50, 53, 56, 255]` with existing `BuildService.validateTileRules` over the result footprint at build admission; other known tile IDs remain allowed. There is no additional final terrain recheck, layer field or build placement behavior policy. Existing Hearth completion remains surface-only. Movement/spawn/return filtering allows only the owner through this object; other players, animals and unrelated obstacles retain ordinary collisions. Manual put-down and construction placement share structural collision checks at admission and final application, independently of owner passage.

Owner-only passage is implemented through one optional callback bound to the surface `hearth.Runtime`, shared by collision candidate filtering and authoritative player spawn. `IgnoreObjectCollision(actorID, targetHandle)` validates the live target's current Hearth behavior and composite identity against `Index.Owner`; unknown or ineligible ownership gives no exemption. No behavior capability/context/dispatcher is needed for this single rule. Existing terrain, phantom and other-object checks remain authoritative. Animals receive no exemption; task 3.2 is complete.

Manual `lift_down` and RMB placement use `LiftService.placementAllowedAt` with the private shared `colliderPlacementAllowed` helper in `internal/game/placement_collision.go` on every layer. Check before creating pending/phantom and again before restoring the carried object's runtime; refusal preserves carry and uses existing attempt cleanup and `LIFT_PUTDOWN_INVALID`. The shape and masks come from the saved `OriginalCollider`, or the current definition's optional `lift.placementSize` for colliderless objects: log_x 24x6, log_y 6x24, default 2x2 with Layer/Mask 1. Size config is validated at catalog loading; ordinary pickup, movement and approach phantom remain unchanged.

Construction uses the same helper in `HandleStartBuild` before new pending/phantom state, and in `FinalizePendingBuildPlacement` before allocating an ID or spawning a site. Each call uses `objectdefs.BuildColliderComponent` from the current result definition; the final check resolves it again. Collision refusal uses `BUILD_PENDING_FAILED`; final refusal cancels the current pending/phantom through `CancelPendingBuildPlacement` without creating a site or allocating an ID. An older finalization with different target coordinates or build key returns without applying or clearing the replacement preview. The rule applies to all recipes and layers, including ordinary construction sites; no Hearth callback or behavior capability is needed.

The shared helper reuses `WorldColliderSpatial.Index.QueryBoundedInto`; `LiftService` and `BuildService` each own a reusable 4096-handle buffer, with 1024-cell and 4096-visit query budgets. Strict positive-area overlap with current live `Transform`/`Collider` using ordinary movement mask compatibility blocks placement; exact edge/corner contact is allowed. Skip the actor, the carried object when applicable, and candidates with a phantom. Hearth ownership and behavior are not consulted, so an ordinary campfire remains an obstacle after conversion. Retain existing chunk admission checks and query loaded colliders only, including those extending across chunk boundaries; do not add neighbor readiness or deferred activation checks. A missing spatial index or query error rejects the attempt without I/O. Task 3.4 is implemented for manual put-down and construction; forced lifecycle drops remain outside this scope.

### 7. Return is an ordinary action with an asynchronous outcome

The no-target `travel_to_hearth_fire` action uses ordinary progress, zero stamina and 360000 ms cooldown. Before publishing the registry, Hearth compiles five seconds to `5 * TickRate` execution ticks; no duration schema or separate timer is added. Optional `BeforeExecution` cleans prior build/craft/link intents and stops movement before progress. Use known runtime ownership from login/hydration; `Unknown` fails closed without an asynchronous lookup. Resolve the latest runtime home again on the target surface shard immediately before authoritative relocation. Coordinates captured at progress completion or queue admission are preparation hints, not a fixed destination. If a newer home needs preparation, reuse ordinary bounded transfer preparation/timeout and revalidate afterward; never spawn at a retired home. The stock asynchronous transfer exposes only optional source-policy, target-spawn and result hooks; Hearth supplies its policy through registration. Return `ActionDeferred` on accepted transfer work, then start cooldown exactly once after successful body relocation, before initial target snapshots. Failure/rollback starts none. Pre-detach failures finish the exact original deferred action instead of leaving `ActionCompletionStarted` waiting; late results cannot clear a newer session, body or generation.

Revalidate the action generation, connection, health/KO, combat and swimming before source saving and again afterward, before destructive capture. The shared resolved-spawn helper holds the target lock across final home resolution, live-object validation and existing exact spawn checks. Changed full identity/location retires the unpublished AOI and repeats preparation within one deadline. Actual coordinates reach participants and position persistence. Clearance uses the player footprint only; no nearby fallback. Use the existing carry participant. Allow post-KO lying only by Hearth transfer policy: use a separate standing target snapshot and preserve the lying rollback snapshot. Other transfer causes retain their rules and ordinary post-capture disconnect handling.

Interruption is an optional active-handler policy invoked through existing cancellation paths at valid gameplay intent, before another action's eligibility/cooldown rejection. Include fresh movement attempts, context/craft/build/carry/Stand Up attempts, any damage, combat/swimming and ordinary disconnect cleanup. Invalid/stale input is not gameplay intent. Chat and personal windows do not interrupt. The client sends existing `C2S_CancelAction` when its cooldown UI blocks another attempted action during return; no new command protocol is needed.

After restoring home metadata, login keeps `tryReattachPlayer` before normal spawning. The spawn fallback tries saved position, exact current home if present, nearby saved-position candidates, then existing random fallback, carrying each candidate's layer. Saved-layer reattachment is followed by a surface-body check so an already relocated body wins over a stale saved layer. Capture original runtime KO/combat data before changing candidate layers, preserve normal lying pose, and retire old caches at successful attachment while still holding the body's shard lock. Every successful candidate shares one owning-shard critical section for spawning, character registration and attachment or logout through the existing locked finalizer. A successful cross-layer login then reuses existing `UpdateCharacterPositionAndLayer` outside that lock with an independent bounded context: ordinary CharacterSaver updates coordinates but omits Layer. No later attachment or logout follows this write, since an intervening world update may already have completed permanent death. This ordinary position write keeps the stock transfer warning policy on failure. Missing ownership never creates an object or changes ordinary first-entry spawn eligibility; metadata loading does not implement this fallback.

### 8. Reuse approved assets and a small transient FX path

Keep the existing green fire and skull-smoke assets; do not generate replacements. Play the eight skull frames once over two seconds at the event position, independent of the surviving object/player view. The renderer is reusable for other death events; animal event wiring is not added by this change.

Reuse `S2C_Fx` fields 1/2; add only `stream_epoch = 3` for world-event freshness. Publish once from real runtime death/conversion to event-time observers and matching sessions. No persistence worker sends effects, and restore/view rebuild never synthesizes old events. No event-ID sequence, retransmission/dedup service, server-authored expiry or new clock protocol is required.

Preload through existing asset loading, bound concurrent one-shot effects, and use a local monotonic two-second deadline starting at playback. Clear effects on world/layer/session/reset/destroy and invalidate late callbacks with the existing reset-generation pattern. Suspended rendering does not extend an already started effect. Legacy local-player `exp_gain` and continuous burning-campfire smoke retain their behavior.

## Risks / Trade-offs

- [Crash or independent save snapshots] -> Recent construction, home changes or death can roll back or lose a home. Conservative restore removes invalid runtime ownership; no lossless or cross-feature checkpoint is claimed.
- [Synchronous construction I/O] -> Read/wait before final costs with separate five-second contexts, then save with a five-second transaction context after runtime completion; accept whole-loop delay, cumulative latency and queued cancellation during the call.
- [Synchronous login lookup] -> Unknown home metadata is read under the surface shard lock with a five-second timeout; accept whole-loop delay as for construction. Client cancellation does not abandon an accepted lookup and is checked again before entry.
- [Stale saved data] -> Existing raw/load guards and `LoadIfUnknown` preserve known current runtime state. No asynchronous Hearth read/save acknowledgment exists.
- [Hearth database error] -> Stop the entire server, including on unknown commit outcome; do not add SQL retries or database-error recovery. The preceding REST character DELETE preserves HTTP 500 on SQL failure and does not start cleanup without a confirmed affected row.
- [Activation I/O and index memory] -> A synchronous batch read and orphan transaction can delay the whole game loop. Index entries stay for the process lifetime, so memory grows with encountered characters; there is no dirty queue, save-lag metric or eviction framework.
- [Cross-layer terminal work] -> Mark the logical home ineligible immediately, release the source lock, and finish conversion/save on the surface owner before the current call returns; validate the latest source identity.
- [Transfer admission confused with success] -> Use existing deferred action/rollback and a target-success callback; do not charge cooldown at queue admission.
- [Cosmetic delay] -> FX is best effort and locally short-lived. It has no durable exactly-once delivery guarantee and does not roll back gameplay.

## Migration Plan

1. Add the Hearth association migration, canonical schema and sqlc queries together; regenerate rather than hand-edit generated code. The feature is undeployed, so no corrective migration or legacy backfill is needed.
2. Implement and test runtime construction/ownership with synchronous construction saving before adding terminal persistence and return. Prepared art remains input; previous reverted code is not counted as delivered work.
3. Regenerate server/client protobuf only for the additive FX epoch field. Run server, PostgreSQL schema/projection, client and relevant asset checks for implemented scope.
4. The owner prepares the approved clean database/world before release. The application performs no automatic database cleanup. Rollback of a populated feature world requires a compatible backup or explicit cleanup; dropping the table under a running writer is not supported.
