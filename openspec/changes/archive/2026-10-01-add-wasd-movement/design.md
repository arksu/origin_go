# Design

## Context

Мотивация и границы продукта описаны в [proposal.md](proposal.md). Пользователь согласовал экранное WASD, серверное движение, совместимость с мышью и подготовку плана; затем отдельно потребовал точечных, production-ready изменений. Документ описывает запланированную реализацию, а не уже внесённые изменения.

Проверенные точки текущего кода:

| Область | Текущее поведение и место интеграции |
| --- | --- |
| Ввод | `web_new/src/game/InputController.ts` получает keyboard/pointer events; клавиатура пока обновляет только модификаторы. Уже есть очистка на blur/visibilitychange/destroy. |
| Горячие клавиши | `composables/useHotkeys.ts` обслуживает разовые UI-команды; отдельного непрерывного ввода нет. WASD не включаем в этот механизм. |
| Команды | `PlayerCommandController.ts` отправляет `MapClick`; `Render.ts` выбирает click/placement/hand-drop/long-press и камеру. |
| Сеть | `game/game.go:handlePlayerAction` преобразует protobuf в `PlayerCommand`; `network/command_queue.go` сохраняет порядок команд одного клиента. Значения по умолчанию: 40 команд/с, 20 команд/тик/клиент. Переполнение fairness откладывается на следующий тик. |
| Авторитетное движение | `components/movement.go` хранит target point/entity; `systems/movement.go` вычисляет intent; `collision.go` разрешает столкновения; `transform.go` применяет позицию, расходует выносливость и формирует movement batch. |
| Полная блокировка | `TransformUpdateSystem` сейчас вызывает `StopAtPointTarget`, который очищает цель. Для удерживаемого направления такое поведение нужно отделить от прекращения ввода. |
| Действия | `ActionService.Cancel` отменяет gameplay action; `ContextActionService.cancelActiveCyclicAction` завершает другие циклы и очищает `ActiveCraft`. `ClearPlayerInteractionIntents` удаляет ожидания pickup/context/link, но сам активный link не разрывает. |
| Сессия | `Shard.Clients`, `Client.InWorld`, `Client.StreamEpoch` представляют активное соединение и мир. В `processPlayerCommand` пока нет общей проверки актуального соединения; новую проверку ограничиваем directional command. |
| Представление | `TimeSync` использует базовую интерполяционную задержку 120 мс, до 250 мс при jitter; `movementTiming.ts` задаёт завершение ходьбы за 300 мс. Клиентского предсказания нет. Маркер цели берётся из серверного `targetPosition`. |

Существующие `map-click-input` и `game-actions` сохраняют правила маршрутизации. Их delta-спецификации добавляют WASD и переключение ввода, не заменяя старые требования целиком.

## Goals / Non-Goals

**Goals:**

- Один серверный путь физики и ограничений для click и directional movement.
- Явное владение движением: направление, точка либо объект; старое удержание не оживляет заменённую команду.
- Ограниченная длительность ввода без зависимости от FPS, key repeat и надёжности доставки последнего keyup.
- Детерминированные проверки поведения на границах сетевого ввода, ECS и lifecycle клиента.
- Небольшие связанные изменения, каждое объясняется требованием или регрессионным тестом.

**Non-Goals:**

- Не расширять `GameConnection` в общий command bus, не перестраивать очереди, action framework или UI hotkey system.
- Не добавлять второй расчёт физики, глобальную систему prediction/reconciliation, новую систему настроек или зависимости.
- Не менять семантику обычных кликов, режимы скорости, формулы выносливости, алгоритм скольжения и общий формат movement broadcast.
- Не сохранять клавиши, revision, lease или направление в БД, transfer snapshots или localStorage.

## Decisions

### 1. Экранный вектор преобразуется до нормализации

`InputController` ведёт набор физических `KeyW/KeyA/KeyS/KeyD`. Из него получается `screenX = D - A`, `screenY = S - W`. Ненулевой вектор преобразуется через существующее линейное `coordScreen2Game`, после чего нормализуется в мировых координатах; именно нормализованный вектор клиент сериализует в `MoveDirection`. Нулевой вектор передаётся как (0,0) без нормализации и означает release. Положение камеры, viewport и zoom не участвуют: это направление, а не экранная точка.

Для текущей проекции 64x32 контрольные соотношения до нормализации: W -> (-1,-1), D -> (1,-1), W+D -> (-1,-3). Последнее после проекции даёт экранную диагональ 45 градусов. Нормализация до обратной проекции или наивная таблица мировых диагоналей дали бы неодинаковую мировую скорость либо неверные экранные углы.

Противоположные клавиши обнуляют свою ось. Переход к нулю является остановкой; возвращение к ненулевому вектору после отпускания одной противоположной клавиши является новым вводом. Shift разрешён без переключения режима скорости. Ctrl/Alt/Meta и composition приостанавливают WASD, чтобы не перехватывать браузер и редакторы.

### 2. Отдельный небольшой protobuf-контракт

Добавить `MoveDirection` в свободное поле `C2S_PlayerAction.action` (в текущем контракте доступно поле 6):

| Поле | Тип | Назначение |
| --- | --- | --- |
| `x`, `y` | `float`, поля 1 и 2 | Нормализованное клиентом направление в мировых координатах, единичной длины с учётом точности float; (0,0) означает release. |
| `input_revision` | `uint32`, поле 3 | Ревизия эффективного ввода; 0 запрещён. Изменение направления/остановка увеличивает ревизию, heartbeat повторяет её. |
| `stream_epoch` | `uint32`, поле 4 | Эпоха из текущего enter-world; защищает от ввода из предыдущего мира на том же соединении. |

Например, для W+D соотношение мировых компонент (-1,-3) перед отправкой становится примерно (-0.316228,-0.948683). Отправка сырого результата проекции не соответствует клиентскому контракту: сервер сначала проверяет диапазон каждой компоненты [-1,1], затем повторно нормализует допустимый ненулевой ввод, не доверяя клиенту расчёт скорости. Heartbeat повторяет уже нормализованный сериализованный вектор.

В `S2C_PlayerEnterWorld` добавить `directional_movement_supported` в свободное поле 10. Это один capability bit, позволяющий новому клиенту безопасно работать со старым сервером и откатить backend. Отсутствие поля означает отсутствие поддержки. Поля 1/2/3 старых player actions остаются reserved. Генерация: `make proto` и `npm --prefix web_new run proto`; сгенерированные файлы руками не исправлять.

Альтернативы: эмуляция MapClick смешивает движение с выбором целей; клиентские координаты требуют доверять позиции; отдельный транспорт и полная negotiation-система избыточны. Новый action проходит через действующую последовательность WebSocket/PlayerCommand, без отдельного канала и без ACK-схемы для prediction.

### 3. Ревизия различает новое действие и подтверждение удержания

На клиенте ревизия монотонна в пределах активной сессии/эпохи, с uint32 serial comparison и пропуском нуля. Heartbeat повторяет тот же сериализованный вектор и revision. Смена только физических клавиш без изменения результирующего вектора не создаёт нового пакета.

В серверном runtime-состоянии сохраняются последняя принятая/закрытая revision и принадлежность сессии, даже после прекращения направления. Дополнительный журнал команд не нужен.

| Вход | Действие |
| --- | --- |
| Новая валидная ненулевая revision | Проверить право двигаться, отменить мешающий выполняемый action, установить направление. |
| Та же revision, то же активное направление | Только продлить оставшийся срок; не отменять действие и не сбрасывать коллизии. |
| Та же revision после stop/expiry/смены владельца | Игнорировать; это подтверждение законченного ввода. |
| Та же revision с другим вектором или старая revision | Игнорировать без побочных эффектов. |
| Новая нулевая revision | Запомнить release; остановить только directional movement. Точечную/объектную цель не трогать. |
| Новая структурно валидная, но просроченная или запрещённая состоянием revision | Закрыть эту revision без запуска и без отмены действия: heartbeat не должен превратить отказ в новое нажатие. |
| Невалидный payload/чужая сессия | Отвергнуть до изменения high-water mark, movement или action state. |

Сравнение uint32: новая revision имеет положительную разницу меньше половины диапазона; граничные случаи покрываются тестами. Counter обычного `ClientMessage.sequence` продолжает работать как сейчас и не заменяется.

### 4. Ограниченный срок удержания и текущая очередь

Именованные значения первой версии: heartbeat 200 мс на клиенте и TTL 800 мс на сервере. Их держим в небольших constants-файлах соответствующих слоёв и фиксируем совместимость в тестах. Не добавляем новый раздел пользовательских настроек. При неизменном удержании это пять refreshes в секунду плюс start/stop; запас относительно текущего лимита 40 команд/с сохраняется для других команд.

`ReceivedAt` нового ввода должен происходить от того же серверного clock, что `TimeState.WallNow`. В ECS сначала вычисляется возраст пакета на начало тика; крайний срок в runtime time равен `TimeState.Now + max(0, TTL - age)`. Не сравнивать wall Unix milliseconds с runtime game time. Системы читают `TimeState`, не вызывают собственный `time.Now`. Просроченный ненулевой ввод не оживляет персонажа после отложенного drain. Свежие release применяются немедленно; старый release допустимо обработать как закрытие своей revision, поскольку он не способен остановить другой тип движения.

Проверка expiry должна работать и когда персонаж упёрся и `StateIdle`. Equal-revision heartbeat, пришедший уже после expiry, не возобновляет направление. На клиенте длительная пауза таймера не компенсируется burst: удержание сбрасывается, требуется свежее нажатие.

Fairness, rate limit, backpressure и порядок общей очереди сохраняются. В одном тике несколько изменений последовательно меняют intent, а физический шаг выполняется один раз по итоговому состоянию. Никакого приоритетного выноса stop впереди ранее полученных команд и coalescing через клики: это могло бы изменить порядок действий.

### 5. Проверка сессии выполняется повторно при применении

Ingress проверяет тип payload, числовые границы, authenticated/in-world и epoch. Перед ECS-эффектами directional handler повторно подтверждает, что `cmd.ClientID` относится к текущему `Shard.Clients[playerID]`, клиент всё ещё `InWorld`, epoch совпадает и игрок не detached/dead. Использовать узкий session-validator callback/interface, предоставленный `Shard`, с существующей синхронизацией; не импортировать game layer в ECS и не дублировать registry соединений.

Это необходимо, поскольку пакет мог пройти ingress до detach/teleport и остаться в очереди. В production directional input без подключённого validator запрещён; в тестах подставляется явный валидатор. Новые revision допустимы после смены подтверждённой сессии; сами по себе packet ClientID/epoch не переопределяют владельца состояния.

При reconnect, world entry, transfer и rollback переносится только существующее состояние персонажа: удержание не восстанавливается. На сервере новые lifecycle resets очищают active direction; на клиенте reset мира очищает таймер/keys/support/epoch. Старые queued commands должны пройти повторную проверку и быть отброшены.

### 6. Направление становится третьим видом movement intent

В `const.TargetType` добавить `TargetDirection` без изменения существующих значений. В `Movement` добавить компактные поля requested direction, revision/session identity, runtime deadline и pending directional update. Поля внутренние, не persistent. Переиспользовать существующие cached storages и prepared query.

В `MovementSystem` обработка `TargetDirection` и pending directional update располагается до существующего раннего выхода `movement.State != StateMoving` и до point-target arrival logic, в том же проходе prepared query. Поэтому `StateIdle` после упора не исключает сущность из проверки expiry и следующего collision probe, а pending update после очистки направления позволяет отправить остановку. Допуск к обработке не разрешает перемещение при stun/KO или другом жёстком запрете: эти ограничения проверяются до физического шага.

Для активного направления:

1. Проверить expiry и жёсткие ограничения состояния; потеря права двигаться закрывает revision.
2. Применить существующий выбор допустимого режима и скорости; один общий путь вычисления скорости для всех видов движения.
3. Рассчитать velocity = normalized requested direction * allowed speed и один intent position = current position + velocity * dt.
4. Передать intent в `MovedEntities`, затем существующую collision/transform цепочку.

`SetTargetPoint`, `SetTargetHandle` и `ClearTarget` завершают активное направление и deadline, но сохраняют закрытую revision до reset сессии. Не стирать запрет `StateStunned` helper-ом ручной остановки. Нельзя применять `HasReachedTarget`/`StopAtPointTarget` к направлению и создавать фиктивную далёкую точку.

Release/expiry помечают необходимость итогового update, даже если персонаж уже стоит. Для новой directional ветки остановка отправляется из общего движения по конечному состоянию тика, а не вторым физическим шагом из network handler. Проверить start/stop/start и stop+MapClick в одном drain: один handle не должен дважды проходить collision/stamina/broadcast из-за нового кода. При необходимости локально свести pending directional update с уже существующей записью; не переделывать весь `MovedEntities`.

Альтернатива отдельной keyboard simulation system дублировала бы проверки скорости/стамины. Отдельный component не нужен: он усложнил бы очистку на многочисленных существующих `ClearTarget`/`SetTarget*` переходах.

### 7. Коллизия останавливает тело, сохраняя допустимый ввод

Существующий swept collision и slide algorithm не меняются. Меняется directional branch в `TransformUpdateSystem`: полная блокировка обнуляет фактическую скорость и задаёт idle, сохраняя `TargetDirection`, requested vector и неизрасходованный срок. Следующий тик снова может проверить такое направление, даже если визуально персонаж стоит.

Для directional movement broadcast velocity и `isMoving` выводятся из фактического post-collision displacement за dt; requested direction хранится отдельно. Это исключает extrapolation сквозь препятствие, ложную ходьбу и расход стамины за нулевой путь. При ненулевом displacement heading соответствует фактическому направлению, при полном упоре сохраняется последнее осмысленное facing. Частичное скольжение использует действующий collision budget.

Первый переход moving -> blocked, release/expiry, изменение позиции/heading/mode и возобновление обязаны попасть в существующий movement batch. Повторное полностью одинаковое blocked-состояние не требует нового broadcast каждый тик. Локальное подавление таких directional duplicates не меняет point/entity потоки, AOI, stream epoch или формат `move_seq`. Саму проверку collision при действительном удержании сохраняем, чтобы удаление препятствия позволило продолжить движение.

`broadcastMoveTarget` для нового target type возвращает false. Нет `PointMovementStoppedEvent` для направления; иначе callback подхода мог бы выполнить отменённое действие. Маркер исчезает по обычному server-driven правилу отсутствия `targetPosition`.

### 8. Клиентский lifecycle и владение клавиатурой

Распределение ответственности:

- `InputController`: нажатые/подавленные physical codes, фильтрация событий и focus, вычисление изменения screen direction; не отправляет сеть.
- Небольшой `KeyboardMovementController` в `game/`: преобразование направления, revision, один refresh timer, enable/reset/handoff; не импортирует Pixi. `Render` владеет экземпляром и его lifecycle.
- `PlayerCommandController`: сериализация `sendMoveDirection`; хранить lifecycle counters в keyboard controller, не в сетевом singleton.
- `Render`/`GameFacade`: связывают input и command controller, предоставляют точечные enable/reset/release методы для Vue/network lifecycle.
- `network/handlers.ts` и `network/index.ts`: текущая эпоха/поддержка на enter, reset на leave/error/disconnect и local-player teleport. Не устанавливать второй `onStateChange`: текущий callback одиночный.
- `GameView.vue`: передаёт блокировку ввода от реальных blocking modal states и готовности мира через facade. Non-modal inventory/character window сам по себе не блокирует WASD.

Обрабатывать `focusin` немедленно: одной фильтрации будущего keydown недостаточно, если игрок держит W и нажал Enter для чата. Для editable проверять input/textarea/select и `isContentEditable`, учитывая event path; compositionstart останавливает ввод. Keyup очищает state вне зависимости от focus. Браузерные shortcuts не подавлять `preventDefault`; у обработанных movement keys подавлять только игровое действие по необходимости.

При handoff сохраняется набор уже удерживаемых keys как подавленный до keyup. Новый неповторный keydown может начать новый ввод, старые подавленные клавиши в него не добавляются. После blur/focus return повторные keydown игнорируются до свежего нажатия. Если keyup потерян вне окна, новый `keydown` с `repeat=false` снимает старое подавление именно этой клавиши: не требовать дополнительного нажатия и не оставлять её заблокированной навсегда. Destroy/reset идемпотентны и удаляют timer/listeners; offline reset не пытается повторно отправлять пакет. Таймер проверяет connected + world ready + support + enabled перед каждой отправкой.

### 9. Переключение управления выполняется в местах реальных команд

| Событие | Keyboard state | Существующая команда |
| --- | --- | --- |
| Map primary/secondary/long-press | Если активен: сначала directional release и suppression. | Обычный ровно один MapClick. |
| Placement/hand-drop click | Release до side-effect callback или inventory operation. | Существующий placement/drop; не добавлять второй MapClick. |
| Context select / activate action / start craft / build execution | Release и suppression перед отправкой. | Существующий запрос без изменения payload. |
| Camera pan/zoom, pointer hover | Без изменений. | Существующее управление камерой. |
| Открытие non-modal UI | Без изменений до фокуса editable. | Существующий UI hotkey. |
| Keyup от подавленного hold | Только очистка физической клавиши. | Пакет не отправляется. |

Release использует то же WebSocket-соединение и идёт перед передающим управление запросом. Он не является `C2S_CancelAction`. При отсутствии active keyboard input ничего не добавляется, поэтому мышиные сценарии, long-press suppression и число их пакетов сохраняются. Отдельный `MapClick` без preceding release по-прежнему имеет старую серверную семантику, в том числе secondary ground не останавливает unrelated click route.

Встраивать handoff в явные отправители команд/facade, без глобального перехвата всех `gameConnection.send`. Учесть ранний путь `trySendDroppedItemMapClick`, placement callbacks и отправители `network/index.ts`, не только основную ветку `Render.onClick`. На сервере переход к point/entity intent также закрывает directional revision, чтобы delayed heartbeat не перехватил маршрут.

### 10. Отмена действия предшествует новому движению

После структурной/session/freshness проверки и проверки допустимости движения, но до установки направления:

1. Для `ActiveGameAction` в selecting оставить action, generation и cursor. Для approaching/executing вызвать существующий `ActionService.Cancel`.
2. Очистить pending pickup/context/link intents через `ClearPlayerInteractionIntents`.
3. Разорвать активный link через `ecs.BreakLinkForPlayer` с существующей причиной и событиями; не удалять map-entry вручную. Ошибку публикации обработать явно, не запускать движение при незавершённом cleanup.
4. Если остался non-gameplay cyclic action, завершить его через узкий публичный adapter существующего `ContextActionService.cancelActiveCyclicAction` (он также чистит `ActiveCraft`). Это нужно и для крафта без объекта/link.
5. Перечитать `Movement` после callback-ов и установить свежий direction intent. Не записывать старую копию компонента поверх изменений отмены.

Очистка выполняется один раз на новый принимаемый ввод, не на каждый heartbeat. Защита generation и существующий механизм отмены сохраняются; особенно проверить cancel на последнем тике до эффекта. При упоре в стену отмена всё равно состоялась. Подтверждённый ранее результат/потраченная movement stamina не откатываются.

### 11. Измеримая приёмка без скрытого изменения rendering

Три разных момента фиксируются отдельно: keyboard event/send, authoritative motion update, окончание visual transition. Первая версия не обещает мгновенную визуальную остановку: сервер отвечает по тикам (по умолчанию 10 Гц), затем действуют сеть, interpolation 120–250 мс и существующий stop transition 300 мс.

Автоматические тесты проверяют физический/сетевой контракт, browser smoke — направление, плавность, camera/marker, UI focus и perceived latency. При неприемлемом управлении результат не объявляется production-ready только потому, что тесты прошли: сохраняется конкретное измерение и решение о следующем отдельном изменении rendering/prediction. В этой реализации не уменьшать глобальные задержки и не перемещать sprite напрямую для маскировки проблемы.

## Risks / Trade-offs

| Риск | Мера |
| --- | --- |
| Буферизация TCP/очереди после отпускания | Lease ограничивает молчание после серверного receipt; возраст в очереди учитывается. Время в пути до сервера не измеряется доверенным server clock и не входит в обещание 800 мс. Зависший transport проверять отдельно, не обещать абсолютный deadline от физического keyup. |
| Поздний heartbeat после другой команды | Revision watermark сохраняется после завершения; повтор продлевает только текущий hold. |
| Повторная сессия/перенос на том же соединении | Повторная server session/epoch проверка в ECS и reset на обеих сторонах. |
| Collision stop выглядит как движение | Requested vector отделён от resolved velocity; blocked переход broadcast-ится, одинаковые повторы подавляются. |
| Потеря стамины или запрет движения | Существующие проверки сохраняются; запрет закрывает hold без auto-resume. |
| Лишние события одного entity за тик | Pending directional update сводится к одному итоговому физическому шагу; тесты проверяют batch count и stamina. |
| Текст/модальные окна перехватываются WASD | Focus/composition/lifecycle reset, keyup вне фильтра editable, suppression held keys. |
| Hotkey/action продолжает старый hold | Единый явный handoff перед нужными отправителями; существующий transport порядок сохраняется. |
| 300 мс завершения ухудшает ощущения | Отдельные измерения latency на browser smoke; без молчаливого расширения объёма в prediction. |
| Разрастание изменения | Никаких общих cleanup commits, новых зависимостей, изменения атласов, БД или blanket fixes соседнего кода. |

## Migration Plan

1. Реализовать и проверить общий контракт и сервер; capability объявлять только после подключения полной серверной цепочки. Старые клиенты продолжают посылать MapClick.
2. Собрать клиент с теми же protobuf bindings; WASD включается только для мира, объявившего поддержку. На старом сервере остаётся управление мышью.
3. До выпуска выполнить автоматическую матрицу и browser smoke из `tasks.md`, включая смешанные версии, reconnect/transfer и задержку сети. Проверить количество input packets и idle/blocked broadcasts, без создания отдельной telemetry-системы.
4. Выпускать сервер перед клиентом; смена backend-соединения обязана очистить удержание. DB migration отсутствует.
5. Rollback клиента возвращает mouse-only управление на новом сервере. Rollback сервера требует закрытия/переподключения его сессий; новый enter-world без capability отключает WASD у нового клиента. Старые подтверждения удержания не переносить через rollout.

Готовность планирования не является подтверждением готовности реализации к выпуску. Все проверки реализации остаются незавершёнными до фактического выполнения.
