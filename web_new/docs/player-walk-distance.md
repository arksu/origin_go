# Ходьба по пройденному расстоянию

Исследование и измерение: 2026-09-09. Изменение касается отображения персонажа;
серверная скорость и сетевой протокол остаются прежними.

## Как это решено в других проектах

| Источник | Механизм | Что подходит нашему клиенту |

Выбран вариант с накоплением дистанции. При постоянной скорости он эквивалентен
множителю `actualSpeed / referenceSpeed`, но сохраняет дробную фазу непосредственно
при переменной скорости, нерегулярном FPS и смене направления.

## Измерение нашей анимации

Из `male_commoner_walk.blend` измерены координаты костей стоп в 13 фазах плоской
опоры каждой ноги. Контакт пятки и отталкивание исключены: во время переката
смещение голеностопа включает вращение стопы и не равно движению корпуса.
Наклон регрессии координаты стопы по нормализованной фазе равен **0,6999996 м за
цикл** для обеих ног. Данные сохранены в
`art_source/characters/male_commoner_v3/pixel_style/walk/stride_calibration.json`.

Далее перемещение спроецировано через **реальную камеру сохранённого .blend**:
ортографический масштаб 1,94, кадр 80×96, угол возвышения 30°. Для каждого
направления результат сравнивается с проекцией единичного мирового перемещения
через `coordGame2Screen` и ромб тайла 64×32.

| Направления | Экранное расстояние за цикл, px при масштабе 1× | Мировое расстояние, тайлы |
| --- | ---: | ---: |
| E, W | 34,6392 | 0,7654244 |
| NE, SE, SW, NW | 27,3847 | 0,7654244 |
| N, S | 17,3196 | 0,7654244 |

Разброс между направлениями — менее 0,0000005 тайла, то есть погрешность вычислений.
Отдельные коэффициенты направлений **не нужны**: камера запекания и игровая
изометрия одинаково сжимают глубину вдвое. Если считать дистанцию в экранных
пикселях, коэффициенты пришлось бы разделить, а также учитывать масштаб камеры.

## Формула в клиенте

```text
distanceTiles += distanceMovedWorld / negotiatedCoordPerTile
frame = floor(distanceTiles / 0.765424409 * 8) mod 8
```

При текущих `CoordPerTile = 12`:

- 9,1850929 единицы мира на цикл из двух шагов;
- 1,1481366 единицы мира на смену кадра;
- 0,8709765 кадра на единицу мира;
- эквивалентный FPS анимации = скорость в мире × 0,8709765.

| Скорость, ед./с | FPS спрайтовой анимации | Цикл, с |
| ---: | ---: | ---: |
| 4 | 3,484 | 2,296 |
| 9,568 (исходный темп) | 8,333 | 0,960 |
| 16 (текущий Crawl) | 13,936 | 0,574 |
| 32 (текущий Walk) | 27,871 | 0,287 |
| 48 (текущий Run) | 41,807 | 0,191 |
| 64 (текущий FastRun) | 55,742 | 0,144 |

Это частота смены **кадров спрайта**, а не FPS приложения. При низком FPS
рендеринга промежуточные позы могут пропускаться, но фаза остаётся связанной с
пройденной дистанцией. Скорости режимов проверены в `internal/const/const.go` и
`internal/ecs/components/movement.go`; в runtime режим не используется для
вычисления темпа, поэтому замедление фактического движения учитывается автоматически.

## Источник дистанции и границы решения

`MoveController.update()` измеряет перемещение **после интерполяции и сглаживания**.
Телепорт заранее переносит начальную точку измерения; большой correction snap
даёт нулевую дистанцию. Render передаёт результат ObjectManager, затем ObjectView.
Для прямых обновлений ObjectManager может вычислить дельту по позиции объекта.
Масштаб/сдвиг камеры и округление экранных пикселей не участвуют в расчёте.

Смена направления сохраняет накопленную фазу. При нулевом перемещении фаза не
продвигается. `RenderPosition.isMoving` описывает визуальное движение: после
серверного `isMoving = false` ходьба продолжается, пока сглаживание доводит тело
до конечной точки. Уменьшающаяся дистанция за кадр автоматически снижает частоту
смены поз; фазу нельзя сбрасывать по самому факту получения серверной остановки.

Когда интерполируемая цель уже неподвижна, остаток до **1/256 тайла** (не более
0,18 пикселя при масштабе 1×) завершается точным попаданием в серверную координату.
Это убирает бесконечный хвост экспоненциального приближения. До времени будущего
stop-кадра движущаяся интерполируемая цель не считается конечной точкой.
Сглаживание учитывает время между обновлениями: коэффициент
`1 - (1 - correctionSpeed)^(deltaMs / (1000 / 60))` сохраняет прежнее поведение
при 60 FPS, а длительность остановки почти не зависит от частоты рендеринга.

При точном прибытии включается отдельная стойка и сбрасывается цикл. Новый старт
до прибытия сохраняет фазу; старт после стойки начинает новый цикл. Телепорты и
большие correction snap не добавляют шаги. KO сразу выбирает стойку и игнорирует
дальнейшую ходьбу, даже если контроллер ещё корректирует позицию.

Короткий исходный шаг при серверной скорости Walk проигрывается примерно в 3,34
раза быстрее исходного рендера. Это закономерный результат согласования длины
шага и скорости. Для естественного бега нужен отдельный клип с более длинным
шагом; ограничение FPS снова вызвало бы скольжение. Восемь дискретных кадров также
оставляют ступенчатое движение стоп внутри каждого кадра. Эта правка убирает
накопленное рассогласование темпа, но не добавляет промежуточные позы или IK.
